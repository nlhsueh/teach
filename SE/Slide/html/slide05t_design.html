歡迎進入 5.1 節：軟體設計導論、流程與設計規格。 在軟體工程中，如果需求工程是探索「要做什麼 (What)」，那麼軟體設計就是決定「如何建造 (How)」。 很多初學者一拿到需求就急著開 IDE 寫程式，但缺乏系統化的設計流程與軟體設計文件，程式碼很快就會演變成無法維護的泥淖。 在這一節中，我們將探討軟體設計的本質、不良設計的四大病徵，以及貫穿本章的「四階段軟體設計流程」與「軟體設計文件 (SDD 與 ADR)」。 總結這張投影片，請記住這個核心觀念：軟體設計是透過四階段系統化工程流程，將使用者需求轉化為架構、介面、物件與資料規格藍圖的關鍵階段。

什麼是軟體設計？ 回顧先前的章節，需求工程給了我們功能規格，例如購物車結帳或使用者認證。 但如果工程師直接從需求跳進寫程式，馬上會面臨無數難題：API 該如何開？資料要存關聯式資料庫還是 NoSQL？當十萬人同時上線時系統會不會崩潰？ 軟體設計就是有系統地回答這些問題的工程學科。它不是表面的視覺排版，而是整套軟體系統的結構與行為藍圖。 總結這張投影片，請記住這個核心觀念：軟體設計是連接抽象人類需求與具體可執行代碼的智慧藍圖。

為什麼軟體設計至關重要？ 第一，缺乏設計會導致盲目開發。初期感覺進度飛快，但幾週後代碼就變得無比僵硬且脆弱：動一行就壞三處。 第二，系統品質無法靠測試憑空產生。你不可能寫出一個高耦合的單體系統，然後靠幾個單元測試就把它變成全球分散式的容錯平台。 第三，Barry Boehm 著名的修復成本曲線顯示：在設計階段發現並解決架構盲點只要 1 塊錢，上線後才重構要花 50 到 100 倍！ 總結這張投影片，請記住這個核心觀念：嚴謹的軟體設計能大幅降低長期維護成本，並將卓越品質深植於系統基因中。

我們進一步拆解左欄的「四大設計階段」與右欄的「設計文件交付產物」。 請看左欄卡片上半部：這四個階段分別解答了軟體設計由巨觀到微觀的四個核心問題，並各自對應專屬的 UML 圖表： 階段一 (5.3 節) 決定巨觀架構模式，並用 UML 套件圖管原始碼相依、用 UML 部屬圖管雲端硬體容器； 階段二 (5.4 節) 規範模組邊界與契約式設計 (DbC)，並用 UML 組件圖的棒棒糖與插座接合 API； 階段三 (5.5 節) 走進組件內部，用 UML 類別圖落實 GoF 設計模式與 SOLID 原則； 階段四 (5.6 節) 用 UML ERD 實體關聯圖與多模態架構設計資料庫與快取。 但請同學特別注意左欄下半部的重點提醒：**為什麼我們課本按照 5.3 → 5.4 → 5.5 → 5.6 的順序講？** 因為從「一萬英尺高空的巨觀架構」一路推進到「地面上的類別與資料表」，最符合大腦建立全景認知的學習順序！ 然而在真實工程與各位的畢業專題中，**Stage 1 到 Stage 4 絕不是死板的單向瀑布步驟**！ 舉例來說：當大家開發選課系統、電商後台或企業資訊系統 (ERP/CRUD) 時，實務上最常見的反而是 **「資料先行 (Data-First：Stage 4 → Stage 2 → Stage 3)」**——團隊會先從 **Stage 4 (5.6 節)** 把核心資料庫 ERD 綱要與欄位確定下來，接著再往外定義 **Stage 2 (5.4 節)** 的前後端 API 契約與 **Stage 3 (5.5 節)** 的物件類別！若是做領域驅動設計 (DDD)，則會從 **Stage 3 領域物件模型** 先行切入。因此，請把這四個階段視為**彼此交織、雙向回饋的四個設計維度**！ 再看右欄卡片：這四個維度的設計成果最終會匯聚為 **軟體設計文件 (SDD)** 與 **ADR 架構決策記錄**——既交代清楚「系統怎麼建 (How)」，也完整保存「為什麼這樣取捨 (Why)」！ 總結這張投影片，請記住這個核心觀念：四大設計階段代表四個緊密交織的設計維度，實務上可依系統特性採「架構先行」或「資料先行」彈性切入，並產出完整的 SDD 與 ADR 藍圖。

請看這張核心總覽圖——它將剛才我們所講的「四大設計維度與雙向迭代流程」完整視覺化，同時也是我們第五章的章節導覽地圖！ 請看最左側的輸入：軟體設計承接需求工程的兩大輸入——功能規格 (SRS 與使用案例) 以及非功能品質驅動因子 (關鍵架構需求 ASR)。 再看正中央的四階段設計流程，每一階段皆搭配專屬的 UML 或資料圖表： 第一階段（**5.3 節**）是 **架構設計 (Architectural Design)**：進行子系統分解、組合架構模式、執行 ATAM 權衡，並以 **UML 套件圖** 與 **UML 部屬圖** 塑模巨觀結構。 第二階段（**5.4 節**）是 **介面與契約規格 (Interface & Contract Specification)**：建立資訊隱藏邊界、定義 **契約式設計 (DbC)**，並以 **UML 組件圖** 的棒棒糖與插座塑模組件合約。 第三階段（**5.5 節**）是 **組件與物件導向設計 (Component & Detailed OO Design)**：深入組件內部，運用 GoF 設計模式與 **SOLID 五大原則**，並以 **UML 類別圖** 塑模。 第四階段（**5.6 節**）是 **資料與持久化設計 (Data & Persistence Design)**：進行三層次資料塑模、繪製 **UML ERD 綱要**，並設計 SQL、Redis 與 Kafka 多模態儲存。 請特別留意四個方塊之間的**雙向箭頭**以及下方的**多起點迭代迴路**：教學上我們由左至右（巨觀 5.3 → 微觀 5.6）依序探索；但在實務開發中，你可以從 Stage 1（架構先行）切入，也可以從 Stage 4（資料結構 ERD 先行）往回推導 API 與類別！ 總結這張投影片，請記住這個核心觀念：軟體設計串聯「架構 (5.3) ⇄ 介面契約 (5.4) ⇄ 物件導向 (5.5) ⇄ 資料設計 (5.6)」四大交織維度，透過雙向迭代產出 SDD 與 ADR 規格。

歡迎進入 5.2 節：通用軟體設計核心原則。 無論你是在跨雲端環境設計一個由數十個 Kubernetes 叢集組成的微服務平台，還是在寫一個二十行的 Java 工具類別，軟體工程背後的物理定律是完全相同的。 在這一節中，我們將學習所有軟體設計的基石：模組化、抽象化、資訊隱藏、關注點分離，以及軟體工程最至高無上的黃金法則：高凝聚度與低耦合度。 總結這張投影片，請記住這個核心觀念：通用設計原則在軟體系統的每一個抽象層次中都如分形般一體適用。

為什麼我們稱這些原則為「通用」原則？ 因為軟體設計具備分形特性。從高空俯瞰整個企業系統，是服務與服務透過 API 互動；放大到單一微服務內部，是套件與套件透過介面溝通；再放大到單一套件內部，是類別與類別透過方法呼叫。 在每一個縮放視角下，規則始終如一：職責專一、彼此解耦、隱藏內部、關注點分離。 總結這張投影片，請記住這個核心觀念：通用設計原則在系統、套件與類別尺度中分形運作，保護人類工程師免於認知超載。

這四大原則是乾淨程式碼的基石： 抽象化讓你在呼叫 map.insert 時，不必管底層是紅黑樹還是雜湊表； 封裝與資訊隱藏運用 private 關鍵字守護內部不變性； 關注點分離確保 UI 程式碼絕不拼接 SQL 語句； 模組化讓數十位工程師能夠同時開工而不互相衝突。 總結這張投影片，請記住這個核心觀念：抽象化、封裝、關注點分離與模組化是抵禦代碼複雜度的四大基石。

如果整堂課你只能記住一句話，請記住這八個字：高內聚、低耦合！ 凝聚度衡量內部專注度：這個類別是只專注於算帳，還是同時包辦發信、產生 PDF 與連接資料庫？我們要追求高凝聚。 耦合度衡量外部牽連度：當我修改 A 類別時，會不會導致十個完全不相關的檔案全部編譯失敗？我們要追求低耦合。 總結這張投影片，請記住這個核心觀念：高凝聚確保內部職責單純聚焦，低耦合杜絕修改引發的致命連鎖反應。

請看這段具體的 Java 代碼對照： 在上面的壞設計中，OrderManager 是典型的上帝類別：一個方法裡塞了 SQL、折扣計算、HTML 模板和底層網路通訊！只要郵件伺服器改通訊協定，結帳類別就得跟著改！ 在下面的好設計中，OrderProcessor 只有一個高內聚職責：工作流調度。它把算數學交給 DiscountCalculator，把存檔交給 OrderRepository，把發信交給 NotificationService。每個協作者都能被獨立測試與替換！ 總結這張投影片，請記住這個核心觀念：將臃腫的單體類別拆解為專注、協同的服務，是實踐高凝聚與低耦合的經典範例。

讓我們深入探討 Larry Constantine 與 Edward Yourdon 提出的經典 7 大內聚力層次。 最高境界是「功能性內聚」：模組或類別只專注做好一件純粹而定義清晰的事情。每一行程式碼都為同一個目標效力。 其次是「順序性內聚」，如流水線般由前一步骤直接供應下一步骤。 而在階梯下方則是常見的反模式：時間性內聚將開機要做的事情全部塞進同一個肥大方法；邏輯性內聚用一個 flag 控制多種不同運算；最嚴重的則是偶然性內聚，也就是大家常見的 GeneralUtils 工具包，裡面什麼雜七雜八的函式都往裡塞。 總結這張投影片，請記住這個核心觀念：極力追求功能性與順序性內聚，並主動重構消除時間性、邏輯性與偶然性內聚。

在看詳細對照表之前，我們先透過這張視覺化全景圖，直觀比較 7 種不同程度的「內聚力 (Cohesion)」。 左半部（綠與藍色系）代表高凝聚、職責清晰的優良設計：第 7 級「功能性內聚」所有元素只為完成單一明確目標；第 6 級「順序性內聚」如同流水線，前一步驟的輸出直接成為下一步驟的輸入；第 5 級「溝通性內聚」共用同一份資料結構；第 4 級「過程性內聚」則依控制流程先後執行。 右半部（橘與紅色系）則是職責糾纏的反模式：第 3 級「時間性內聚」只因同在開機瞬間執行就塞進 initStartup；第 2 級「邏輯性內聚」用外部傳入的 mode 旗標控制龐大的 switch 分支；最糟的第 1 級「偶然性內聚」則是毫無關聯的 CommonUtils 大雜燴。 總結這張投影片，請記住這個核心觀念：模組設計應極力向左上角的「功能性與順序性內聚」靠攏，並重構拆解右半部的旗標大傘與雜物箱類別。

接著我們來看耦合度的 6 大層次，從最危險的緊密耦合邁向最優質的鬆散解耦。 最糟的稱為「內容耦合」：A 模組直接深入 B 模組的私有實作細節，徹底擊穿封裝。B 模組稍有改動，A 模組直接陣亡。 「共用耦合」則是多個模組共用全域變數，往往引發難以重現的並行競爭與副作用。 「控制耦合」是傳入 flag 決定對方的內部分支，這表示呼叫端對被呼叫端的內部實作細節知曉得太多。 「標記耦合」是傳遞過大的資料物件，造成不必要的資料結構綁定。 「資料耦合」是直接呼叫時的黃金標準：只傳入運算所需的純量參數。 而「訊息/事件解耦」則透過事件匯流排達到時空徹底分離。 總結這張投影片，請記住這個核心觀念：杜絕內容與共用耦合，降低控制耦合，優先採用資料耦合與事件驅動設計。

接著我們透過同樣的視覺化風格，對比模組之間 6 種不同程度的「耦合度 (Coupling)」。 左半部代表鬆散、低度牽連的優良耦合：第 6 級「訊息與事件耦合」透過非同步 Event Bus 通訊，發送端與接收端達到零編譯期依賴；第 5 級「資料耦合」只傳遞必要的純量參數（如距離與金額）；第 4 級「標記耦合」則傳遞了整包 CustomerDTO，但對方其實只讀取其中的 zipCode 欄位。 右半部則是高風險的緊密耦合反模式：第 3 級「控制耦合」由呼叫端傳入 flag=2 去遙控被呼叫端內部的 if-else 分支；第 2 級「共用耦合」讓多個模組同時讀寫同一個全域變數 GLOBAL_STATE，極易引發競爭條件；最致命的第 1 級「內容耦合」則直接刺穿封裝邊界，竄改另一模組的 private 私有欄位。 總結這張投影片，請記住這個核心觀念：鬆散耦合如同架構防火牆，能將修改影響完全隔離；緊密耦合則會引發骨牌效應，改動一個欄位就導致全系統連環崩潰。

讓我們檢驗一下對凝聚度與耦合度的理解。 題目問：將高凝聚度與低耦合度結合，最主要的實質工程效益是什麼？ 我們來分析選項： 選項 A，為了極致 CPU 效能把程式碼全混在一起，是在破壞模組化。 選項 C，使用全域變數，是低凝聚高耦合的教科書級反模式！ 選項 D，免除寫測試，是不切實際的幻想。 正確答案是 B！高凝聚讓類別職責聚焦，低耦合確保邊界乾淨——因此改動單一類別時，波及範圍最小。 總結這張投影片，請記住這個核心觀念：高凝聚與低耦合嚴格限制代碼變更的衝擊半徑，確保長期的系統可維護性。

歡迎來到 5.3 節：軟體設計流程的階段一 —— 架構設計：架構模式、ATAM 權衡與套件/部屬圖。 在 5.1 確立了四階段設計流程、並在 5.2 掌握了通用設計原則之後，我們正式進入第一階段：巨觀架構設計 (Architectural Design)。 在本節中，我們首先探索六大經典架構模式（MVC、Layered、Repository、Client-Server、Pipe & Filter 與 Microservices）、剖析外送平台的複合架構與 ATAM 品質權衡；緊接著示範如何使用專屬於架構設計階段的兩張巨觀 UML 圖表——**UML 套件圖 (Package Diagram)**（編譯期模組邊界）與 **UML 部屬圖 (Deployment Diagram)**（執行期雲端硬體拓撲）將系統架構完整描繪出來！ 總結這張投影片，請記住這個核心觀念：階段一架構設計結合了架構模式合成、ATAM 權衡評估，以及 UML 套件圖與部屬圖的巨觀塑模。

什麼是軟體架構？ 軟體架構是系統的根本性組織，體現在其組件、組件與環境的關係，以及指導演進的原則中。 請注意它的橋樑角色：需求工程告訴我們要做什麼，寫程式是具體代碼的產出。架構是連接兩者的橋樑——它決定了系統的骨架模組、資料庫持久化策略與網路通訊協定。 因為架構決策是日後最難、成本最高更換的部分，儘早把架構做對，是專案成敗的關鍵。 總結這張投影片，請記住這個核心觀念：軟體架構透過建立高階組件結構與通訊邊界，串接起抽象需求與具體程式碼。

什麼是軟體架構模式？ 架構模式是針對反覆發生的結構性問題，淬鍊出的標準解法。 請注意，模式不是程式碼，而是結構原型。當架構師提出『分層架構加儲存庫模式』時，團隊每個人腦中立刻浮現出模組邊界與資料流向。 架構模式凝聚了業界數十年的智慧，為工程團隊建立了共同的架構詞彙與可預測的取捨。 總結這張投影片，請記住這個核心觀念：架構模式凝聚成熟結構經驗，為團隊建立共通溝通語言與可預測的權衡指標。

這份六大經典架構模式全景對照表，是架構師必備的工具庫： MVC 解耦呈現與資料； 分層架構建立垂直嚴格邊界； 儲存庫架構圍繞中央資料庫運作； 主從式架構分散運算； 管線過濾器專精串流轉換； 微服務架構則將大系統拆解為獨立部署的網狀服務。 總結這張投影片，請記住這個核心觀念：全景矩陣提供了評估各種經典架構機制與取捨代價的清晰全貌指南。

在逐一深入各個架構模式之前，請先看這張 5.3 節的「架構模式視覺全景導覽圖」。 我們可以將本節的六大經典架構模式分為左右兩大陣營： 左側是「集中式與結構型模式 (Centralized & Structural Patterns)」： 包含垂直分層的 Layered (N-Tier) 架構、分離畫面與狀態的 MVC 架構、圍繞中央資料樞紐運作的 Repository (黑板) 架構，以及最下方的單體架構與模組化組件基礎。 右側則是「分散式、路由與資料流模式 (Distributed, Routing & Flow Patterns)」： 包含跨越網路邊界的 Client-Server 架構、串接無狀態串流轉換的 Pipe-and-Filter 管線架構、各擁私有資料庫的 Microservices 微服務架構，以及底部的事件匯流排 (Event Bus) 與多模式複合架構！ 總結這張投影片，請記住這個核心觀念：掌握「集中結構型」與「分散資料流型」兩大譜系，就能快速建立軟體架構的全景心智地圖。

接著我們深入剖析 MVC 模式的職責分工與工程取捨。 透過將 Model、View 與 Controller 嚴格分離，前端工程師可以隨時改版網頁介面排版，完全不必觸碰底層核心的算帳與驗證程式碼！同時，同一份 Model 可以同時驅動網頁與手機 App 多種視圖。 不過在極簡單的單表維護功能中，完整套用 MVC 可能增加跳轉層級；團隊也必須避免把商業邏輯塞進 Controller 造成「肥控制器」反模式。 總結這張投影片，請記住這個核心觀念：MVC 以少許結構間接層為代價，換取前端視覺與後端領域模型的獨立演進彈性。

我們先透過架構拓撲圖來觀察第一個經典模式：Model-View-Controller (MVC)。 請順著圖中的編號箭頭觀察三角循環資料流： 第一步：User 透過瀏覽器或 App 發送操作請求給 Controller。 第二步：Controller 將操作轉譯為商業動作，呼叫 Model 更新領域狀態。 第三步：Model 狀態變更後，主動發送通知給觀察者 View。 第四步：View 向 Model 查詢最新狀態資料。 第五步：View 將最新畫面渲染呈現給使用者。 總結這張投影片，請記住這個核心觀念：MVC 透過 Controller、Model 與 View 的三角互動迴圈，徹底解耦視覺呈現與底層資料邏輯。

我們接著分析分層架構的核心規範與權衡代價。 分層架構之所以成為企業系統最普及的標準，是因為它的結構天然對齊工程團隊職責：前端、後端業務與資料庫管理各司其職。 它最大的價值在於「變更隔離」：當公司決定更換資料庫引擎時，只需抽換最底層的 Persistence 實作，上層商業邏輯一行都不必改！ 但架構師必須防範「架構水槽反模式」：若多數請求只是機械式穿透四層卻沒有業務邏輯，將白白耗損記憶體轉換與呼叫延遲。 總結這張投影片，請記住這個核心觀念：分層架構確保底層技術變更不波及上層核心業務，但須避免無謂的跨層穿透耗損。

我們來看第二個模式：分層架構 (Layered Architecture) 的視覺拓撲圖。 圖中由上而下垂直堆疊了四個標準抽象層次： 最上層是 Presentation 展示層（Web 畫面、行動介面、REST API 控制器）； 第二層是 Application 應用服務層（負責使用案例工作流調度與交易邊界）； 第三層是 Business / Domain 領域業務層（封裝核心商業規則與實體演算法）； 最底層是 Persistence 持久化與基礎設施層（資料庫存取與外部系統介接）。 請特別注意右側向下的箭頭：每一層只允許單向呼叫其正下方的一層。 總結這張投影片，請記住這個核心觀念：分層架構將系統組織為由上而下嚴格單向呼叫的垂直抽象階層。

接著看儲存庫架構的職責與取捨。 以大家每天用的 VS Code 或 IntelliJ IDE 為例：程式碼高亮器、編譯器、Linter 靜態分析器與除錯器，都需要讀取你正在寫的語法樹 (AST)。若讓工具之間彼此傳遞幾百 MB 的語法樹，記憶體早就爆了！透過中央儲存庫，各工具直接共享同一份核心狀態，外掛擴充無比輕鬆。 但它的致命傷在於單點故障與競爭瓶頸：中央儲存庫一旦當機或鎖死，外圍所有工具將瞬間全數停擺。 總結這張投影片，請記住這個核心觀念：儲存庫架構極度適合多工具高效共享海量複雜資料，但必須嚴密防範中央瓶頸與單一故障點風險。

我們來看第三個模式：儲存庫架構 (Repository Architecture) 的視覺拓撲圖。 請觀察圖中的「星狀輻射樞紐 (Hub-and-Spoke)」結構： 正中央是 Central Repository 中央儲存庫，維護著全系統唯一的真實共享資料（例如 IDE 中的抽象語法樹 AST 或大型共用資料庫）。 四周圍繞著獨立運作的子系統：Code Editor、Compiler、Static Analyzer 與 Interactive Debugger。 請注意：這四個工具彼此之間完全沒有連線，所有資料交換與協作皆透過中央儲存庫完成。 總結這張投影片，請記住這個核心觀念：儲存庫架構透過中央共享資料樞紐，讓多個獨立工具在不產生直接耦合的前提下協同運作。

我們來剖析主從式架構的工程職責與權衡。 主從式架構將最敏感的資料庫與商業邏輯鎖在受防火牆保護的伺服器叢集中，而把輕量化的操作介面交給瀏覽器與手機。當後端需要修補漏洞或升級演算法時，直接更新伺服器即可，全球使用者立即生效。 然而，跨越實體網路意味著「網路永遠是不可靠的」：架構師必須在設計中納入 TLS 加密、タイムアウト重試、快取與負載平衡機制，以應對延遲與流量洪峰。 總結這張投影片，請記住這個核心觀念：主從式架構實現了資料安全與核心運算的集中治理，但必須針對網路延遲與伺服器負載進行韌性設計。

我們來看第四個模式：主從式架構 (Client-Server Architecture) 的視覺拓撲圖。 左側是分布在世界各地的多樣化客戶端 (Clients)：包含 Web 瀏覽器、iOS/Android 原生行動 App 以及門市 POS 終端機。 中間是網際網路邊界 (Network / WAN)，透過 HTTPS、REST 或 gRPC 傳輸加密封包。 右側則是集中式伺服器叢集 (Centralized Server Tier)：由負載平衡閘道器接收流量，分發給可水平擴展的無狀態應用伺服器，最後存取中央資料庫與快取叢集。 總結這張投影片，請記住這個核心觀念：主從式架構跨越網路邊界，將分散式前端互動終端與集中式後端運算儲存清楚分離。

接著我們檢視管線與過濾器模式的職責與優缺點。 因為每一個 Filter 都是無狀態且只認標準資料流，它完全不關心前一手是誰、後一手是誰。這帶來了極致的模組化：你可以隨時在管線中間插入一個「加密過濾器」或「日誌過濾器」，而不必修改任何既有程式碼！ 但請注意它的限制：這種單向流水線完全不適合處理使用者隨機點擊的圖形互動介面，而且每一站對資料的打包與拆包也會消耗 CPU 資源。 總結這張投影片，請記住這個核心觀念：管線過濾器架構賦予資料流處理極致的組合彈性與並行能力，但不適用於互動式使用者介面。

我們來看第五個模式：管線與過濾器 (Pipe-and-Filter Architecture) 的視覺拓撲圖。 請看上半部的單向資料處理流水線： 原始資料從左側 Data Source 流出，經由 Pipe 傳入 Filter 1 進行語法解析 (Parse)； 解析後的結構化串流經由下一段 Pipe 傳入 Filter 2 進行資料清洗與驗證 (Cleanse)； 接著再流入 Filter 3 進行統計聚合 (Transform)，最後輸出至右側 Data Sink。 下半部則是經典的 Unix 命令列管線實例：將 cat、grep、sort 與 uniq 串接成一氣呵成的處理管線。 總結這張投影片，請記住這個核心觀念：管線與過濾器模式將複雜資料處理拆解為一連串無狀態、單向串接的獨立轉換階段。

最後我們深入剖析微服務架構的核心規範與權衡代價。 微服務解決了超大型企業的兩大痛點：「故障雪崩」與「組織擴展瓶頸」。當支付服務發生異常時，商品瀏覽與搜尋服務依然正常運作，故障被嚴格鎖在單一容器邊界內；同時，數十個團隊每天可以各自獨立部署上線，互不卡關。 然而，微服務絕非銀彈：原本奈秒級的記憶體呼叫變成了可能失敗的網路呼叫，原本簡單的資料庫 ACID 交易變成了複雜的 Saga 最終一致性，更需要強大的 DevOps 團隊維運 Kubernetes 與分散式監控。 總結這張投影片，請記住這個核心觀念：微服務架構以承擔分散式網路與維運複雜度為代價，換取大型團隊極致的部署自治與故障隔離。

我們來看第六個模式：微服務架構 (Microservices Architecture, MSA) 的視覺拓撲圖。 請從左至右觀察整體雲原生拓撲： 左側所有外部請求統一經過 API Gateway 閘道器，完成路由分發、JWT 權限驗證與速率限制。 中間則是依業務領域拆分的自治微服務叢集：User 會員服務 (Node.js + Postgres)、Order 訂單服務 (Spring Boot + MongoDB) 與 Payment 支付服務 (Python + MySQL)。 請特別注意：每個微服務都擁有自己專屬的 Private DB，嚴禁跨服務直接連資料庫做 SQL JOIN！ 底部則透過 Kafka / RabbitMQ 非同步事件匯流排發布領域事件，實現跨服務解耦協作。 總結這張投影片，請記住這個核心觀念：微服務架構將龐大系統拆解為獨立部署、各自封裝私有資料庫的自治領域服務叢集。

請仔細對比單體架構與微服務架構。 單體就像一棟摩天大樓，所有代碼同住在一個地基資料庫上。呼叫只要奈秒，維運極為簡單。但在十樓漏水，整棟大樓都受影響！ 微服務就像獨立別墅社區，每棟房子有自己的水電系統。一間跳電，社區其他人家依然燈火通明。 但請牢記：別墅社區需要複雜的道路、管線維護。不要為了趕時髦而貿然採用微服務；小型團隊從模組化單體起步通常是更明智的選擇。 總結這張投影片，請記住這個核心觀念：微服務是以維運複雜度換取團隊自治與故障隔離；初期除非組織規模龐大，否則應謹慎採用。

請看這張外送平台六大架構模式對照表，這正是軟體架構「分形與合成」的最佳典範： 第一，在前端 App 層級使用 MVC，確保訂單資料與多重視覺畫面解耦。 第二，在單一服務內部使用 Layered 分層架構，保護商業邏輯不受資料庫技術綁架。 第三，在 AI 智慧派單中心使用 Repository 黑板模式，讓多個最佳化演算法高效共享全城即時路況與訂單池。 第四，在跨網路邊界使用 Client-Server，集中守護資安與金流。 第五，在即時定位串流使用 Pipe-and-Filter，實現高吞吐量的串流清洗與 ETA 計算。 第六，在企業後台巨觀層級使用 Microservices，達成故障隔離與獨立彈性擴展。 這也直接引出我們下一節 5.4 的主題：架構設計不是逛街挑單一模式，而是由需求驅動的多視角合成！ 總結這張投影片，請記住這個核心觀念：優秀的架構師不會死守單一模式，而是根據不同層級與非功能需求靈活組合多種架構模式。

學完了六大經典架構模式後，請思考一個關鍵問題：真實世界的大型系統（例如 UberEats 或 foodpanda 外送平台），是只挑選其中一種模式來建造的嗎？ 請看這張外送平台的複合架構全景圖，答案絕對是否定的！真實系統會在不同「縮放層級」與「子系統領域」中，巧妙組合這六種模式： 在左側系統邊界，採用 Client-Server 連接顧客、商家與外送員三大終端；而放大進到顧客 App 內部，則用 MVC 讓同一份訂單狀態同時驅動地圖畫面與進度列。 在中間雲端後台，巨觀上採用 Microservices 拆分菜單、訂單与支付服務；但放大進到單一 Order Service 內部，則是標準的四層 Layered 分層架構。 在右側即時資料流，採用 Pipe-and-Filter 管線處理每秒十萬筆外送員 GPS 訊號；而在智慧派單中心，則採用 Repository 儲存庫模式，讓路徑規劃、順路併單與動態加價演算法圍繞同一份全城即時地理狀態庫協同運算！ 總結這張投影片，請記住這個核心觀念：真實世界的軟體架構絕非單一模式，而是跨層級、跨子系統的多模式分形組合。

為什麼說架構直接主宰了系統的品質屬性？ 因為非功能品質屬性——效能、安全性、可用性、容錯力——是結構骨架產生的物理特性，根本無法在事後靠貼補丁加上去！ 舉汽車軟體為例：如果把控制煞車的程式碼跟車載娛樂系統放在同一條未隔離的記憶體匯流排上，娛樂系統當機就可能導致煞車失靈！這就是為什麼安全關鍵系統必須有嚴密的實體隔離架構。 總結這張投影片，請記住這個核心觀念：非功能品質屬性是系統結構骨架的直接體現，絕無法在完工後憑空補救。

軟體架構最核心的修煉，就是權衡分析 (Trade-off Analysis)。 卡內基美隆大學軟體工程研究所 (SEI) 提出的 ATAM 架構權衡分析法，協助架構師在動工寫代碼前，用真實壓力情境找出系統的「敏感點」與「權衡點」。 下一頁我們立即以剛剛的「Food Delivery 外送平台」為例，實際演練一次 ATAM 架構權衡分析！ 總結這張投影片，請記住這個核心觀念：ATAM 能在編碼前系統化揪出架構敏感點與品質衝突點，讓技術妥協成為透明的工程決策。

讓我們把 ATAM 放到剛剛的 Food Delivery 外送平台上，看看架構師每天都在面對什麼樣的真實權衡： 第一個決策：外送員的手機 App 應該幾秒回傳一次 GPS？如果設成每 1 秒回傳，顧客看地圖上的小機車移動非常滑順（易用性高），但外送員的手機兩小時就沒電了，伺服器頻寬也暴增！ATAM 找出這個權衡點後，採取「動態自適應頻率」：快到顧客家時每 2 秒傳一次，在餐廳等餐時每 15 秒傳一次。 第二個決策：周五暴雨晚餐尖峰，結帳時如果要同步鎖定「訂單、金流、餐廳、派單」四個資料庫 (2PC)，只要派單慢一點，全站結帳就卡死！ATAM 決策將金流預授權設為同步，而通知餐廳與呼叫外送員改走 Kafka 非同步 Saga 事件，保住尖峰高可用性。 第三個決策：智慧派單的 Repository 中央儲存庫雖然讓配對最快，卻是單點故障 (SPOF) 的高度敏感點；因此透過「依城市分區分片 (Geo-Sharding) + 主從備援」來消除風險。 第四個決策：防盜刷風控若在結帳當下跑大型 AI 模型會拖慢速度，因此拆為「Gateway 15 毫秒快篩 + 事後非同步深度風控」。 總結這張投影片，請記住這個核心觀念：ATAM 幫助我們針對外送平台的真實壓力場景，在互斥的品質屬性之間設計出最精準的折衷機制。

我們進一步拆解 UML 套件圖的語法重點與外送平台的設計巧思。 請看左欄卡片的四個核心符號： 資料夾圖示代表 Package；內部的 `+` 號代表對外公開的 API 或介面，`-` 號則將內部演算法鎖在套件裡，防止外部模組越界耦合。 虛線箭頭代表 `«import»` 相依關係，而且必須嚴格遵守 ADP 無環相依原則。 再看右欄卡片的外送平台設計洞察： 初學者畫套件圖時，常讓 `domain.order` 向下依賴 `infra.persistence`；但在專業架構中，我們把 `+IOrderRepository` 介面放在 `domain.order` 套件內，讓底層的 `infra.persistence` 向上 `«import»` 領域層！ 如此一來，無論未來把資料庫從 PostgreSQL 換成 MySQL，或把金流從 Stripe 換成 LINE Pay，`domain.*` 核心套件一行程式碼都不必重編譯！ 總結這張投影片，請記住這個核心觀念：套件圖能一眼檢驗系統是否落實依賴反轉，確保核心業務邏輯不受底層基礎設施綁架。

當我們選定了架構模式並完成 ATAM 權衡後，該如何用標準的 UML 圖表把「階段一：巨觀架構設計」畫出來？ 在架構設計階段，我們使用兩張互補的巨觀 UML 圖表：第一張是 **UML 套件圖 (Package Diagram)**（描繪編譯期原始碼模組切分與相依規則），第二張是 **UML 部屬圖 (Deployment Diagram)**（描繪執行期雲端硬體與容器拓撲）。 我們先看第一張巨觀架構圖：UML 套件圖 (Package Diagram)，並以 Food Delivery 外送平台為例。 請先看左側面板的標準 UML 符號： 第一，Package 符號畫成一個帶有左上角標籤的資料夾 (Tabbed Folder)，用來將高內聚的類別與介面收納在同一個命名空間內。 第二，可見度符號 (Visibility)：加號 `+` 代表公開匯出給外部套件呼叫的元素（如 `+OrderService`、`+IOrderRepo`）；減號 `-` 代表封閉在套件內部的私有實作細節（如 `-OrderValidator`）。 第三，虛線開放箭頭 (`- - ->`) 搭配 `«import»` 或 `«access»`，代表編譯期相依：當被指向的供應端套件修改時，來源端套件就可能被迫重新編譯。 第四，架構治理的黃金鐵律——無環相依原則 (ADP)：套件之間的相依圖絕對不能出現循環 (`A → B → A`)！ 再看右側面板的外送平台實例：無論是頂層的 UI 展示套件 (`ui.customer_app`, `ui.rider_app`)，還是底層的基礎設施套件 (`infra.persistence`, `infra.messaging_geo`, `infra.payment_sdk`)，所有的相依箭頭全部朝向中間的核心領域套件 (`domain.order`, `domain.dispatch`, `domain.payment`)！ 總結這張投影片，請記住這個核心觀念：UML 套件圖負責規範編譯期命名空間邊界，並強制所有外部套件向核心領域單向相依。

現在我們進行 4 分鐘的同儕討論與動手塑模練習！ 假設你的團隊正在開發一款「西洋棋遊戲 (Chess Game)」，並決定採用我們在 5.3 節學過的 **MVC (Model-View-Controller)** 架構模式。 請與鄰座同學合作，打開 PlantText.com，用 PlantUML 語法畫出它的 **UML 套件圖 (Package Diagram)**： 第一，定義三個套件：`chess.model`、`chess.view` 與 `chess.controller`，並在套件內標示公開類別（`+Board`、`+MoveValidator`）與私有內部引擎（`-BitboardEngine`）。 第二，畫出套件之間的虛線相依箭頭 `..> : «import»`。 請特別與夥伴討論檢查：哪一個套件應該「完全沒有向外射出的相依箭頭」，好讓它能在沒有視窗介面的情況下獨立跑單元測試？（答案是 `chess.model`！）此外，你要如何設計 `chess.view` 與 `chess.controller` 的關係，才不會違反「無環相依原則 (ADP)」產生循環依賴？ 總結這張投影片，請記住這個核心觀念：透過 PlantUML 繪製 MVC 套件圖，能確保核心棋規模型 (Model) 與視覺介面 (View) 徹底解耦並符合無環相依原則。

我們來統整 UML 部屬圖的語法精髓與實務價值。 請看左欄卡片的三個核心元素： 第一，3D 立體方塊代表 Node（`«device»` 硬體主機或 `«executionEnvironment»` 容器環境）。 第二，`«artifact»` 文件方塊代表實際編譯出來的 `.jar`、`.apk` 或 `.sql` 檔案。 第三，實線通訊路徑標明了兩台機器之間到底走什麼網路協定與開幾台實例。 再看右欄卡片的外送平台洞察： 這張部屬圖呈現了原始碼階段完全看不到的維運關鍵——我們一眼就能檢查：派單服務有沒有設定 `[5..20]` 自動擴縮？PostgreSQL 有沒有設 Read Replica 防止單點故障？Redis 有沒有分片？連往外部 Stripe 金流有沒有走 mTLS 加密？ 總結這張投影片，請記住這個核心觀念：部屬圖讓負載擴縮、叢集備援與網路安全邊界一目了然，是架構師與 DevOps 團隊溝通的共同語言。

套件圖管的是編譯期原始碼資料夾，那如果要呈現主從式架構與微服務在 AWS 雲端上的執行期硬體拓撲，該畫哪張圖？答案就是 **UML 部屬圖 (Deployment Diagram)**！ 請先看左側面板的標準 UML 部屬圖符號： 第一，節點 (Node) 一律畫成「3D 立體方塊」，分為兩類刻板印象：`«device»` 代表實體運算硬體（如智慧型手機、AWS EC2 主機、硬體負載平衡器）；`«executionEnvironment»` 則代表巢狀執行環境（如 Kubernetes Pod、Docker 容器、JVM 或資料庫引擎）。 第二，部屬產物 (`«artifact»`) 畫成帶有摺角文件圖示的方框，代表真正被複製並安裝到節點上的實體二進位檔案（例如 `order-service.jar`、`customer.ipa` 或 `orders_schema.sql`）。 第三，節點之間的實線稱為「通訊路徑 (Communication Path)」，必須標註網路傳輸協定（如 `«HTTPS»`、`«gRPC»`、`«TCP/RESP»`、`«JDBC/TLS»`）以及節點數量基數 (`[3..12]`)。 再看右側面板的外送平台實體雲端拓撲：顧客與外送員的手機節點透過 HTTPS 與 WSS 長連線連入跨可用區的 AWS API Gateway，再以 gRPC 轉發至 AWS EKS 叢集中的三個自動擴縮 Pod 群（Order `[3..12]`、Dispatch `[5..20]`、Payment `[2..6]`），底層則連接一主二從的 RDS PostgreSQL、6 分片的 Redis ElastiCache 以及 3 節點的 Kafka 叢集！ 總結這張投影片，請記住這個核心觀念：UML 部屬圖將軟體二進位產物映射至 3D 硬體節點、容器叢集與網路協定上。

讓我們檢驗一下對架構模式的理解。 題目問：微服務能提供卓越故障隔離能力的核心結構原因是什麼？ 分析選項： 選項 A，共用資料庫是微服務的大忌，會造成資料嚴重耦合！ 選項 C，微服務會增加網路傳輸延遲，不可能消除。 選項 D，微服務需要更多的維運與開發人力。 正確答案是 B！每個服務執行在獨立的 Process 與私有資料庫內，單一服務當機不會直接把其他服務拖下水。 總結這張投影片，請記住這個核心觀念：行程與資料庫的實體隔離，是微服務杜絕區域故障演變成全域崩潰的關鍵防線。

我們進一步剖析左欄的「契約式設計權利義務對稱」與右欄的「工業級 API 規格標準」。 請看左欄卡片：在商業合約中，有義務就有權利。 對呼叫端 (Client) 而言，遵守前置條件是義務，獲得後置條件的正確結果就是受保障的權利； 對供應端 (Supplier) 而言，達成後置條件與維持不變量是義務，而不必浪費程式碼處理違法輸入則是它的權利！ 再看右欄卡片：在現代軟體工程中，我們如何把這些契約寫進軟體設計文件 (SDD)？ 對外 REST API 使用 **OpenAPI 3.1**；內部微服務通訊使用 **gRPC Protocol Buffers (`.proto`)**；Kafka 非同步事件則使用 **AsyncAPI 與 Avro**——並且務必在付款與結帳合約中設計 `idempotency_key`（冪等鍵），確保顧客在網路斷線重按結帳時絕對不會被扣兩次錢！ 總結這張投影片，請記住這個核心觀念：結合 DbC 邏輯規則與 OpenAPI/Protobuf 規格，能消除跨團隊溝通歧義並實現契約驅動的平行開發。

請看這張「階段二：正式介面規格與契約式設計 (DbC)」的全景架構圖，我們以 Food Delivery 外送平台的結帳介面 (`IOrderCheckoutAPI.placeOrder`) 為例！ 請先看上半部：為什麼光寫一行方法簽章 `placeOrder(cart, token)` 不足以作為設計規格？因為它只規定了參數型別，完全沒規定行為義務與邊界條件！ 圖靈獎級大師 Bertrand Meyer 提出的 **契約式設計 (Design by Contract, DbC)**，將每個公開 API 轉化為 **呼叫端 (Client)** 與 **供應端 (Supplier)** 之間具有約束力的三要素法律合約： 1. **前置條件 (`Precondition / require`)**：呼叫端在呼叫方法**之前**必須滿足的義務——購物車不可為空 (`!cart.isEmpty()`)、付款憑證有效 (`token.isValid()`) 且餐廳營業中。 2. **後置條件 (`Postcondition / ensure`)**：供應端在方法執行**完成後**保證兌現的結果——訂單狀態為 `CONFIRMED`、庫存精準扣除 `qty`，並發出 `OrderPlacedEvent`。 3. **類別不變量 (`Class Invariant / invariant`)**：在任何公開方法呼叫**前後皆必須恆為真**的領域約束——訂單總金額永遠 `>= 0` 且外送員同時接單數 `<= 3`。 再看下半部：DbC 消除了各模組重複寫 `if (x != null)` 的防禦性檢查地獄，並且直接對應後續的 **UML 組件圖（棒棒糖與插座）** 以及 5.5 節的 **里氏替換原則 (LSP)**！ 總結這張投影片，請記住這個核心觀念：契約式設計（前置條件、後置條件、不變量）將靜態的方法簽章昇華為可驗證的工程行為合約。

定義好契約式設計 (DbC) 後，我們該如何用標準 UML 圖表把「階段二：組件邊界與介面合約」視覺化畫出來？答案正是 **UML 組件圖 (Component Diagram)**！ 請先看左側面板的 UML 2.x 標準組件圖符號： 第一，組件 (`«component»`) 畫成方框，並在右上角附帶一個「左側突出兩小格」的經典組件圖示。它代表一個可獨立替換、內部狀態完全封裝的軟體單元。 第二，提供介面 (Provided Interface) 畫成一根「棒棒糖 / 圓球 (Lollipop `—○`)」——這正是供應端對外公開的 DbC 合約（承諾兌現 Postcondition）。 第三，需求介面 (Required Interface) 畫成一個「半圓形插座 (Socket `—( `)」——這正是呼叫端對外部合約的依賴（承諾遵守 Precondition）。 第四，當需求端的「插座」扣上供應端的「棒棒糖」，就形成「組裝連接器 (Assembly Connector `—(○—`，俗稱 Ball-and-Socket 球窩接頭)」，搭配邊界上的方形「連接埠 (Port `□`)」轉發內部請求！ 再看右側面板的外送平台組件圖：`Order Management` 複合組件透過左側 Port 對 `API Gateway` 提供 `IOrderCheckoutAPI` 棒棒糖；同時在下方伸出三個插座，分別接合 `Payment Component` 的 `IPaymentGateway`、`Rider Dispatch Engine` 的 `IDispatchMatcher` 與事件匯流排的 `IEventBus`！ 總結這張投影片，請記住這個核心觀念：UML 組件圖透過棒棒糖（提供介面）與插座（需求介面）精準定義隨插即用的契約式架構。

在進入個別 UML 圖之前，我們先釐清一個關鍵觀念：什麼是設計模式 (Design Pattern)？它跟 SOLID 又有什麼關係？ 在 5.3 節我們學的是「架構模式 (Architectural Patterns)」，像是微服務、分層架構等系統級藍圖。當我們把鏡頭拉近到單一組件內部，思考十幾個類別與介面該怎麼組合時，就進入了「物件導向設計模式 (Design Patterns)」的領域。 軟體工程史上最著名的設計模式聖經，是 1994 年由 Gamma、Helm、Johnson 與 Vlissides 四位大師（合稱 Gang of Four, GoF 四人幫）所整理的 23 種經典設計模式，分為三大類：生成型（如 Factory 工廠、Builder 生成器）、結構型（如 Adapter 轉接器、Facade 外觀）以及行為型（如 Strategy 策略、Observer 觀察者）。 既然設計模式這麼多，為什麼我們在這裡專門聚焦於 SOLID？因為 SOLID 是所有 GoF 設計模式背後的「物理定律（第一性原理）」！只要你真正看懂了 SOLID 在 UML 上的結構精神，未來學習任何 GoF 設計模式都會水到渠成。 總結這張投影片，請記住這個核心觀念：GoF 定義了 23 種具體的物件導向設計套路，而 SOLID 則是支撐所有設計模式得以成立的底層核心法則。

請從 UML 圖表結構的角度來審視 SOLID 五大原則。 你會發現，SOLID 絕不是死背語法口訣，它其實是在教你「怎麼畫出乾淨的 UML 方框與箭頭」： SRP 決定一個類別方框裡面該裝什麼、不該裝什麼； OCP 教你如何用介面實作箭頭 (`- - -|>`) 取代脆弱的直接相依； LSP 檢驗你的繼承箭頭 (`───|>`) 是否違反了父類別的行為契約； ISP 規範介面方框的顆粒度，禁止出現肥大介面； 而 DIP 則將跨套件的相依箭頭徹底由下往上反轉！ 接下來，我們逐一以「一頁全幅 UML 對照圖 ＋ 一頁結構解析」深入探討這五個原則。 總結這張投影片，請記住這個核心觀念：SOLID 五大原則在 UML 圖上直接體現為類別內聚度、介面顆粒度與相依箭頭方向的精準治理。

我們來歸納單一職責原則 (SRP) 的結構精髓。 Uncle Bob 後來在《Clean Architecture》書中特別澄清：「一個改變的理由」指的就是「一個特定的利益關係人或部門 (Actor)」。 請看左欄卡片：當財務部、行銷部與 DBA 三個部門的需求都指向同一個 `OrderInvoiceReport` 類別時，任何一邊改需求都會波及另外兩邊。 再看右欄卡片：重構後的 UML 將計算、渲染與持久化拆成三個獨立類別，共用純資料物件 `OrderInvoice`。現在行銷部怎麼改 HTML 樣式，都絕對不會影響到財務計稅與資料庫寫入！ 總結這張投影片，請記住這個核心觀念：將 UML 類別邊界對齊組織中的利益關係人，確保每個類別只擁有一條獨立的變更軸線。

請看第一個原則：單一職責原則 (SRP) 的 UML 前後對照圖。 請先看左側面板（紅色違反 SRP 的設計）： `OrderInvoiceReport` 是一個典型的「上帝類別 (God Class)」。注意左邊有三個截然不同的利益關係人（Actors）同時將相依箭頭指向它： 第一，財務長與會計部門（要求修改稅率與尖峰加成公式 `calculateTaxAndSurge`）； 第二，UX 與行銷團隊（要求修改 HTML/PDF 電子發票排版 `renderHtmlInvoice`）； 第三，DBA 資料庫團隊（要求修改 PostgreSQL 寫入語法 `saveToPostgresDb`）。 再看右側面板（綠色遵循 SRP 的重構設計）： 我們保留純粹的資料模型 `OrderInvoice`，並將三大正交職責拆分為三個獨立且高內聚的類別：`InvoiceTaxCalculator`（只對財務部負責）、`InvoiceHtmlRenderer`（只對 UX 團隊負責）與 `InvoiceSqlRepository`（只對 DBA 負責）！ 總結這張投影片，請記住這個核心觀念：SRP 要求將多重角色的「上帝類別」拆解為各司其職的獨立類別，使每個類別僅對單一角色負責。

我們來剖析開放封閉原則 (OCP) 在 UML 圖上的關鍵差異。 請看左欄卡片：只要你的高階服務類別直接把實線相依箭頭 (`───>`) 射向具體的實作類別，每增加一種新變化，你就必須打開高階類別動手術。 再看右欄卡片：我們在中間放入一個 `«interface» INotificationChannel` 作為防火牆。高階服務只指向這個介面；底下無論要擴充多少種通知管道，全都是畫虛線空心三角箭頭 (`- - -|>`) 指向介面！ 這就是策略模式 (Strategy Pattern) 與外掛架構的靈魂：核心引擎永久鎖定不必修改，新功能像插卡一樣無限擴充。 總結這張投影片，請記住這個核心觀念：善用 UML 抽象介面作為多型樞紐，即可同時達成核心邏輯「對修改封閉」與外圍能力「對擴充開放」。

接著請看第二個原則：開放封閉原則 (OCP) 的 UML 前後對照圖。 請先看左側面板（紅色違反 OCP 的設計）： `OrderNotificationService` 直接用實線箭頭硬編碼相依於具體的 `EmailSender` 與 `SmsSender`，並在內部靠 `if / else if` 分支判斷。當業務決定新增臺灣消費者最常用的 `LineNotifySender` 時，工程師被迫拿手術刀剖開已經在線上穩定運行的 `OrderNotificationService`，新增第三條相依箭頭並修改 `if/else` 邏輯！ 再看右側面板（綠色遵循 OCP 的重構設計）： 我們在中間引入了一個穩定的抽象介面樞紐 `«interface» INotificationChannel`。 `OrderNotificationService` 只相依於這個介面（因此對修改封閉 🔒）；而 `EmailChannel`、`SmsChannel` 與新加入的 `LineNotifyChannel` 則透過虛線空心三角箭頭 (`- - -|>`) 實作該介面（對擴充開放 🔓）！新增 LINE 通知時，核心服務類別一行程式碼都不必改！ 總結這張投影片，請記住這個核心觀念：OCP 透過抽象介面樞紐隔離變更，讓系統能以新增實作類別 (`- - -|>`) 的方式擴充功能，而不必修改既有核心類別。

我們來總結里氏替換原則 (LSP) 的工程守則。 許多初學者學 UML 時被教導：「繼承 (`───|>`) 就是日常生活中的 IS-A（是一個）」。Barbara Liskov 提醒我們：日常語言的 IS-A 不代表軟體行為上的可替換性！ 請看左欄卡片：無論是 `Square 繼承 Rectangle` 偷偷改動寬度，還是外送平台裡讓 `CashOnDelivery（貨到付款）` 繼承 `OnlinePayment` 並在自動退刷時拋出 `UnsupportedOperationException`，都會讓依賴父類別的呼叫端在執行期當機！ 再看右欄卡片：只有當子類別 100% 履行父型態承諾的前置條件、後置條件與不變量（Invariants）時，才能畫繼承或實作箭頭。 總結這張投影片，請記住這個核心觀念：在 UML 中繪製繼承或實作箭頭前，務必檢驗子型態是否完全符合行為可替換性，而非僅憑字面語意。

現在我們來看第三個原則：由圖靈獎得主 Barbara Liskov 提出的里氏替換原則 (LSP) UML 對照圖。 請先看左側面板（紅色違反 LSP 的經典「正方形繼承長方形」陷阱）： 在國中數學裡，正方形是一種長方形，所以初學者很自然地在 UML 圖上畫了一條實線空心三角繼承箭頭 (`───|>`)，讓 `Square` 繼承 `Rectangle`。 然而，`Rectangle` 提供了可變狀態的 `setWidth(w)` 與 `setHeight(h)`，其隱含的契約後置條件是：「修改高度時，寬度保持不變」。為了維持四邊等長，`Square` 覆寫了 `setHeight(10)`，偷偷把 `width` 也改成 `10`！結果當用戶端 `MapZoneTester` 把 `Square` 當作 `Rectangle` 傳入並執行 `寬 5 × 高 10` 時，面積竟然算出 `100` 而不是 `50`，直接導致系統契約崩潰！ 再看右側面板（綠色遵循 LSP 的重構設計）： 我們拔除錯誤的父子繼承關係，改提取純粹的行為介面 `«interface» IShape` (`+ getArea(): int`)，並讓不可變 (Immutable) 的 `Rectangle` 與 `Square` 以平輩兄弟關係分別實作 (`- - -|>`) `IShape`。現在任何子型態替換進 `MapZoneTester`，都 100% 遵守契約、毫無副作用！ 總結這張投影片，請記住這個核心觀念：LSP 要求 UML 繼承與實作關係必須嚴格履踐基礎型態的行為契約，絕不能因覆寫而產生破壞預期的副作用。

請注意介面隔離原則 (ISP) 與前面 SRP、LSP 的巧妙呼應！ 請看左欄卡片：如果說 SRP 禁止出現肥大的「上帝類別」，那麼 ISP 就是禁止出現肥大的「上帝介面」！一旦介面太肥大 (`IMultiFunctionDevice`)，簡單的設備 (`KitchenThermalPrinter`) 就被迫寫出拋出異常的假方法（同時違反了 LSP），而且只要傳真模組改參數，廚房出單機就跟著陪葬重編譯。 再看右欄卡片：將 UML 介面拆解為小巧專一的 `IPrintable`、`IScannable` 與 `IFaxable` 後，每個設備與呼叫端都只綁定自己真正需要的最小合約。 總結這張投影片，請記住這個核心觀念：寧可設計多個高內聚的小型角色介面，也絕不打造強迫客戶端買單無用方法的肥大介面。

接著請看第四個原則：介面隔離原則 (ISP) 的 UML 前後對照圖。 請先看左側面板（紅色違反 ISP 的「肥大介面 Fat Interface」反模式）： 系統定義了一個包山包海的 `«interface» IMultiFunctionDevice`，裡面塞滿了列印訂單 (`printOrderTicket`)、掃描發票 (`scanInvoicePdf`) 與傳真給供應商 (`sendVendorFax`) 三個方法。 雖然企業辦公室的複合事務機 (`CorporateOfficeMFP`) 三個功能都有，但請看外送平台合作餐廳廚房裡的熱感應出單機 (`KitchenThermalPrinter`)：它只能印出單！卻因為實作了這個肥大介面，被迫為掃描和傳真寫出拋出錯誤的空殼方法！ 再看右側面板（綠色遵循 ISP 的重構設計）： 我們將肥大介面精確拆解為三個專一的角色介面 (Role Interfaces)：`IPrintable`、`IScannable` 與 `IFaxable`。現在廚房熱感應出單機只需要乾淨地實作 (`- - -|>`) `IPrintable` 即可，完全不受掃描與傳真功能的污染！ 總結這張投影片，請記住這個核心觀念：ISP 主張將臃腫的肥大介面拆解為精巧的角色介面，確保實作類別與客戶端絕不依賴其不需要的方法。

請將這張相依反轉原則 (DIP) 的 UML 圖，與我們在 5.4 節學過的外送平台套件圖與組件圖連結起來！ 在左欄卡片中，傳統結構化設計的相依箭頭是一路向下的：高階業務依賴低階資料庫。這導致底層資料庫一換，高階業務就壞；而且沒有真實資料庫就無法跑單元測試。 在右欄卡片中，DIP 施展了一個關鍵魔法：把 `IOrderRepository` 介面放在高階的 `domain.order` 套件裡，強迫底層的 `infra.persistence` 實作類別把 `- - -|>` 箭頭**由下往上畫**！ 透過建構子依賴注入 (Dependency Injection)，我們在生產環境傳入 PostgreSQL，在測試環境傳入記憶體內的 `InMemoryMockRepo`，一秒鐘就能跑完上千個領域邏輯測試！ 總結這張投影片，請記住這個核心觀念：將跨套件邊界的 UML 相依箭頭向上反轉，能徹底保護核心業務邏輯不受基礎設施更迭影響，並賦予系統極致的可測試性。

最後，請看第五個原則——也是整潔架構 (Clean Architecture) 的核心基石：相依反轉原則 (DIP) 的 UML 對照圖！ 請特別觀察跨越水平套件邊界（`domain.order` 與 `infra.*`）的那根 UML 箭頭方向： 在左側面板（紅色違反 DIP 的設計）中，高階領域層的 `OrderCheckoutService` 直接建立並向下相依 (`───>`) 於低階基礎設施層的 `MySqlOrderDatabase`。這時執行期的控制流與編譯期的原始碼相依箭頭「雙雙朝下」，高階業務邏輯被底層 MySQL 死死綁架！ 再看右側面板（綠色遵循 DIP 的重構設計）： 高階的 `domain.order` 套件自己定義並擁有 `«interface» IOrderRepository` 抽象介面，`OrderCheckoutService` 只依賴同套件內的這個介面。 而在底層的 `infra.persistence` 套件中，`MySqlOrderRepo`、`PostgresOrderRepo` 與測試用的 `InMemoryMockRepo`，全都畫出虛線空心三角箭頭 (`- - -|>`) **由下往上反轉指向領域層的 `IOrderRepository`**！ 總結這張投影片，請記住這個核心觀念：DIP 將跨層的 UML 實作箭頭由下往上反轉，使底層基礎設施細節依賴於高階領域定義的抽象介面。

讓我們檢驗一下對 SOLID 原則的掌握。 題目問：哪一個原則主張新增功能時應當「新增類別」擴充，而非直接修改舊代碼？ 分析選項： 選項 A，SRP，強調單一改變理由。 選項 B，OCP（開放封閉原則），明確主張對擴充開放、對修改封閉！ 選項 C，ISP，強調介面不肥大。 選項 D，LSP，強調子類別替換父類別不破壞契約。 因此，正確答案是 B：開放封閉原則！ 總結這張投影片，請記住這個核心觀念：開放封閉原則透過多型擴充保護生產環境的穩定舊碼，有效防止擴展功能時引入非預期迴歸錯誤。

歡迎來到 5.6 節：軟體設計流程的階段四 —— 資料與持久化設計：ERD 塑模、快取與多模態儲存！ 回顧我們走過的前三個設計階段： 階段一（5.3 節）設計了巨觀架構模式與套件/部屬圖； 階段二（5.4 節）定義了契約式設計 (DbC) 與組件圖； 階段三（5.5 節）設計了組件內部的 GoF 模式、SOLID 原則與類別圖； 現在進入第四階段（5.6 節）：系統的核心業務狀態與高頻即時資料，究竟該如何塑模、正規化、建立索引、快取並持久化到資料庫中？ 在本節中，我們將掌握三層次資料塑模流程、**UML 資料 / ERD 實體關聯圖符號**、第三正規化 (3NF) 與實體索引調校，以及外送平台如何結合 **PostgreSQL (ACID)**、**Redis Geo-Hash (空間快取)** 與 **Apache Kafka (事件日誌)** 建構多模態儲存架構！ 總結這張投影片，請記住這個核心觀念：階段四資料與持久化設計將領域模型轉化為高完整性之 ERD 資料庫綱要、記憶體快取與事件串流。

我們進一步拆解左欄的「三層次資料塑模與 ERD 符號」以及右欄的「正規化與實體索引調校」。 請看左欄卡片：在繪製資料庫 ERD 時，有三個必備符號： `«PK»` 代表主鍵，`«FK»` 代表外來鍵。特別注意關聯線上的菱形符號：`Customer 1 ── 0..* Order` 是一般關聯；而 `Order 1 ◆── 1..* OrderItem` 則是實心菱形「組合 (Composition)」——代表訂單明細完全隸屬於該張訂單，訂單刪除時明細也隨之銷毀。 再看右欄卡片：資料庫設計永遠在平衡「寫入正確性」與「讀取速度」： 為了確保寫入正確，我們在邏輯層採用 **第三正規化 (3NF)**，避免餐廳改電話號碼時要更新五十萬筆歷史訂單； 為了確保讀取飛快，我們在實體層加上 `(customer_id, created_at)` 複合索引與按月表分區，讓數億筆訂單依然保持毫秒級查詢！ 總結這張投影片，請記住這個核心觀念：邏輯層的 3NF 正規化守護寫入資料完整性，而實體層的複合索引與分區則保障高併發讀取的低延遲。

接著我們看階段四資料設計在分散式架構下的兩大關鍵議題：多模態持久化與跨庫一致性。 請看左欄卡片：在外送平台中，我們讓三種儲存引擎各司其職： 第一，金流與訂單用 **PostgreSQL**，並在資料表加上 `«UQ» idempotency_key` 唯一索引守住最後一道防重複扣款防線； 第二，熱門菜單用 **Redis Cache-Aside** 擋下 95% 的讀取流量，外送員即時 GPS 用 **Redis GeoHash + 30 秒 TTL** 避開 SQL 鎖表瓶頸； 第三，跨服務狀態變更用 **Kafka** 串流日誌，並以 `order_id` 作為分區鍵確保事件順序不亂跳。 再看右欄卡片：當一筆訂單同時涉及 PostgreSQL 與 Kafka 時，如何避免「資料庫寫成功、Kafka 卻發送失敗」的雙寫不一致？ 答案就是業界標準的 **Transactional Outbox 模式**：利用 PostgreSQL 本地 ACID 交易同時寫入 `orders` 與 `outbox_events` 兩張表，再由背景程序轉發到 Kafka，優雅兼顧高吞吐量與資料零遺失！ 總結這張投影片，請記住這個核心觀念：多模態持久化結合了 SQL 的 ACID 嚴謹性、Redis 的極速快取與 Kafka 的串流解耦，並透過 Transactional Outbox 確保最終一致性。

請看這張「階段四：資料與持久化設計」的全景架構圖，完整呈現了資料塑模三層次與外送平台的多模態儲存設計！ 請先看左側面板：資料設計由抽象到具體分為三個層次： 1. **Level 1 概念資料模型 (Conceptual Data Model)**：與資料庫技術無關，專注於梳理核心業務實體與基數關係（如 `Customer 1 ── 0..* Order 1 ── 1..* Item`）。 2. **Level 2 邏輯 ERD 模型 (Logical ERD Model)**：明確定義欄位型別、主鍵 (`«PK»`)、外來鍵 (`«FK»`)，並執行第三正規化 (3NF) 以消除資料更新異常。 3. **Level 3 實體資料綱要 (Physical Data Schema)**：撰寫具體的 SQL DDL、建立複合索引 (`«idx»`)、按月資料表分區 (Partitioning)、設定 Redis 快取過期時間 (`TTL`) 與 Kafka 分區鍵。 再看右側面板：外送平台能不能只用單一資料庫打天下？絕對不行！現代架構採用 **多模態持久化 (Polyglot Persistence)**： A. **PostgreSQL 關聯式資料庫 (ACID)**：儲存 `customers`、`restaurants`、`orders`、`order_items` 與 `payments`，利用 3NF 與嚴格 ACID 交易確保金流與訂單絕對不掉單、不重複扣款。 B. **Redis 記憶體空間資料庫 (In-Memory Spatial Store)**：面對 5 萬名外送員每 5 秒回傳一次 GPS（每秒 1 萬次寫入），使用 64-bit `GeoHash` 搭配 `TTL = 30 秒` 自動過期，在 5 毫秒內秒級找出最近外送員！ C. **Apache Kafka 不可變事件日誌 (Event Log)**：透過 Transactional Outbox 發布訂單事件，非同步同步派單與分析系統。 總結這張投影片，請記住這個核心觀念：資料設計結合三層次 ERD 綱要塑模與多模態持久化，針對不同讀寫特性匹配最適合的儲存引擎。

讓我們檢驗一下對階段四「資料與持久化設計」與「多模態持久化 (Polyglot Persistence)」的理解。 題目問：為什麼外送平台把訂單與金流存在 PostgreSQL，卻把 5 萬名外送員的即時 GPS 座標存在 Redis？ 分析選項： 選項 A 說反了：PostgreSQL 才是支援主鍵、外來鍵與第三正規化 (3NF) 的關聯式資料庫。 選項 B 說反了：PostgreSQL 負責持久化保存歷史帳務，而 Redis 則透過 30 秒 TTL 自動淘汰過期的即時座標。 選項 C 完全正確：PostgreSQL 提供嚴格的 ACID 交易保證，確保金流絕不漏單或重複扣款；而記憶體內的 Redis GeoHash 則能輕鬆吞吐每秒上萬筆座標寫入，並在 5 毫秒內完成方圓 3 公里最近司機的空間搜尋！ 選項 D 不合理：後端資料庫選型不可能消除手機端的物理無線網路延遲。 因此，正確答案是 C！ 總結這張投影片，請記住這個核心觀念：多模態持久化依工作負載特性選用最適儲存引擎——以 ACID 關聯式資料庫守護金流正確性，以記憶體空間索引支撐高頻即時座標查詢。
