在動態測試中，如果你的測試資料剛好把目標元素放在索引值 2，測試就會亮綠燈通過，讓漏掉索引值 `0` 的錯誤繼續潛伏在水面之下。但在靜態審查中，有經驗的同儕或靜態分析器一眼就能抓出 `i = 1`。此外，IEEE 1028 嚴格區分了正式檢視（由協調者主持、獨立導讀者換句話說轉述邏輯）與非正式走查（由作者本人主導）。 難字與專業術語解說： - author blindness: 作者盲點／當局者迷（作者因大腦預設自身邏輯正確，自讀文件或程式碼時極難察覺自身筆誤或思維漏洞的現象） - collective code ownership: 程式碼集體共有制（透過同儕審查讓團隊多數成員皆理解系統各模組邏輯，避免知識孤島）

Michael Fagan (IBM, 1976) 將軟體檢視制度化為六個嚴謹步驟與五個專業角色。在步驟 4（檢視會議）中，由獨立的導讀者 (Reader)——絕非作者本人——大聲轉述產出物的邏輯，而協調者 (Moderator) 則嚴格執行一條鐵律：會議中專注於發現並記錄缺陷（將最佳檢視速率控制在每小時 200–400 行程式碼），絕不在會議上浪費時間爭辯如何修改（修改屬於步驟 5 重做 Rework 的工作）。 難字與專業術語解說： - Fagan Inspection: 范根檢視法（具備六大標準步驟與五大明確角色分工的正式軟體靜態檢視典範） - optimal inspection rate: 最佳檢視速率（實證研究顯示每小時審查 200–400 行程式碼的抓錯率最高，超過 1,000 行會陷入走馬看花的橡皮圖章效應）

靜態審查適用於整個軟體開發生命週期 (SDLC) 的每一項產出物——絕不僅限於原始碼！ 1. **需求與 SRS 規格文件：** 我們檢視正確性、無歧義性（剔除模稜兩可詞彙）、完整性、一致性、可驗證性（具可測試之量化門檻）以及雙向追溯性 (RTM)。 2. **架構與設計模型（ADD、UML、DFD、ERD、API 契約）：** 我們稽核模組化品質（高內聚、低耦合）、DFD 資料守恆（無黑洞或奇蹟）、類別圖與 ERD 參照完整性，以及 OpenAPI 契約一致性。 3. **原始碼與測試套件：** 我們檢視資料／邊界／控制流缺陷、資源洩漏、程式碼臭味（重複程式碼、上帝類別、霰彈槍手術）以及 OWASP Top 10 資安弱點。 難字與專業術語解說： - data conservation (DFD black hole / miracle): 資料守恆（在資料流程圖審查中，只有輸入卻無輸出的程序稱為黑洞 Black Hole；無輸入卻憑空產出資料稱為奇蹟 Miracle） - code smell: 程式碼臭味（表面雖能編譯執行，但內部結構腐化、違反設計原則並預示深層維護風險的徵兆）

現代軟體工程將人工同儕審查與強大的自動化靜態分析工具相結合，在不執行程式的情況下自動檢驗 AST 抽象語法樹、位元組碼與相依性圖譜： 1. **AST 與程式碼臭味檢查器 (`PMD`, `Checkstyle`, `ESLint`, `Ruff`)：** 在數毫秒內抓出未使用變數、空的 `catch {}` 區塊、圈複雜度膨脹與編碼風格違規。 2. **位元組碼與資料流除錯器 (`SpotBugs`, `ErrorProne`, `Infer`)：** 追蹤控制流與資料流，精準定位空指標解參照 (Null-Pointer Dereference)、資源未關閉洩漏與並行競爭。 3. **資安 SAST 與 SCA 掃描器 (`SonarQube`, `Semgrep`, `Snyk`, `OWASP Dependency-Check`)：** 偵測 SQLi/XSS 污點傳播路徑與含已知 CVE 漏洞的第三方開源套件。 4. **AI 審查機器人與模型檢查器 (`GitHub Copilot`, `CodeRabbit`, `Spectral`)：** 稽核 SRS／OpenAPI 規格並初步篩檢 PR 差異——在**第一階段 (Stage 1)** 自動過濾掉 80% 的機械性雜訊，讓**第二階段 (Stage 2)** 的人類領域專家能將 100% 心力聚焦於領域商業邏輯與系統架構設計！ 難字與專業術語解說： - Abstract Syntax Tree (AST) static analyzer: 抽象語法樹靜態分析器（將原始碼解析為語法樹結構，透過規則匹配自動偵測壞味道與潛在缺陷的工具，如 PMD） - SAST vs. SCA: 靜態應用程式安全測試 vs. 軟體組成分析（掃描自寫原始碼之安全弱點 vs. 掃描第三方開源套件是否含有已知 CVE 漏洞）

現在我們進入第 7.3 節：黑箱測試——邊界值分析 (Boundary Value Analysis, BVA) 與等價分割法 (Equivalence Partitioning, EP)，整合了 SQA 教材第 5.1、5.3 與 5.4 節的核心精髓。 難字與專業術語解說： - specification-based testing: 規格導向測試（完全依據外部需求規格書與介面契約設計測試案例的黑箱測試方法）

一個看似微不足道的雙整數加法函式 `int add(int a, int b)` 就有 2^64 種輸入組合，以 1 GHz 速度窮舉測試需耗時 584 年。黑箱測試方法論旨在挑選最具代表性的最小子集，以極大化缺陷揭露率。 難字與專業術語解說： - decoupling from implementation: 與實作解耦（黑箱測試僅針對公開 API 契約斷言，因此內部重構演算法時測試程式碼無須修改）

在單一錯誤假設 (Single Fault Assumption) 下，測試 n 個變數的函式時，我們每次僅讓一個變數在邊界點 (`min, min+, max-, max`) 之間變動，同時將其餘 n - 1 個變數錨定在名義中心值 (`norm`)。 難字與專業術語解說： - Single Fault Assumption: 單一錯誤假設（假設系統失效主要由單一變數處於極端值即可觸發，無須多個變數同時取極端值）

切勿在未檢查輸出等價分割涵蓋率的情況下機械式套用 `4n + 1`！將三角形的兩邊固定在 `norm = 100` 會導致每一個測試案例至少有兩邊相等，徹底漏測不等邊三角形 (Scalene triangle)。 難字與專業術語解說： - diversity deficit: 多樣性缺失（因機械式固定名義值 `norm` 導致產生出的測試案例全部落在相同輸出類別、遺漏其他重要業務分支的盲區）

二維平面上的這 49 個點代表雙變數完整的邊界取樣空間。在一般 BVA (4n+1) 下，僅點亮沿著各名義軸交會的 9 個十字基準點（最小基線）。切換至強固 BVA (6n+1) 時，外圍 4 個越界端點 (min-, max+) 會亮起紅燈。最壞情況一般測試 (5^n) 會啟用藍色合法框內的全部 25 個點。最後，最壞情況強固測試 (7^n) 則會點亮完整笛卡爾乘積的全部 49 個點。 難字與專業術語解說： - boundary sampling space: 邊界取樣空間（在多變數輸入域中，由各變數極值、名義值與越界值張成之測試點候選集合） - single fault assumption: 單一錯誤假設（假設系統失效絕大多數僅由單一變數抵達極值所誘發，因而測試時其餘變數固定在名義中心值） - Cartesian product explosion: 笛卡爾乘積爆炸（當捨棄單一錯誤假設時，測試案例數由線性 O(n) 暴增為指數級 O(k^n) 的組合膨脹現象）

請熟記左側的 2x2 BVA 公式表 (`4n+1`, `6n+1`, `5^n`, `7^n`)，並掌握右側的兩個實務 FAQ：使用三點法 Out-On-In (`99, 100, 101`) 捕捉 `<` 與 `<=` 誤用，以及對浮點數邊界採用業務最小刻度 (`± 0.01`)。 難字與專業術語解說： - 3-point boundary value analysis (Out-On-In): 三點邊界分析法（針對每一個邊界同時取邊界內、邊界上與邊界外三點，以百分百攔截開閉區間關係運算子誤用的標準做法）

將 `@ParameterizedTest` 與 `assertAll` 結合使用，能讓你乾淨俐落地執行數十個邊界檢查，徹底免除樣板重複與早期中斷遮蔽問題。 難字與專業術語解說： - grouped assertions (`assertAll`): 群組聚合斷言（JUnit 5 以 Lambda 封裝多個斷言，確保所有斷言皆被執行並一次彙整所有失敗結果的機制）

在進入下一頁的互動式 EP 矩陣之前，我們先建立等價分割法 (Equivalence Partitioning, EP) 的形式化定義與 2x2 分類體系。 首先，等價分割將輸入定義域切分為互斥且完全窮盡的子集，使軟體對同一子集內的每一個數值皆展現相同的處理行為。因此，從一個分割區間中心挑選單一代表值，就足以代表數百萬個冗餘數值。 其次，將「錯誤假設」（弱涵蓋 Weak = 單一錯誤 `max`，強涵蓋 Strong = 多重錯誤笛卡爾乘積）與「無效輸入處理」（一般 Normal = 僅測有效類，強固 Robust = 有效類 + 無效類）交叉組合，即可得出四種標準 EP 策略：弱一般 (Weak Normal)、強一般 (Strong Normal)、弱強固 (Weak Robust，遵循單一無效原則) 與強強固 (Strong Robust)。 難字與專業術語解說： - mutually disjoint and collectively exhaustive: 互斥且完全窮盡（各等價類別之間交集為空集合，且所有類別之聯集完整涵蓋整個輸入定義域） - equal defect-detection hypothesis: 等效抓錯假設（同一等價分割內的任意兩個輸入值，走過相同的條件分支，具備相同的揭露缺陷能力）

等價分割法涵蓋四種維度策略。在弱一般 EP (Weak Normal) 下，只需 3 個綠色測試案例即可涵蓋每一個有效橫列與直行。強一般 EP (Strong Normal) 則擴展至綠色有效區內的全部 6 種組合。弱強固 EP (Weak Robust) 引入了極為關鍵的「單一無效原則」：4 個紅色測試案例各自在搭配有效同儕值的嚴格隔離條件下測試每一個無效分割（共 7 個案例），防止早期例外中斷遮蔽了次要缺陷。強強固 EP (Strong Robust) 則以暴力笛卡爾乘積測試全部 20 個儲存格。 難字與專業術語解說： - Equivalence Partitioning (EP): 等價分割法（將輸入或輸出域切割為若干互斥子集合，使集合內任一輸入值對揭露缺陷具有同等效力的黑箱測試技術） - single invalid rule: 單一無效原則（在強固等價分割中，每次測試僅允許單一變數取無效值，其餘變數一律取有效值，防止例外中斷造成缺陷遮蔽） - fault masking: 缺陷遮蔽（當一個輸入錯誤引發提前崩潰或例外返回時，下游其他變數潛藏的錯誤無法被執行或驗證的現象）

點擊上方互動區「下一步」或輸入任意目標值 k，即可逐步追蹤二元搜尋的折半過程。左下方列出的 4 大結構化分割維度（陣列基數 A、搜尋結果 F、命中位置 C 與輸入合法性 K）完整描繪了輸入與輸出定義域；右下方則透過弱涵蓋策略規劃出 R1..R8 共 8 個代表性測試案例，涵蓋每一個分割區間。 難字與專業術語解說： - interval halving: 區間折半（二分搜尋每次比對中間元素後，依大小關係排除一半候選區間的核心機制，使時間複雜度降至 O(log N)） - array cardinality: 陣列基數／元素個數（依空集合 0、單元素 1 與多元素 * 劃分的等價類）

引導學生逐步探索 NextDate(Y, M, D) 的等價分割。先列出年、月、日三大變數，詢問學生該如何劃分定義域；接著點擊逐步揭示子項目：閏年 vs. 平年、大小月分群，以及最關鍵的發現——由 12/31 跨年邊界所催生出的獨立等價類「12 月 (M4)」！ 難字與專業術語解說： - state transition divergence: 狀態轉移分歧（相同等價類之輸入在特定邊界觸發截然不同的變數更新，如年份進位與月份歸一，證明原劃分未達等價） - domain-driven partitioning: 領域驅動等價分割（依據領域業務規則與日曆曆法物理約束進行的精密黑箱等價類劃分）

這張主控打點矩陣將等價分割涵蓋率極其清晰地視覺化呈現。沿著每一個直行往下檢視：每一個等價類都在前 5 個基底測試案例 (TC1..TC5) 中至少擁有一個打點，證實達成 100% 弱涵蓋。案例 TC6 至 TC8 則是精準耦合補充案例，專門驗證跨變數耦合邊界（例如非 12 月的 31 日換月，以及平年 2 月 28 日換月）。 難字與專業術語解說： - coverage matrix table: 涵蓋矩陣表（以橫列表示測試案例、以直行標示所有等價類別，透過打點視覺化確認各直行皆被測試涵蓋的標準驗證工具） - precision supplements: 精準耦合補充案例（在弱涵蓋基線之上，針對高度耦合之邊界業務規則進行定向補充的高效測試策略）

切勿在同一個測試向量中放入兩個無效值——否則第一個例外檢查就會短路返回，進而遮蔽後續驗證邏輯中的缺陷！ 難字與專業術語解說： - Single Invalid Rule: 單一無效原則（設計無效等價類測試案例時，每筆測資僅能包含一個無效輸入，其餘參數皆須維持有效值，以防錯誤遮蔽）

100% 分支涵蓋度嚴格包含 100% 敘述涵蓋度；然而即便達到 100% 分支涵蓋度，複合 `if` 判斷式內部的個別原子條件仍可能始終卡在單一真假值而從未翻轉。 難字與專業術語解說： - Statement Coverage vs. Branch Coverage: 敘述涵蓋度 vs. 分支涵蓋度（僅要求每行指令執行一次 vs. 要求每個決策判斷的真假分支走向皆被執行）

在 JVM 位元組碼層級，`if (A && B)` 會被拆解為兩道條件跳躍指令（共 4 個位元組碼分支），這完美解釋了為何在補齊 `(A=True, B=False)` 測資之前，JaCoCo 會一直顯示 75% 的黃色菱形警告。 難字與專業術語解說： - short-circuit evaluation: 短路求值（在 `A && B` 中若 `A` 為 False，或在 `A || B` 中若 `A` 為 True，程式直接略過不計算右式 `B` 的求值機制）

透過 `sample-code-01` 的具體推演可以清楚看出，為何**分支／條件複合涵蓋度 (Branch/Condition Coverage, B/CC)** 必須同時強制要求兩項準則皆達 100%。 難字與專業術語解說： - Branch/Condition Coverage (B/CC): 分支與條件複合涵蓋度（同時要求每個原子條件皆經歷 T/F，且每個整體決策分支亦經歷 T/F 的覆蓋標準）

MC/DC 的精髓在於證明：在固定其他所有條件不變的前提下，每一個原子條件皆能「獨立翻轉」最終的決策結果，且理論上最少僅需 `n + 1` 筆測試案例。 難字與專業術語解說： - Modified Condition / Decision Coverage (MC/DC): 修改條件／決策涵蓋度（要求證明每一個原子條件在固定其他條件不變下，皆能獨立翻轉整體決策結果的航太與車規最高白箱標準）

因為第 `#2` 列與第 `#6` 列同時扮演多組配對的共用基準錨點（Anchor Rows），聯集 `{#2, #4, #5, #6}` 總共僅需 `n + 1 = 4` 筆測試案例，即可完成三個條件的獨立性證明。 難字與專業術語解說： - Independence Pair: 獨立影響配對（一對測試案例中，僅目標條件真假值改變、其餘條件固定不變，且整體決策輸出隨之翻轉的配對證據）

請熟記航太 DO-178C DAL A 與車規 ISO 26262 ASIL D 對 100% MC/DC 的強制映射關係，並警惕古德哈特定律下的 100% 覆蓋率三大迷思。 難字與專業術語解說： - Goodhart's Law: 古德哈特定律（當一個度量指標被當作硬性績效考核目標時，工程師便會透過無斷言測試等方式迎合數字，使其失去衡量品質的意義）

觀察 `LoanCalculator` 的三階段演進：階段 1（快樂路徑）、階段 2（黑箱 Pairwise 成對組合）能自動推進至約 90% 分支涵蓋度；接著透過階段 3 檢視 JaCoCo 紅黃標記，發現只差一筆多重優惠疊加觸發 `if (rate < 2.0) rate = 2.0;` 利率下限的測資，補上後即完美達成 100%！ 難字與專業術語解說： - infeasible branch / path: 不可行分支／死路徑（因前後條件矛盾或數學遞移律限制，在任何輸入下皆不可能被觸發的邏輯分支）

變異測試會在你的程式碼中自動植入人為的單點微小錯誤（變異體），藉此檢驗你的 JUnit 斷言是否真的會亮起紅燈並將其「殺死（Kill）」。 難字與專業術語解說： - Competent Programmer Hypothesis (CPH): 稱職程式設計師假設（假設工程師寫出的程式與正確版本在語法樹上僅有些微差距，因此微小變異算子能有效模擬真實缺陷） - Coupling Effect Hypothesis: 耦合效應假設（能殺死所有一階單點微小變異體的敏銳測試集，亦能同時殺死 99% 以上複雜高階複合錯誤的實證定律）

RIPR 模型（可達 Reachability、感染 Infection、傳播 Propagation、揭露 Revealability）清楚解釋了為何 100% 敘述涵蓋度（僅滿足第一階段 Reachability）遠遠不足以殺死變異體；同時也說明了為何在計算 `MS = K / (M - E)` 時，必須將語意完全等價的等價變異體（`E`）從分母中扣除。 難字與專業術語解說： - RIPR Model: RIPR 故障傳播模型（測試案例殺死變異體必經的可達、狀態感染、結果傳播與斷言揭露四階段） - Equivalent Mutant: 等價變異體（語法雖然被修改，但在所有可能輸入下之執行結果皆與原程式完全一致、永遠無法被任何測試殺死的變異體）

請注意這兩個實戰推演的共通規律：所有存活下來的關係運算子變異體（例如將 `>` 變異為 `>=` 的 `P3`、`P1` 與 `P4`），全部都是被<strong>精確邊界值（On-Point Boundary Values）</strong>所殺死（包括 `[2, 2, 1]` 中的 `a[i] == a[r]`、`(10, 1)` 中的 `X == 10`、`(8, 6)` 中的 `X - Y == 2`，以及 `(7, 10)` 中的 `Y == 10`）！這從數學上完美證明了黑箱邊界值分析（BVA）與白箱變異測試之間的深刻內在連結。 難字與專業術語解說： - mutation hunting matrix: 變異體獵殺矩陣（列出各測試案例在原程式與各變異體上之輸出，藉以識別存活變異體並設計補彈測資的分析表）

觀察 `bs02`（`while (left < right)`）與 `bs03`（`while (left >= right)`）： - 為了殺死 `bs02`，二分搜尋必須一路收斂到 `left == right` 的最後一個單元素視窗（例如在 `[0, 1, 2]` 中尋找位於邊界的元素 `2`）。 - 為了殺死 `bs03`，陣列長度必須至少為 2（使初始 `left < right`），如此一來 `left >= right` 就會在第一步直接跳出迴圈並錯誤回傳 `-1`。 難字與專業術語解說： - PITest (PIT Mutation Testing): Java 工業級變異測試框架（直接在記憶體中篡改 JVM 位元組碼並平行執行 JUnit 測試，自動產出變異刪除率報告的工具）

我們現在進入第 7.6 節：整合測試、測試替身（Test Doubles）與 Mockito 實戰（整合 SQA 第 7 章第 7.1 至 7.6 節）。 難字與專業術語解說： - contract mismatch: 介面契約失配（呼叫端模組與被呼叫端模組對於前置條件防呆責任、例外型別或資料格式之假設不一致，導致整合時崩潰的缺陷）

使用 Mock 替身進行的單元測試，只驗證了「你對外部依賴的主觀假設」；唯有真實的整合測試（Integration Testing），才能驗證兩個模組是否真正遵守同一份介面契約！ 難字與專業術語解說： - false green light from mocking: 模擬替身假綠燈（單元測試中因開發者對 Mock 設定了與真實底層實作不符的理想化回傳或例外，導致單元測試通過但真實整合崩潰的陷阱）

當 `Prime` 透過建構子接收 `PrimeChecker` 抽象介面時，完全同一份正式生產程式碼，既能搭配手寫 Stub 進行由上而下測試、也能搭配動態 Mockito Mock 進行隔離單元測試，更能搭配真實 `RealPrimeChecker` 進行由下而上整合測試！ 難字與專業術語解說： - Constructor Dependency Injection (Constructor DI): 建構子依賴注入（不於類別內部自行 `new` 具體底層依賴，而是透過建構子參數由外部傳入抽象介面實作的解耦設計模式）

在由下而上整合測試（Bottom-Up Integration）中，我們先以 JUnit 的 `@Test` 方法作為測試驅動程式（Test Driver）驗證最底層的葉節點模組，接著逐層向上組裝已驗證的真實元件，全程完全不需要撰寫任何 Stub 測試樁！ 難字與專業術語解說： - Bottom-Up Integration: 由下而上整合測試（從最底層無依賴之葉節點模組開始，藉由測試驅動程式 Driver 驗證後逐層往上真實組裝的策略）

在由上而下整合測試（Top-Down Integration）中，我們從最頂層的協調控制模組開始，針對尚未完成的下層模組先以輕量級測試樁（Test Stubs）頂替，再由上往下逐步將測試樁替換為真實實作。 難字與專業術語解說： - Test Stub: 測試樁／存根（在由上而下整合測試中，用以模擬尚未完成之底層被呼叫模組、回傳固定硬編碼結果的極簡替身）

三明治混合整合（Sandwich / Hybrid Integration）是業界最受青睞的折衷方案：底層工具與 DAO 資料存取層採用由下而上搭配 JUnit Drivers 穩固驗證，頂層 UI 與 Controller 採用由上而下搭配輕量 Stubs 提早驗證流程，最後在中間核心業務服務層（Service Layer）會師整合。 難字與專業術語解說： - Sandwich Integration: 三明治整合測試法（結合由上而下與由下而上策略，以中間核心業務層為會師目標同時推進的混合式整合策略）

在 `MarketTest` 中，我們僅對 `StockService`（股價每秒跳動的外部網路 API）進行 Mock 佈樁，而讓 `Stock` 價值物件（Value Object）與 `List.of(...)` 保持 100% 真實運作！ 難字與專業術語解說： - State Verification vs. Behavior Verification: 狀態驗證 vs. 行為驗證（狀態驗證透過 `assertEquals` 檢查方法回傳值或物件最終狀態；行為驗證透過 `verify` 檢查受測系統是否依預期次數與參數呼叫外部協作者）

`mock()` 是一個空殼虛擬代理（任何未設定的方法呼叫皆回傳 `0`、`false` 或 `null`）；而 `spy()` 則包裹了一個真實物件實體，使所有未特別設定的呼叫皆執行真實程式碼，讓我們能精準地只對 `isPrime(7)` 進行局部打補丁（Patching）。 難字與專業術語解說： - Partial Mocking (`spy`): 局部模擬／間諜包裝（以真實物件實體為基底，未特別佈樁的方法皆執行真實程式碼，僅針對特定方法或參數局部覆寫回傳值的機制）

切記：絕不要對價值物件（Value Objects）、標準集合或純領域演算法進行 Mock。測試應該驗證「可觀測的外部行為與邊界互動」，而非綁死內部私有實作細節。 難字與專業術語解說： - Brittle Test (Over-Mocking): 脆化測試／過度模擬反模式（因測試案例過度綁定受測類別內部實作細節與呼叫順序，導致在外部功能完全正確的重構後測試卻大面積損壞的現象）
