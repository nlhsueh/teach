## 什麼是軟體設計？ (What is Software Design?)

* **從需求 (What) 到實作 (How) 的轉化過程：**
  - **需求工程 (Requirements)**：定義利益關係人的痛點與功能期待（*建造什麼*）。
  - **軟體設計 (Software Design)**：構思結構分解、組件邊界、資料模型與通訊協定（*如何建造*）。
* **軟體設計的核心任務：**
  - **建立工程藍圖 (Blueprinting)**：產出架構模型、介面合約與規範，作為工程團隊實作的依據。
  - **進行權衡決策 (Trade-off Decision Making)**：在互斥的非功能需求間取得平衡（如效能 vs. 安全性 vs. 開發成本）。
* **「設計」與「寫程式 (Coding)」的本質區別：**
  - 寫程式是用特定程式語言語法實現演算法邏輯。
  - 設計則是決定**模組如何切割、狀態放在哪裡、組件之間如何解耦**以因應未來的變更。

## 為什麼軟體設計至關重要？ (Why Design Matters?)

* **1. 杜絕「憑感覺寫代碼 (Vibe Coding)」與結構腐敗：**
  - 缺乏設計的程式碼會迅速誘發 Robert C. Martin 指出的「不良設計四大病徵」：
    - **僵直性 (Rigidity)**：改動一處引發數十個檔案骨牌式連鎖修改。
    - **脆弱性 (Fragility)**：修復模組 A 的錯誤，莫名其妙導致毫無關聯的模組 B 崩潰。
    - **不可移植性 (Immobility)**：組件糾纏不清，無法被抽取復用於其他系統。
* **2. 品質屬性是「設計」出來的，不是「測試」出來的：**
  - 可擴展性、容錯力、低延遲與安全性必須從第一天納入架構骨幹，無法靠日後補寫單元測試補救。
* **3. Barry Boehm 缺陷修復成本曲線 (Cost of Change)：**
  - 在**需求與設計階段**修復瑕疵只需 **1 美元**；若拖到**正式上線維護階段**，修復代價飆升高達 **50 到 100 倍**！
* **4. 建立工程團隊的共通語言與平行開發合約：**
  - 清晰的組件切分與介面規範，讓數十名工程師能並行協作而不互相卡關。

## 軟體設計包含什麼？多層次設計光譜 (Design Spectrum)

* **軟體設計是一套由巨觀至微觀的完整工程光譜：**
  - 🏛️ **1. 架構設計 (Architectural Design / 巨觀結構)：**
    - 系統整體骨架、主要子系統切分、分散式通訊機制與全域架構模式（如分層、MVC、微服務）。
  - 🔌 **2. 介面設計 (Interface Design / 合約與邊界)：**
    - 公開 API 規範、通訊協定、組件間互動合約與資訊隱藏邊界（封裝內部細節）。
  - 🧩 **3. 組件與詳細物件導向設計 (Detailed OO Design / 微觀實作)：**
    - 類別內部結構、演算法、資料結構、SOLID 設計原則與 GoF 設計模式。
  - 💾 **4. 資料與資料庫設計 (Data & Persistence Design / 狀態儲存)：**
    - 概念實體模型、關聯式綱要 (ERD)、NoSQL 文件模型、快取策略與資料一致性模型。
* **使用者介面設計 (UI/UX Design)：**
  - 聚焦於人機互動體驗、認知人因與易用性啟發原則——將於**第六章**深入剖析。

## 本章學習路徑：為什麼通用設計原則必須先行？

* **教學編排的根本思維：原則先行 vs. 架構先行**
  - 若一開始就背誦架構模式，模式往往淪為孤立、死記的框線圖。
  - 當你徹底理解**關注點分離**，你便能自然洞悉分層架構 (Layered) 的存在必要；
  - 當你深刻掌握**低耦合度**，你便能透徹理解 MVC 為何堅持將 Model 與 View 隔離；
  - 當你深悟**高凝聚度**，你便能明白微服務 (Microservices) 為何必須嚴格對齊領域邊界。
* **步步為營的完整學習軌跡：**
  - **第一步：通用設計原則 (5.2)**：核心基石、內聚力與耦合度的詳細層次劃分。
  - **第二步：經典架構模式與權衡 (5.3)**：六大架構樣式、單體 vs. 微服務技術對決與 ATAM。
  - **第三步：架構推導與塑模 (5.4)**：超越 Pattern：ASR 驅動、UML 陷阱、4+1 視圖、C4 Model 與 ADR。
  - **第四步：微觀詳細設計 (5.5)**：類別層級的 SOLID 物件導向工程匠藝。
  - **第五步：現代實踐與 AI 賦能 (5.6 & 5.7)**：AI 副駕駛工作流、防範盲點與全景統整。

# **5.2 通用軟體設計核心原則**

> "優良的設計極易修改；拙劣的設計在每一步都抗拒改變。"  
> — *Dave Thomas (The Pragmatic Programmer)*

<!--

總結這張投影片，請記住這個核心觀念：通用設計原則在軟體系統的每一個抽象層次中都如分形般一體適用。

## 通用原則：貫穿全尺度的「分形 (Fractal)」特性

* **軟體設計具有分形特性 (Fractal Nature)：**
  - 同一套核心法則，在不同層級的放大鏡下展現出完全一致的規律：
    - **系統巨觀層級 (System Scale)**：微服務架構將業務領域拆解為獨立解耦、高凝聚的自治服務。
    - **模組套件層級 (Module Scale)**：Package 與函式庫將特定職責封裝於公開 API 邊界之後。
    - **類別微觀層級 (Class Scale)**：單一類別嚴格封裝狀態，只保留單一的改變理由 (SRP)。
* **原則的本質是為了克服人類心智的極限：**
  - 電腦記憶體有幾十 GB，但人類的「工作記憶 (Working Memory)」只有 7 ± 2 個區塊 (Miller's Law)。
  - 設計原則是工程心智工具，旨在確保大型軟體能被人類大腦理解、維護與擴充。

## 經典設計準則：模組化、抽象化與關注點分離

* **1. 抽象化 (Abstraction)：**
  - 將低階實作細節隱藏在清晰高階概念之後，讓工程師能在不被雜訊干擾的狀態下推演系統行為。
* **2. 封裝與資訊隱藏 (Encapsulation & Information Hiding)：**
  - *David Parnas 原則：* 將資料與行為綑綁於模組內部，嚴格隱藏私有變數，防止外部程式產生非法副作用。
* **3. 關注點分離 (Separation of Concerns, SoC)：**
  - 將系統切分為互不重疊的功能面向（例如：UI 呈現邏輯絕不混雜 SQL 查詢語法）。
* **4. 模組化 (Modularity)：**
  - 將大型軟體劃分為高內聚、可獨立測試與替換的積木單元。

封裝與資訊隱藏運用 private 關鍵字守護內部不變性；
關注點分離確保 UI 程式碼絕不拼接 SQL 語句；
模組化讓數十位工程師能夠同時開工而不互相衝突。

總結這張投影片，請記住這個核心觀念：抽象化、封裝、關注點分離與模組化是抵禦代碼複雜度的四大基石。
-->

## 至高黃金法則：高凝聚度與低耦合度

* **凝聚度 (Cohesion)：**
  - 衡量單一類別或模組內部所有責任與成員彼此關聯的緊密程度。
  - **工程目標：** **高凝聚度 (High Cohesion)**（一個模組只專注做好一件事）。
* **耦合度 (Coupling)：**
  - 衡量不同模組之間直接相依與牽扯的強烈程度。
  - **工程目標：** **低耦合度 (Low Coupling)**（模組間透過抽象合約互動，對彼此實作細節完全無知）。
* **軟體工程至高黃金法則：**
  > **「極大化凝聚度，極小化耦合度！」**  
  > 高凝聚確保模組專注好懂；低耦合確保改動不會引發骨牌式連鎖崩潰。

<!--
如果整堂課你只能記住一句話，請記住這八個字：高內聚、低耦合！

耦合度衡量外部牽連度：當我修改 A 類別時，會不會導致十個完全不相關的檔案全部編譯失敗？我們要追求低耦合。

總結這張投影片，請記住這個核心觀念：高凝聚確保內部職責單純聚焦，低耦合杜絕修改引發的致命連鎖反應。

## 凝聚度與耦合度：不良設計 vs. 優良設計對比

```java
// ❌ 劣質設計：低凝聚度 ＋ 高耦合度（臭名昭著的「上帝類別 God Class」）
class OrderManager {
    public void processOrder() {
        // 直接硬編碼寫死 MySQL 資料庫查詢 SQL
        // 計算複雜的 VIP 客戶打折數學公式
        // 手工拼接顧客發票的 HTML 字串
        // 打開底層 TCP/SMTP socket 連線直接發送 Email
    }
}
```

```java
// ✅ 優良設計：高凝聚度 ＋ 低耦合度（職責分明、依賴抽象介面）
class OrderProcessor {
    private final DiscountCalculator discountCalculator;
    private final OrderRepository orderRepository;
    private final NotificationService notificationService;

    public OrderProcessor(DiscountCalculator dc, OrderRepository repo, NotificationService ns) {
        this.discountCalculator = dc;
        this.orderRepository = repo;
        this.notificationService = ns;
    }
    // 透過外部注入的抽象介面，優雅協調整體工作流程！
}
```

在上面的壞設計中，OrderManager 是典型的上帝類別：一個方法裡塞了 SQL、折扣計算、HTML 模板和底層網路通訊！只要郵件伺服器改通訊協定，結帳類別就得跟著改！

在下面的好設計中，OrderProcessor 只有一個高內聚職責：工作流調度。它把算數學交給 DiscountCalculator，把存檔交給 OrderRepository，把發信交給 NotificationService。每個協作者都能被獨立測試與替換！

總結這張投影片，請記住這個核心觀念：將臃腫的單體類別拆解為專注、協同的服務，是實踐高凝聚與低耦合的經典範例。

## 內聚力的層次與類型：從弱到強 (Weak to Strong)

* **內聚力階梯譜系 (Larry Constantine & Edward Yourdon)：**
  - 衡量「單一模組 / 類別內部各元素彼此關聯與聚焦的緊密程度」：

| 層次 | 內聚力類型 | 核心特徵與運作機制 | 實務範例 | 品質評估 |
| :--- | :--- | :--- | :--- | :--- |
| **7** | **功能性內聚 (Functional)** | 模組內部所有元素只為完成單一、明確且具體的運算或業務功能 | `calculateTax()`, `sin(x)` | **最高境界 (最理想)** |
| **6** | **順序性內聚 (Sequential)** | 前一個操作的輸出，直接作為下一個操作的輸入（如生產線） | `readData() → parseJSON() → validate()` | **強烈推薦** |
| **5** | **溝通性內聚 (Communicational)**| 各項操作共用相同的輸入資料，或產出相同的輸出資料 | `updateCustomerAddress()` 兼 `printLabel()` | **可接受** |
| **4** | **過程性內聚 (Procedural)** | 各步驟僅因「特定執行先後順序」而被綁在一起，處理不同資料 | 先 `validateOrder()`，再 `auditLog()` | **普通 (中度)** |
| **3** | **時間性內聚 (Temporal)** | 元素僅因「在同一時間點執行」而被包在一起 | `systemStartup()`, `loadConfigAndConnect()` | **偏弱 (應重構)** |
| **2** | **邏輯性內聚 (Logical)** | 模組包攬同類任務，由傳入的控制 Flag 決定具體執行哪一段分支 | `printReport(int format)` (內部 switch CSV/PDF) | **不良 (違反 OCP)** |
| **1** | **偶然性內聚 (Coincidental)** | 元素之間毫無邏輯關聯，僅是隨機雜湊的大雜燴 | `CommonUtils.java`, `GeneralHelper.java` | **最差 (務必杜絕)** |

<!--
讓我們深入探討 Larry Constantine 與 Edward Yourdon 提出的經典 7 大內聚力層次。

最高境界是「功能性內聚」：模組或類別只專注做好一件純粹而定義清晰的事情。每一行程式碼都為同一個目標效力。

其次是「順序性內聚」，如流水線般由前一步骤直接供應下一步骤。

而在階梯下方則是常見的反模式：時間性內聚將開機要做的事情全部塞進同一個肥大方法；邏輯性內聚用一個 flag 控制多種不同運算；最嚴重的則是偶然性內聚，也就是大家常見的 GeneralUtils 工具包，裡面什麼雜七雜八的函式都往裡塞。

總結這張投影片，請記住這個核心觀念：極力追求功能性與順序性內聚，並主動重構消除時間性、邏輯性與偶然性內聚。
-->

## 耦合度的層次與類型：從緊到鬆 (Tight to Loose)

* **耦合度階梯譜系 (模組之間的相互依賴程度)：**
  - 衡量「模組之間呼叫、資料傳遞與知識共享的牽扯深度」：

| 層次 | 耦合度類型 | 依賴機制與破壞風險 | 實務範例 | 品質評估 |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **內容耦合 (Content)** | 一個模組直接竄改或存取另一個模組的私有內部記憶體或邏輯 | 繞過封裝直接修改他者 private 欄位 | **最差 (極度危險)** |
| **2** | **共用耦合 (Common)** | 多個模組共同讀寫全域變數或全域共用記憶體狀態 | 多執行緒下共用未加保護的全域狀態 flag | **高風險 (難追蹤)** |
| **3** | **控制耦合 (Control)** | 一個模組透過傳遞控制旗標 (Flag) 來支配另一個模組的內部流程 | 呼叫時傳入 `mode = 3` 操控被呼叫者行為 | **中高風險** |
| **4** | **標記耦合 (Stamp)** | 模組傳遞整包複合資料結構，但被呼叫者僅需其中一小部分 | 函式只需 `zipCode`，卻傳入整包 `Customer` | **中度 (可改善)** |
| **5** | **資料耦合 (Data)** | 模組間僅透過簡單、獨立且必要的純參數進行通訊 | `calculateArea(width, height)` | **函式呼叫最佳** |
| **6** | **訊息/事件耦合 (Message)**| 模組間透過非同步訊息/事件通訊，彼此完全不知曉對方存在 | EventBus：發布 `OrderPlacedEvent` | **完全解耦 (最理想)** |

<!--
接著我們來看耦合度的 6 大層次，從最危險的緊密耦合邁向最優質的鬆散解耦。

最糟的稱為「內容耦合」：A 模組直接深入 B 模組的私有實作細節，徹底擊穿封裝。B 模組稍有改動，A 模組直接陣亡。

「共用耦合」則是多個模組共用全域變數，往往引發難以重現的並行競爭與副作用。

「控制耦合」是傳入 flag 決定對方的內部分支，這表示呼叫端對被呼叫端的內部實作細節知曉得太多。

「標記耦合」是傳遞過大的資料物件，造成不必要的資料結構綁定。

「資料耦合」是直接呼叫時的黃金標準：只傳入運算所需的純量參數。

而「訊息/事件解耦」則透過事件匯流排達到時空徹底分離。

總結這張投影片，請記住這個核心觀念：杜絕內容與共用耦合，降低控制耦合，優先採用資料耦合與事件驅動設計。
-->

## 什麼是軟體架構？ (What is Software Architecture?)

* **正式定義 (IEEE 1471 / ISO 42010)：**
  > 軟體架構是系統的根本性組織，體現在其組件、組件彼此與環境之間的相互關係，以及指導其設計與演進的原則中。
* **架構的「橋樑角色 (The Bridge Role)」：**
  - **需求 (What)**：利益關係人的期望、使用者故事與限制條件。
  - **實作 (How)**：具體程式碼、資料表綱要與測試案例。
  - **架構 (橋樑)**：將混亂的人類需求轉化為結構化的子系統、服務邊界與部屬拓撲。
* **微觀架構 vs. 巨觀架構 (In the Small vs. In the Large)：**
  - **微觀架構 (In the Small)**：單一應用程式內部的模組組織與類別劃分。
  - **巨觀架構 (In the Large)**：企業級分散式系統、雲端叢集、事件匯流排與異質資料庫拓撲。

## 什麼是軟體架構模式？ (Architectural Patterns)

* **架構模式的本質：**
  - 架構模式是在給定軟體工程情境下，針對**反覆出現的結構性設計問題，所提出經過實戰檢驗的通用可復用解法**。
  - 設計模式 (Design Patterns) 作用於微觀類別層次；架構模式則決定**整個系統的巨觀宏觀結構拓撲**。
* **架構模式的三大核心要素：**
  - **1. 情境 (Context)**：特定反覆出現的軟體系統開發環境與工程挑戰。
  - **2. 問題與作用力 (Problem & Forces)**：相互抗衡的需求拉扯（如：資料解耦 vs. 即時性延遲）。
  - **3. 解法與代價 (Solution & Consequences)**：組件劃分、通訊約束與必須接受的缺點妥協。
* **為什麼架構模式至關重要：**
  - 為大型工程團隊建立共通詞彙，避免重複犯下歷史上的經典架構錯誤。

## 1. 模型-視圖-控制器模式 (Model-View-Controller, MVC)

<div class="centered-image">
  <img src="../../img/ch05/architecture/pattern_mvc.svg" style="max-height: 290px; width: auto;" alt="MVC Architecture Diagram" />
</div>

* **三大核心組件職責切分：**
  - **Model (模型)**：封裝核心領域商業資料、驗證規則與狀態，對視圖完全無知。
  - **View (視圖)**：負責將資料渲染成視覺介面呈現給使用者；監聽模型狀態變化。
  - **Controller (控制器)**：攔截使用者輸入與 HTTP 請求，轉譯並調度商業邏輯更新 Model。
* **工程優勢與取捨代價：**
  - **優勢**：同一資料模型可支援多種不同視圖（Web、App）；UI 前端與後端工程師可平行開發。
  - **代價**：在簡單介面中引入過多跳轉層級；若 View 直接碰 Model 易引發耦合破壞。

<!--
我們來剖析第一個經典模式：Model-View-Controller (MVC)。

看圖中的三角循環資料流：
Controller 攔截使用者的 HTTP 請求，呼叫領域邏輯更新 Model。
Model 維護著真實的商業資料與狀態。
View 讀取 Model 的資料，將其渲染成 HTML 或 App 介面展示給使用者。

MVC 最強大的地方在於關注點分離：前端工程師可以隨時改版 CSS 排版，完全不必動到底層核心的算帳與驗證程式碼！

總結這張投影片，請記住這個核心觀念：MVC 透過分離視覺呈現與領域資料模型，賦予使用者介面獨立演進的高度彈性。
-->

## 2. 分層架構模式 (Layered Architecture)

<div class="centered-image">
  <img src="../../img/ch05/architecture/pattern_layered.svg" style="max-height: 290px; width: auto;" alt="Layered Architecture Diagram" />
</div>

* **階層劃分與相依規則：**
  - 水平劃分為四層：**呈現層 (UI) → 商業邏輯層 (Business) → 資料存取層 (DAO) → 資料庫 (DB)**。
  - **嚴格分層原則 (Strict Layering)**：每一層只允許單向呼叫其緊鄰的下一層 (`Layer N → Layer N-1`)。
* **工程優勢與取捨代價：**
  - **優勢**：抽象層次清晰；模組替換性極佳（更換資料庫底層技術時，商業邏輯層完全無感）。
  - **代價**：**架構水槽反模式 (Architecture Sinkhole Anti-pattern)**（簡單查詢穿透多層卻不做事，徒增延遲）。

<!--
第二個模式是企業資訊系統最廣泛採用的：分層架構 (Layered Architecture)。

請注意由上至下的水平階層：呈現層在最上方，中間是核心商業邏輯，下方是資料存取層與資料庫。

其鐵律是單向向下呼叫：呈現層呼叫商業邏輯，商業邏輯呼叫資料存取。資料庫絕不能反過來呼叫前端！

這帶來絕佳的模組化：未來若想將關聯資料庫換成 NoSQL，只要抽換資料存取層，上層的商業邏輯一行都不用改！

總結這張投影片，請記住這個核心觀念：分層架構實踐嚴格的垂直抽象邊界，確保上層邏輯不受底層實作技術變更的干擾。
-->

## 3. 儲存庫架構模式 (Repository Architecture)

<div class="centered-image">
  <img src="../../img/ch05/architecture/pattern_repository.svg" style="max-height: 290px; width: auto;" alt="Repository Architecture Diagram" />
</div>

* **核心組件與拓撲特徵：**
  - **中央儲存庫 (Central Repository)**：維持系統所有持久化資料的被動共享儲存中心。
  - **獨立存取組件 (Active Subsystems)**：各自獨立運作的工具或子系統，僅透過中央庫進行資料交換。
* **工程優勢與取捨代價：**
  - **優勢**：極度適合共享海量複雜資料（如 IDE 的語法樹 AST、編譯器各階段 pass）；各工具間零直接相依。
  - **代價**：中央儲存庫極易成為全系統的效能瓶頸與**單一故障點 (SPOF)**；資料綱要變更牽一髮動全身。

<!--
第三個模式：儲存庫架構 (Repository Architecture)，在 AI 領域常被稱為黑板模式 (Blackboard)。

看它的星狀拓撲：編譯器裡的詞法分析器、語法檢查器、最佳化器與程式碼產生器，彼此完全不互相呼叫！它們只讀取與寫入中央儲存庫中的抽象語法樹 (AST)。

這讓擴充新工具變得無比簡單：只要插上中央庫就能開工。

但致命缺點也很明顯：中央庫一旦當機，全系統癱瘓；高並行讀寫時，中央庫會成為巨大的效能瓶頸。

總結這張投影片，請記住這個核心觀念：儲存庫架構以中央共享儲存中心消除組件間直接相依，但需承擔單一故障點風險。
-->

## 4. 主從式架構模式 (Client-Server Architecture)

<div class="centered-image">
  <img src="../../img/ch05/architecture/pattern_client_server.svg" style="max-height: 290px; width: auto;" alt="Client-Server Architecture Diagram" />
</div>

* **分散式節點分工：**
  - **伺服端 (Server)**：集中式服務提供者，提供資料儲存、安全運算與核心商業邏輯。
  - **客戶端 (Client)**：分散式消費者，負責向伺服端發送網路請求並呈現操作結果。
* **工程優勢與取捨代價：**
  - **優勢**：資料與商業權限高度集中治理；後端升級部署對使用者透明無感。
  - **代價**：受制於不可靠的網路延遲與中斷；尖峰流量易造成伺服器過載，需額外設計負載平衡與快取。

<!--
第四個模式是現代網際網路的基石：主從式架構 (Client-Server)。

前端瀏覽器與手機 App 透過 TCP/IP 或 HTTPS 網路協定，向後端伺服器請求資源。

這種架構實現了資料的安全集中治理：使用者的敏感情資與銀行帳戶，安全地存放在受防火牆保護的伺服端，而不是放在脆弱的手機裝置上。

但其主要挑戰在於網路的不確定性與伺服器負載：必須設計負載平衡器、反向代理快取與自動擴展機制。

總結這張投影片，請記住這個核心觀念：主從式架構將呈現邏輯推向邊緣終端，並將資料安全與核心治理集中於伺服端。
-->

## 5. 管線與過濾器模式 (Pipe-and-Filter Architecture)

<div class="centered-image">
  <img src="../../img/ch05/architecture/pattern_pipe_filter.svg" style="max-height: 290px; width: auto;" alt="Pipe and Filter Architecture Diagram" />
</div>

* **資料流串流機制：**
  - **過濾器 (Filters)**：獨立、無狀態的資料處理組件，讀取輸入串流，套用轉換後輸出至下一階段。
  - **管線 (Pipes)**：單向傳輸通道，負責緩衝並引導資料流從一個過濾器流向另一個過濾器。
* **工程優勢與取捨代價：**
  - **優勢**：極高可復用性（如 Unix 指令 `cat file | grep 'error' | sort`）；各階段極易並行或分散式加速。
  - **代價**：完全不適合互動式 GUI 系統；各組件間反覆序列化與反序列化文字資料帶來額外開銷。

<!--
第五個模式：管線與過濾器 (Pipe-and-Filter)。

想想 Unix 命令列的管線符號，或是大數據 ETL 資料處理管線。

每一個過濾器都只專注於單一轉換：從管線讀資料、轉換、吐回管線。過濾器完全不知道前一手是誰、後一手是誰，因此能任意排列組合，也能輕鬆利用多核心並行運算！

但這種模式完全不適合需要使用者點擊即時反饋的圖形介面。

總結這張投影片，請記住這個核心觀念：管線過濾器架構將循序資料串流轉換拆解為可自由組合、高度並行的獨立運算單元。
-->

## 6. 微服務架構模式 (Microservices Architecture, MSA)

<div class="centered-image">
  <img src="../../img/ch05/architecture/pattern_microservices.svg" style="max-height: 290px; width: auto;" alt="Microservices Architecture Diagram" />
</div>

* **去中心化自治服務：**
  - 將龐大單體系統分解為圍繞商業領域能力構建的**小型、獨立部署服務叢集**。
  - **一服務一資料庫 (Database-per-Service)**：各服務擁有專屬私有資料庫，嚴禁跨服務直接進行 SQL JOIN 查詢！
* **工程優勢與取捨代價：**
  - **優勢**：團隊自治與獨立部署發布步調；異質技術棧選擇；**卓越的故障衝擊半徑隔離 (Blast Radius)**。
  - **代價**：分散式系統噩夢：網路延遲、跨服務分散式交易 (Saga Pattern) 與最終一致性 (Eventual Consistency)。

<!--
第六個模式是雲原生時代的寵兒：微服務架構 (Microservices Architecture)。

我們不再把整個公司的功能包成一個巨大二進位檔，而是依據領域切分為訂單服務、金流服務、庫存服務。

特別注意：每個服務擁有自己專屬的私有資料庫！金流服務想查使用者，只能透過 REST 或 gRPC API 詢問使用者服務，嚴禁直接跨庫查詢！

雖然它帶來了團隊自治與故障隔離，但分散式交易與網路延遲的維運複雜度極高，絕非免費午餐。

總結這張投影片，請記住這個核心觀念：微服務架構以承擔分散式網路與維運複雜度為代價，換取團隊極致的部署自治與故障隔離。
-->

## 單體架構 vs. 微服務架構：深度技術對比

| 比較維度 | 單體架構 (Monolithic Architecture) | 微服務架構 (Microservices Architecture) |
| :--- | :--- | :--- |
| **部署單元** | 單一巨大二進位執行檔 / WAR 包 / 容器 | 數十至數百個獨立運行的輕量微容器 |
| **資料儲存** | 單一共享全域關聯式資料庫 (Shared DB) | **各服務私有資料庫 (Database-per-Service)** |
| **通訊成本** | 極速奈秒級程序內記憶體呼叫 (In-memory) | 毫秒級網路呼叫 (RPC / REST / gRPC / 訊息佇列) |
| **故障隔離** | **極差**：模組 A 記憶體洩漏會導致全系統當機 | **卓越**：金流服務崩潰，使用者依然能正常瀏覽商品 |
| **團隊擴展** | 龐大代碼衝突、部署協調成本隨人數激增 | 獨立特徵團隊，每週自主上線部署數十次 |
| **維運門檻** | 低門檻（單一 CI/CD 流水線、集中式日誌） | 極高門檻（Kubernetes、分散式追蹤、服務網格） |
| **適用時機** | 新創公司、MVP 概念驗證、小型團隊 (<15人) | 組織規模龐大 (>50人)、業務領域極度複雜之企業 |

<!--
請仔細對比單體架構與微服務架構。

單體就像一棟摩天大樓，所有代碼同住在一個地基資料庫上。呼叫只要奈秒，維運極為簡單。但在十樓漏水，整棟大樓都受影響！

微服務就像獨立別墅社區，每棟房子有自己的水電系統。一間跳電，社區其他人家依然燈火通明。

但請牢記：別墅社區需要複雜的道路、管線維護。不要為了趕時髦而貿然採用微服務；小型團隊從模組化單體起步通常是更明智的選擇。

總結這張投影片，請記住這個核心觀念：微服務是以維運複雜度換取團隊自治與故障隔離；初期除非組織規模龐大，否則應謹慎採用。
-->

## 軟體架構直接決定非功能品質屬性

* **品質屬性無法在軟體完工後靠補丁外掛：**
  - 你無法建造一個高度緊耦合的單體系統，然後指望靠寫幾個單元測試就讓它具備百萬並行能力。
* **架構決策如何實質主宰品質屬性：**
  - ⚡ **效能 (Performance)**：由跨網路呼叫跳轉數、記憶體快取層與資料庫分割策略直接決定。
  - 🛡️ **安全性 (Security)**：由零信任網路隔離、API 閘道防護與機密資料庫階層切分嚴格把關。
  - 🦺 **安全性/防護力 (Safety)**：由關鍵控制核心與非關鍵模組之物理隔離所保障（如汽車煞車 vs. 影音娛樂系統）。
  - 🔄 **可用性與容錯 (Availability)**：由冗餘備援節點、健康檢查、斷路器 (Circuit Breaker) 與自動容錯轉移所構築。
  - 🔧 **可維護性 (Maintainability)**：由系統是否嚴格落實高凝聚與低耦合邊界所主宰。

<!--
為什麼說架構直接主宰了系統的品質屬性？

因為非功能品質屬性——效能、安全性、可用性、容錯力——是結構骨架產生的物理特性，根本無法在事後靠貼補丁加上去！

舉汽車軟體為例：如果把控制煞車的程式碼跟車載娛樂系統放在同一條未隔離的記憶體匯流排上，娛樂系統當機就可能導致煞車失靈！這就是為什麼安全關鍵系統必須有嚴密的實體隔離架構。

總結這張投影片，請記住這個核心觀念：非功能品質屬性是系統結構骨架的直接體現，絕無法在完工後憑空補救。
-->
---
## 架構權衡分析 (Architecture Trade-off Analysis) 與 ATAM

* **不可避免的衝突矩陣 (The Inevitable Conflict Matrix)：**
  - 軟體架構中**不存在完美解法，只有取捨與妥協 (Trade-offs)**：
    - **效能 vs. 安全性**：高強度加密演算法與多層身分驗證必然增加連線延遲。
    - **可用性 vs. 一致性 (CAP 定理)**：分散式系統中，追求絕對一致性必然犧牲高可用響應。
    - **模組化 vs. 執行效能**：極致解耦的多層呼叫，必然帶來物件序列化與堆疊開銷。
* **ATAM (架構權衡分析法 / Architecture Trade-off Analysis Method)：**
  - 由卡內基美隆 SEI 研發之業界標準架構評估方法論，旨在編寫代碼前預先發掘潛在架構風險：
  - **ATAM 核心概念：**
    - **敏感點 (Sensitivity Points)**：對單一品質屬性具有決定性影響的關鍵架構決策。
    - **權衡點 (Trade-off Points)**：同時影響多個互斥品質屬性的兩難決策點（如加密提升安全卻壓低效能）。

<!--
軟體架構最核心的修煉，就是權衡分析。

加重加密能提升安全性，但必然犧牲連線吞吐量；
追求分散式資料的絕對一致性，遇到網路分區時就必須拒絕服務（CAP 定理）。

卡內基美隆大學軟體工程研究所 (SEI) 提出的 ATAM 架構權衡分析法，幫助工程師在動工寫代碼前，提早找出『敏感點』與『權衡點』，做出最負責任的商業決策。

總結這張投影片，請記住這個核心觀念：架構設計的核心本質在於衡量互斥的非功能品質屬性，從中取得最符合商業目標的權衡點。
-->

# **5.4 軟體架構推導與塑模表現：超越 Pattern**

> 「架構是那些你希望一開始就能做對的重要決策。」  
> — *Ralph Johnson (Design Patterns 作者)*

<!--
歡迎來到 5.4 節：軟體架構推導與塑模表現。

在學習完六大經典架構模式之後，初學者常常會產生一個疑問：在真實企業專案中，架構師難道只是像推著購物車一樣，從型錄中挑一個 Pattern 就能收工嗎？

## 架構如何推導？超越 Pattern 挑選的 5 步決策流程

* **架構絕非「挑選 Pattern 的購物車」：**
  - 架構模式只是積木與範本；架構設計的本質是一套嚴謹的**推導、分解與權衡流程**：
* **架構推導五大核心步驟：**
  - **1. 提煉 ASR (關鍵架構需求 / Architecturally Significant Requirements)**：
    - 並非所有需求都影響架構！聚焦於具決定性影響的非功能品質屬性（如 99.99% 可用性、<100ms 延遲）與核心使用案例。
  - **2. 系統分解與邊界劃分 (Decomposition)**：
    - 依據業務領域能力（DDD 限界上下文 Bounded Contexts）或技術層次切分子系統。
  - **3. 組合與合成架構模式 (Pattern Synthesis)**：
    - 現實系統皆為複合架構：外層微服務 Mesh、中間事件驅動管線、內部則是分層 MVC！
  - **4. 定義介面合約與通訊協定 (Protocols & Interfaces)**：
    - 同步 RESTful / gRPC vs. 異步 Kafka / RabbitMQ 事件流。
  - **5. 評估驗證與沉澱決策 (Evaluate & Document)**：
    - 透過 ATAM 評估極端情境，並以 ADR 記錄決策脈絡。

## 如何畫架構圖？傳統 UML 在實務中的定位與陷阱

* **「巨大類別圖陷阱」 (學生最常見的嚴重誤區)：**
  - 學生常畫出一張擠滿 50 個類別的 UML Class Diagram，宣稱那是「系統架構圖」。
  - **致命盲點：** 類別圖只呈現編譯期的物件關聯；它**完全掩蓋了網路通訊、程序隔離、伺服器節點與雲端部屬邊界**！
* **傳統 UML 在巨觀架構中的正確用法：**
  - **1. 組件圖 (Component Diagram)**：
    - 呈現高階軟體組件、提供的介面 (`--O` 棒棒糖符號) 與相依的介面 (`--( ` 插座符號)。
  - **2. 套件圖 (Package Diagram)**：
    - 呈現命名空間分群、子系統模組邊界與套件相依方向。
  - **3. 部屬圖 (Deployment Diagram)**：
    - 呈現實體硬體節點、虛擬機器、容器、執行環境與網路協定 (HTTPS, TCP/IP, JDBC)。

<!--

這是軟體工程學生最常犯的經典錯誤：花了整整三天畫了一張塞滿 50 個 Class 的類別圖，交上去當架構圖。

總結這張投影片，請記住這個核心觀念：切忌以類別圖充當架構圖；應採用組件圖、套件圖與部屬圖呈現巨觀結構。

## 多維度架構視圖：Kruchten 的 4+1 架構視圖模型

* **Philippe Kruchten (1995) 經典洞察：「沒有單一圖表能滿足所有利益關係人！」**
* **4+1 多維度架構模型：**
  - **1. 邏輯視圖 (Logical View / 終端使用者與領域功能)**：
    - 系統的類別結構、領域概念與物件封裝，滿足系統的功能性需求。
  - **2. 程序視圖 (Process View / 整合工程師與效能調校)**：
    - 系統的並行運算 (Concurrency)、執行緒、非同步訊息佇列、處理行程間通訊 (IPC) 與回應效能。
  - **3. 開發視圖 (Development View / 軟體工程師與專案管理)**：
    - 原始碼套件組織、第三方函式庫相依、Maven/Gradle 建置模組結構。
  - **4. 實體視圖 (Physical View / 系統維運與 DevOps)**：
    - 實體伺服器、Docker 容器叢集、網路拓撲、防火牆邊界與部署通訊協定。
  - **+1. 核心場景 (Scenarios / 驅動與驗證核心)**：
    - 貫穿並驗證前述四個視圖的核心業務使用案例 (Use Cases)。

<!--
請看 Philippe Kruchten 享譽全球的 4+1 架構視圖模型。

Kruchten 發現，想用一張圖討好所有人是不可能的任務：業務主管只在乎功能邏輯；程式設計師在乎套件怎麼拆；維運工程師在乎 Kubernetes 節點怎麼連；架構師在乎並行執行緒會不會死結。

總結這張投影片，請記住這個核心觀念：Kruchten 4+1 模型以四個專屬視角結合核心場景，全面調和所有利益關係人的關注點。

## 現代架構視覺化主流：C4 Model

* **Simon Brown 創立之現代、直觀且開發者友善的架構表達標準：**
* **「軟體架構的 Google Maps」——四層層次化縮放邏輯：**
  - 🗺️ **Level 1: System Context (系統情境圖 / 全景空照圖)**：
    - 誰在使用系統？系統與哪些外部系統整合（如第三方金流 Stripe、Google SSO）？
  - 🏙️ **Level 2: Container Diagram (容器圖 / 城市街區圖)**：
    - 包含哪些可獨立部署的單元？（SPA 前端、手機 App、API 後端、關聯資料庫、Redis 快取）與其通訊協定（JSON/HTTPS, gRPC）。
  - 🏛️ **Level 3: Component Diagram (組件圖 / 建築平面圖)**：
    - 放大單一 Container 內部：包含哪些核心架構組件（如 AuthController, PaymentService, UserRepository）？
  - 🚪 **Level 4: Code Diagram (程式碼圖 / 室內裝潢圖)**：
    - 類別圖特寫（通常為選填；只針對極度複雜的演算法模組繪製）。

## 沉澱架構決策：架構決策記錄 (Architecture Decision Records, ADR)

* **為什麼必須撰寫 ADR：**
  - 程式碼忠實記錄了「*怎麼做 (How)*」，但程式碼從不解釋「*為什麼這麼做 (Why)*」。
  - 缺乏 ADR 會引發**「架構考古學 (Architectural Archaeology)」**——新進工程師花費數月苦思當年為何選擇這套非主流技術。
* **標準 ADR 結構 (Michael Nygard 輕量模板)：**
  - **1. 標題 (Title)**：編號與明確決策（例如：`ADR-003: 採用 PostgreSQL 作為交易持久化資料庫`）。
  - **2. 狀態 (Status)**：`提議 (Proposed)` → `接受 (Accepted)` → `廢棄 (Deprecated)` → `被取代 (Superseded)`。
  - **3. 背景脈絡 (Context)**：面臨的商業問題、技術約束與相互抗衡的力量。
  - **4. 決策內容 (Decision)**：採取的具體架構方案與選型依據。
  - **5. 後續影響 (Consequences)**：帶來的好處，以及**明確承擔的負面代價與權衡**！

<!--
架構師如何記錄他們的決策？

優秀的架構師絕不只畫圖，他們一定會撰寫 ADR：架構決策記錄。

當三年後新工程師加入團隊，看到系統竟然用 Kafka 而不用 RabbitMQ，常常會心生抱怨。但如果有一份 ADR，記載了當年是因為必須支撐每天五千萬筆即時串流事件，大家就會立刻理解這個決策的智慧與代價。

## 從巨觀架構邁向微觀詳細設計 (From Architecture to Detailed Design)

* **架構藍圖與原始代碼的深度連結：**
  - 巨觀架構建立了系統骨架與子系統邊界。
  - 微觀詳細設計則以健全、易讀的類別與方法填滿該骨架。
* **防範「微觀腐敗 (Micro-Decay)」危機：**
  - 即便採用最先進的微服務或分層架構，若單一服務內部的類別退化為高耦合的義大利麵代碼，整體系統依然會崩塌！
* **SOLID 五大原則全稱 (Robert C. Martin 提煉)：**
  - **S**：單一職責原則 (Single Responsibility Principle, SRP)
  - **O**：開放封閉原則 (Open / Closed Principle, OCP)
  - **L**：里氏替換原則 (Liskov Substitution Principle, LSP)
  - **I**：介面隔離原則 (Interface Segregation Principle, ISP)
  - **D**：相依反轉原則 (Dependency Inversion Principle, DIP)

## S &ndash; 單一職責原則 (Single Responsibility Principle, SRP)

* **核心原則：**
  > 一個類別應該有且僅有一個引起它改變的原因 (Reason to Change)。
* **為什麼 SRP 至關重要：**
  - 當一個類別承擔多重職責時，來自不同業務利益關係人的需求變更會混雜在一起，導致非預期的迴歸錯誤。

```java
// ❌ 違反 SRP：承擔多重責任的「上帝類別」，擁有多個改變理由
class UserInvoiceReport {
    public void calculateTotal() { /* 財務部規則變更 */ }
    public void renderHtmlPage()  { /* 行銷部 UI 樣式變更 */ }
    public void saveToDatabase()  { /* DBA 資料表欄位變更 */ }
}
```

```java
// ✅ 遵循 SRP：各司其職，每個類別只有單一改變理由
class InvoiceCalculator { public BigDecimal calculateTotal(Invoice inv) { ... } }
class InvoiceHtmlRenderer { public String render(Invoice inv) { ... } }
class InvoiceRepository { public void save(Invoice inv) { ... } }
```

<!--
我們先來看第一個原則：單一職責原則 (SRP)。

Uncle Bob 對職責的定義非常精準：『一個引起改變的原因』。
在上面的錯誤示範中，UserInvoiceReport 居然有三個不同的改變理由：
財務部改稅率，找它改；行銷部改網頁版型，找它改；DBA 改欄位，還是找它改！

將其拆分為 Calculator、HtmlRenderer 與 Repository 後，每個類別只對應單一業務部門與單一修改理由。

## O &ndash; 開放封閉原則 (Open / Closed Principle, OCP)

* **核心原則 (Bertrand Meyer 提出)：**
  > 軟體實體（類別、模組、函式）應當**對擴充開放 (Open for extension)**，但**對修改封閉 (Closed for modification)**。
* **如何達成 OCP：**
  - 依賴抽象介面；當需要加入新行為時，透過「新增新的類別」來擴充，**絕不開刀修改已通過測試的既有程式碼**！

```java
// ❌ 違反 OCP：每新增一種通知管道，就必須打開既有類別硬改 if/else！
if (type.equals("EMAIL")) { sendEmail(); }
else if (type.equals("SMS")) { sendSms(); }
else if (type.equals("DISCORD")) { sendDiscord(); } // 風險極高的修改！
```

```java
// ✅ 遵循 OCP：藉由多型介面，以新增實作類別達成無痛擴充
interface NotificationChannel { void send(String message); }
class EmailChannel implements NotificationChannel { ... }
class DiscordChannel implements NotificationChannel { ... } // 核心引擎零修改！
```

<!--
第二個原則：開放封閉原則 (OCP)。

OCP 主張：當商業需求擴充時，你應該透過新增代碼來擴展功能，而不是透過修改既有已經在線上穩定運行的代碼。

看看壞例子：每次行銷團隊想新增通知管道（簡訊、LINE、Discord），工程師就得打開既有的 NotificationManager 補上一段 else if。一不小心打錯字，連原本正常的 Email 通道也跟著陪葬！

改用多型介面後，新增 DiscordChannel 只要寫新類別，原本的核心引擎一行都不用動！

總結這張投影片，請記住這個核心觀念：OCP 提倡以新增多型類別達成功能擴展，杜絕修改既有穩定代碼帶來的迴歸風險。

## L &ndash; 里氏替換原則 (Liskov Substitution Principle, LSP)

* **核心原則 (圖靈獎得主 Barbara Liskov 提出)：**
  > 子型態必須能夠無痛替換其基礎型態，而不會破壞程式的任何預期正確性。
* **經典反例：正方形繼承長方形 (The Square-Rectangle Problem)：**
  - 數學上正方形是長方形；但在物件導向中，覆寫 `setWidth(w)` 連帶修改 `height` 會破壞呼叫端的契約期待！

```java
// ❌ 違反 LSP：覆寫引發非預期副作用，破壞基礎契約
class Rectangle {
    protected int w, h;
    public void setWidth(int w) { this.w = w; }
    public void setHeight(int h) { this.h = h; }
    public int getArea() { return w * h; }
}
class Square extends Rectangle {
    @Override public void setWidth(int w) { this.w = this.h = w; } // 破壞了調用端期待！
}
```

* **工程守則：** 子類別絕不可放寬前置條件 (Preconditions)，亦不可縮減後置條件 (Postconditions)！

<!--
第三個原則：圖靈獎得主 Barbara Liskov 提出的里氏替換原則 (LSP)。

LSP 要求：如果你的程式能接受父類別，那麼傳入任何子類別時，行為必須符合預期，絕不能拋出意外異常或產生奇怪副作用。

經典反例就是正方形繼承長方形。呼叫端以為拿到長方形，把寬設成 5、高設成 10，期待面積是 50。沒想到傳進來的是正方形，改高的時候連寬一起變成 10，算出來面積居然變成 100！

子類別必須完全遵守父類別承諾的契約。

總結這張投影片，請記住這個核心觀念：子類別必須忠實履踐父類別承諾的行為契約，確保多型替換時系統維持穩定正確。
-->

## I &ndash; 介面隔離原則 (Interface Segregation Principle, ISP)

* **核心原則：**
  > 用戶端不應該被迫依賴其所不需要的方法。
* **核心主張：** 寧可建立多個**精巧專一的角色介面 (Role Interfaces)**，絕不要打造包山包海的「肥大介面 (Fat Interface)」。

```java
// ❌ 違反 ISP：肥大介面強迫實作者填入無意義的虛構實作
interface MultiFunctionPrinter {
    void print();
    void scan();
    void fax();
}
class SimpleInkjetPrinter implements MultiFunctionPrinter {
    public void print() { /* 正常列印 */ }
    public void scan()  { throw new UnsupportedOperationException(); } // 遭受污染！
    public void fax()   { throw new UnsupportedOperationException(); } // 遭受污染！
}
```

```java
// ✅ 遵循 ISP：精確切分角色介面，各取所需
interface Printer { void print(); }
interface Scanner { void scan(); }
class SimpleInkjetPrinter implements Printer { public void print() { ... } }
```

<!--
第四個原則：介面隔離原則 (ISP)。

ISP 警告我們千萬別設計臃腫肥大的介面。
看看包含列印、掃描、傳真的多功能事務機介面。一台只要一千塊的陽春噴墨印表機只能列印，但因為實作了這個大介面，它必須為掃描和傳真寫出拋出異常的空函式！

未來只要傳真通訊協定一修改，原本跟傳真毫不相干的印表機類別居然得被迫重新編譯！

將大介面拆解成 Printer 與 Scanner，客戶端就能依需求乾淨引用。

總結這張投影片，請記住這個核心觀念：設計精巧專一的角色介面，避免客戶端被迫相依其不需要的方法簽名。
-->

## D &ndash; 相依反轉原則 (Dependency Inversion Principle, DIP)

* **核心原則：**
  > 1. 高階模組不應依賴低階模組；兩者皆應依賴於抽象介面。  
  > 2. 抽象介面不應依賴於細節實作；細節實作必須依賴於抽象介面。

```java
// ❌ 違反 DIP：高階商業邏輯與特定底層 MySQL 資料庫死死綁定
class OrderService {
    private MySQLDatabase db = new MySQLDatabase(); // 直接 'new' 出具體實作！
}
```

```java
// ✅ 遵循 DIP：依賴注入抽象介面 (Dependency Injection)
interface Database { void save(Order o); }
class MySQLDatabase implements Database { ... }
class MockDatabase implements Database { ... } // 單元測試秒跑記憶體假物件！

class OrderService {
    private final Database db;
    public OrderService(Database db) { this.db = db; } // 由外部注入抽象！
}
```

<!--
第五個原則：相依反轉原則 (DIP)。

傳統程式設計中，高階業務邏輯通常直接 import 底層資料庫。DIP 將這個相依方向徹底倒轉！

在壞設計中，OrderService 裡面直接 new 出 MySQLDatabase。這把核心業務死死釘在 MySQL 上！想換成 PostgreSQL 就得重寫商業邏輯，寫測試時還必須真的架設 MySQL！

在好設計中，OrderService 只依賴抽象的 Database 介面。正式上線注入 MySQL，跑單元測試時注入極速的記憶體 Fake 物件！

總結這張投影片，請記住這個核心觀念：反轉相依方向，讓高階商業邏輯依賴於抽象介面，而非底層具體實作細節。
-->

## AI 在架構與設計中的角色：副駕駛典範 (The Copilot Paradigm)

* **軟體架構師工具庫的典範轉移：**
  - **傳統工作流**：純手工白板繪圖、耗時冗長的人工作業評審、步履維艱的手工重構。
  - **AI 賦能工作流**：對話式架構權衡探索、自動化架構異味掃描、提示詞驅動介面生成。
* **「是副駕駛 (Copilot)，不是自動駕駛 (Autopilot)」鐵律：**
  - AI 擅長於**發散生成多元備選方案、快速草擬文檔與列舉極端情境**。
  - 人類架構師必須提供**組織團隊脈絡、雲端維運預算、法規資安邊界與最終責任承擔**。

## AI 在軟體設計中的 4 大核心落地應用

* **1. 架構權衡探索與極端壓力演練 (ATAM 輔助)：**

* **2. 自動化代碼異味與反模式掃描 (Code Smell Detection)：**

## 人機協同防護：防範 AI 架構盲點 (Architectural Blind Spots)

* **盲目採納 AI 產生的三大致命風險：**
  - **過度複雜化 (Resume-Driven Architecture)**：AI 經常過度工程化，為 3 個人兩週就能搞定的內部工具推薦 Kubernetes、微服務與 Kafka！
  - **組織脈絡盲目 (Context Blindness)**：AI 完全不知道你們團隊無人會除錯分散式競態條件，也無視你們的雲端預算上限。
  - **膚淺表面重構 (Superficial Refactoring)**：僅替換變數名稱，卻未根本解決資料耦合與架構瓶頸。
* **系統架構的至高金科玉律：**
  > **「AI 提案得失，架構師裁奪決策！」**  
  > 人類工程師必須依據現實組織環境做裁量，並對系統的長期健全負起終極責任。

<!--
儘管 AI 威力無窮，架構師必須隨時保持清醒，提防 AI 的盲點。

大型語言模型常患有『履歷導向架構症候群』——動輒推薦分散式微服務與訊息佇列。但 AI 根本不知道你們團隊連 Docker 都不熟，也不知道雲端預算只剩一萬塊！

最可怕的失敗不是被 AI 取代，而是被 AI 推薦的過度工程化徹底搞垮。

總結這張投影片，請記住這個核心觀念：AI 加速得失探索，但人類架構師必須依據真實組織脈絡把關，堅守防範過度工程化的防線。
-->

<script>
(function() {
  // =========================================================================
  // 1. Header Dropdown (Table of Contents / Outline)
  // =========================================================================
  function initHeaderDropdown() {
    const sections = [];
    const seenTitles = new Set();
    const slideSections = document.querySelectorAll('section[id]');
    
    // 1. Scan unique section titles and their slide IDs
    slideSections.forEach(sec => {
      const header = sec.querySelector('header');
      if (!header) return;
      
      let title = header.textContent.trim();
      title = title.replace(/^[◄◀]\s*/, '').replace(/\s*[►▶]$/, '').trim();
      if (!title || seenTitles.has(title)) return;
      
      seenTitles.add(title);
      sections.push({
        id: sec.id,
        title: title
      });
    });

    if (sections.length === 0) return;

    // Detect language: if slide titles don't have Chinese characters, use English
    const allTitles = sections.map(s => s.title).join('');
    const isEn = !/[\u4e00-\u9fa5]/.test(allTitles);
    const txtOutline = isEn ? '📑 Table of Contents' : '📑 章節目錄';
    const txtTitleTooltip = isEn ? 'Click to pin or hover to view outline' : '點擊固定或懸停查看章節目錄';
    const txtPrev = isEn ? 'Previous Section' : '上一章節';
    const txtNext = isEn ? 'Next Section' : '下一章節';

    // Helper to create the dropdown DOM
    function createDropdownWrapper(currentTitle) {
      const wrapper = document.createElement('span');
      wrapper.className = 'header-nav-wrapper';
      
      const titleSpan = document.createElement('span');
      titleSpan.className = 'header-nav-title';
      titleSpan.title = txtTitleTooltip;
      titleSpan.innerHTML = currentTitle + '<span class="nav-caret"> ▾</span>';
      
      titleSpan.addEventListener('click', function(e) {
        e.stopPropagation();
        const wasOpen = wrapper.classList.contains('is-open');
        document.querySelectorAll('.header-nav-wrapper.is-open').forEach(w => w.classList.remove('is-open'));
        if (!wasOpen) {
          wrapper.classList.add('is-open');
        }
      });
      
      const dropdown = document.createElement('div');
      dropdown.className = 'nav-dropdown';
      
      dropdown.addEventListener('click', function(e) {
        e.stopPropagation();
      });
      
      const dropHeader = document.createElement('div');
      dropHeader.className = 'nav-dropdown-header';
      dropHeader.innerHTML = '<span>' + txtOutline + '</span>';
      dropdown.appendChild(dropHeader);
      
      const grid = document.createElement('div');
      grid.className = 'nav-dropdown-grid';
      
      sections.forEach(s => {
        const item = document.createElement('a');
        const isActive = (s.title === currentTitle);
        item.className = 'nav-dropdown-item' + (isActive ? ' active' : '');
        item.href = '#' + s.id;
        item.innerHTML = '<span class="badge">#' + s.id.padStart(2, '0') + '</span><span class="item-text" title="' + s.title + '">' + s.title + '</span>';
        
        item.addEventListener('click', function(e) {
          e.preventDefault();
          wrapper.classList.remove('is-open');
          dropdown.style.display = 'none';
          const targetHash = '#' + s.id;
          if (window.location.hash === targetHash) {
            window.dispatchEvent(new HashChangeEvent('hashchange'));
          } else {
            window.location.hash = targetHash;
          }
          setTimeout(() => { dropdown.style.display = ''; }, 350);
        });
        
        grid.appendChild(item);
      });
      
      dropdown.appendChild(grid);
      wrapper.appendChild(titleSpan);
      wrapper.appendChild(dropdown);
      return wrapper;
    }

    // Close any pinned dropdown when clicking anywhere outside
    document.addEventListener('click', function(e) {
      if (!e.target.closest('.header-nav-wrapper')) {
        document.querySelectorAll('.header-nav-wrapper.is-open').forEach(w => w.classList.remove('is-open'));
      }
    });

    // 2. Enhance each header element across all slides
    slideSections.forEach(sec => {
      const header = sec.querySelector('header');
      if (!header || header.dataset.navEnhanced) return;
      header.dataset.navEnhanced = 'true';
      
      const links = header.querySelectorAll('a');
      let prevLink = null;
      let nextLink = null;
      
      links.forEach(a => {
        const txt = a.textContent.trim();
        if (txt === '◄' || txt === '◀') prevLink = a;
        if (txt === '►' || txt === '▶') nextLink = a;
      });
      
      let title = header.textContent.trim();
      title = title.replace(/^[◄◀]\s*/, '').replace(/\s*[►▶]$/, '').trim();
      if (!title) return;
      
      header.innerHTML = '';
      if (prevLink) {
        prevLink.className = 'header-nav-arrow';
        prevLink.title = txtPrev;
        header.appendChild(prevLink);
        header.appendChild(document.createTextNode(' '));
      }
      
      const wrapper = createDropdownWrapper(title);
      header.appendChild(wrapper);
      
      if (nextLink) {
        header.appendChild(document.createTextNode(' '));
        nextLink.className = 'header-nav-arrow';
        nextLink.title = txtNext;
        header.appendChild(nextLink);
      }
    });
  }

  // =========================================================================
  // 2. Number Quick Jump (<kbd>Num</kbd> + <kbd>Enter</kbd>)
  // =========================================================================
  function initNumberQuickJump() {
    let inputBuffer = '';
    let timer = null;
    let hud = null;

    // Detect language: check titles or body text
    const slideSections = document.querySelectorAll('section[id]');
    let hasZh = false;
    slideSections.forEach(s => {
      if (/[\u4e00-\u9fa5]/.test(s.textContent || '')) hasZh = true;
    });
    const isEn = !hasZh;

    function getOrCreateHud() {
      if (!hud) {
        hud = document.createElement('div');
        hud.id = 'slide-quick-jump-hud';
        hud.style.cssText = [
          'position: fixed',
          'bottom: 36px',
          'left: 50%',
          'transform: translateX(-50%)',
          'background: rgba(15, 23, 42, 0.94)',
          'color: #ffffff',
          'padding: 8px 18px',
          'border-radius: 28px',
          'font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, system-ui, sans-serif',
          'font-size: 14px',
          'font-weight: 500',
          'box-shadow: 0 16px 36px rgba(0, 0, 0, 0.35), 0 0 0 1px rgba(255, 255, 255, 0.15)',
          'backdrop-filter: blur(16px)',
          '-webkit-backdrop-filter: blur(16px)',
          'z-index: 999999',
          'display: none',
          'align-items: center',
          'gap: 8px',
          'pointer-events: none',
          'opacity: 0',
          'transition: opacity 0.15s ease, transform 0.15s ease'
        ].join(';');
        const targetParent = document.fullscreenElement || document.body;
        targetParent.appendChild(hud);
      }
      const parent = document.fullscreenElement || document.body;
      if (hud.parentElement !== parent) {
        parent.appendChild(hud);
      }
      return hud;
    }

    function getTotalSlides() {
      const secs = document.querySelectorAll('section[id]');
      return secs.length || 1;
    }

    function showHud() {
      const el = getOrCreateHud();
      const total = getTotalSlides();
      const label = isEn ? 'Go to slide:' : '跳至頁碼:';
      const enterHint = isEn ? 'Enter ↵' : 'Enter 確認 ↵';
      el.innerHTML = '<span>🧭 ' + label + '</span> ' +
        '<strong style="color: #38bdf8; font-size: 20px; font-weight: 700; font-family: ui-monospace, SFMono-Regular, Menlo, monospace; letter-spacing: 1px;">' + inputBuffer + '</strong> ' +
        '<span style="opacity: 0.6; font-size: 13px;">/ ' + total + '</span> ' +
        '<span style="background: rgba(255,255,255,0.18); padding: 2px 7px; border-radius: 6px; font-size: 11px; margin-left: 2px; font-weight: 600;">' + enterHint + '</span>';
      el.style.display = 'flex';
      el.style.opacity = '1';

      if (timer) clearTimeout(timer);
      timer = setTimeout(clearInput, 2800);
    }

    function clearInput() {
      inputBuffer = '';
      if (timer) {
        clearTimeout(timer);
        timer = null;
      }
      if (hud) {
        hud.style.opacity = '0';
        setTimeout(() => {
          if (inputBuffer === '' && hud) hud.style.display = 'none';
        }, 150);
      }
    }

    function jumpToSlide(num) {
      const total = getTotalSlides();
      const target = Math.max(1, Math.min(num, total));
      const targetHash = '#' + target;
      
      // Visual flash confirmation
      const el = getOrCreateHud();
      const confirmedMsg = isEn ? ('✓ Slide ' + target) : ('✓ 第 ' + target + ' 頁');
      el.innerHTML = '<span style="color: #34d399; font-weight: 700; font-size: 15px;">' + confirmedMsg + '</span>';
      el.style.display = 'flex';
      el.style.opacity = '1';
      setTimeout(clearInput, 500);

      if (window.location.hash === targetHash) {
        window.dispatchEvent(new HashChangeEvent('hashchange'));
      } else {
        window.location.hash = targetHash;
      }
    }

    window.addEventListener('keydown', function(e) {
      // Don't intercept when focusing editable form elements
      const active = document.activeElement;
      if (active && (active.tagName === 'INPUT' || active.tagName === 'TEXTAREA' || active.tagName === 'SELECT' || active.isContentEditable)) {
        return;
      }

      // Ignore if modifier keys are pressed
      if (e.ctrlKey || e.altKey || e.metaKey) {
        return;
      }

      // Resolve digit from key or code (supports '2', 'Digit2', 'Numpad2')
      let digit = null;
      if (e.key >= '0' && e.key <= '9') {
        digit = e.key;
      } else if (/^(?:Digit|Numpad)([0-9])$/.test(e.key)) {
        digit = e.key.replace(/^(?:Digit|Numpad)/, '');
      } else if (/^(?:Digit|Numpad)([0-9])$/.test(e.code || '')) {
        digit = (e.code || '').replace(/^(?:Digit|Numpad)/, '');
      }

      if (digit !== null) {
        inputBuffer += digit;
        if (inputBuffer.length > 4) inputBuffer = inputBuffer.slice(-4);
        showHud();
        return;
      }

      // Backspace
      if ((e.key === 'Backspace' || e.code === 'Backspace') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        inputBuffer = inputBuffer.slice(0, -1);
        if (inputBuffer.length === 0) {
          clearInput();
        } else {
          showHud();
        }
        return;
      }

      // Escape
      if ((e.key === 'Escape' || e.code === 'Escape') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        clearInput();
        return;
      }

      // Enter key confirms numeric jump
      if ((e.key === 'Enter' || e.code === 'Enter' || e.code === 'NumpadEnter') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        const targetPage = parseInt(inputBuffer, 10);
        if (!isNaN(targetPage)) {
          jumpToSlide(targetPage);
        } else {
          clearInput();
        }
      }
    }, true);
  }

  // Initialize both features
  function init() {
    initHeaderDropdown();
    initNumberQuickJump();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', init);
  } else {
    init();
  }
  setTimeout(init, 400);
})();

</script>
