# **6.1 使用者體驗 (UX) 設計基礎**

> "Good design is actually a lot harder to notice than poor design, in part because good designs fit our needs so well that the design is invisible."  
> *(優秀的設計往往比糟糕的設計更難被察覺，因為好設計與我們的需求契合得天衣無縫，以至於它本身隱形了。)*  
> — *Don Norman (《設計的心理學》作者)*

## 為什麼好設計如此重要？從「諾曼門」談起

> **什麼是「諾曼門 (Norman Door)」？** 一扇外觀給出**錯誤直覺暗示**的門——例如裝了明顯的「**拉把**」，實際上卻必須「**用推的**」才打得開！

<div class="split73">
<div class="left">

* **當設計違背直覺時的真實情緒（尷尬與生氣）：**
  - 看到門把下意識用力拉，門卻紋風不動——瞬間讓人感到**尷尬、丟臉、懷疑自己，甚至惱怒生氣**。
  - Don Norman 指出：**這絕不是使用者的錯，而是糟糕的設計**違背了人類的本能反應！
* **從一扇門帶出 UX（使用者體驗）的核心價值：**
  - *「當一扇日常大門還需要貼上『**請用推的 (PUSH)**』字條時，這個設計本身就失敗了。」* —— Don Norman
  - 軟體介面同樣充滿「數位諾曼門」：好的 **UX 設計**讓視覺線索契合人類直覺，讓使用者感到**順暢與被尊重**，而非受挫生氣。

## 劣質 UI/UX 所帶來的挫折與代價

> 「當介面混亂難用時，使用者很少怪罪系統架構師——他們只會感到**認知挫折**、懷疑自己，然後**憤而放棄產品**。」

<div class="split73">
<div class="left">

* **糟糕軟體對使用者心理的摧殘：**
  - 引發認知超載、困惑迷惘、焦慮無助，最後導致使用者憤而放棄（User Rage & Churn）。
  - 使用者往往不會怪罪背後的資料庫或架構師，只會留下 1 星負評並怒刪 App。
* **劣質 UX 如何摧毀企業商業價值：**
  - **購物車放棄率高達 70%：** 結帳流程過於繁瑣、表單驗證不明確直接導致營收蒸發。
  - **龐大客服成本支出：** 數以萬計的客服電話與工單，根本源頭都是混亂的介面導覽。
  - **企業員工生產力內耗：** 難用的內部企業 ERP/CRM 系統，導致日常操作頻繁出錯與嚴重工時浪費。

## 不良設計原型 (1)：「夜市擺攤風」的感官超載

> **「夜市擺攤風」(Arngren-Style Overload)：** 將數百項商品、閃爍跑馬燈與衝突連結全部硬塞進單一畫面，毫無視覺階層。

<div class="split73">
<div class="left">

* **為什麼這種設計很糟糕？**
  - **模式識別失效：** 每個商品區塊的長寬比、對齊線與字體完全隨機，大腦無法建立模式，必須對每個點重新「對焦」，造成極度疲勞。
  - **缺乏網格系統與視覺錨點：** 沒有水平或垂直對齊軸線，視線無法順暢掃描。
  - **急性感官超載：** 當畫面上每個元素都同時大聲搶奪注意力時，使用者無法找到核心任務，跳出率極高。

## 不良設計原型 (2)：「油漆不用錢」的色彩對比災難

> **「油漆不用錢」原型：** 濫用衝突刺眼的配色、波紋背景與浮雕陰影，徹底摧毀易讀性與專業品牌信賴感。

<div class="split73">
<div class="left">

* **為什麼這種設計很糟糕？**
  - **色彩對比崩壞：** 在藍色波紋漸層背景上直接壓深紅細體字與亮黃字，產生視覺閃爍感，嚴重違反 **WCAG 無障礙對比度標準**。
  - **排版與字體災難：** 標題濫用厚重浮雕陰影增加視覺噪音；連結列表長短參差不齊，造成嚴重視覺疲勞。
  - **缺乏負空間且摧毀信賴感：** 內容塞得密不透風，尤其在專業醫療 X 光器材網站採用這種配色，會直接摧毀專業信任度。

## 不良設計原型 (3)：「不知從何下手」的導覽與行寬失控

> **「不知從何下手」原型：** 滿螢幕充斥著數十個尺寸相同、未分主次的按鈕與超寬文字段落，缺乏明確的行動呼籲 (CTA)。

<div class="split73">
<div class="left">

* **為什麼這種設計很糟糕？**
  - **缺乏視覺焦點與主次：** 左側一整排紅黑按鈕尺寸與視覺權重完全相同，沒有主要行動呼籲（CTA），使用者不知道該先按哪裡。
  - **資訊洪流無分類：** 頂部將電話、地址與標語全塞進刺眼的亮綠橫幅，毫無導覽層次。
  - **文字行寬失控 (Line Length)：** 右側段落直接橫跨整個寬螢幕，遠超過人類舒適閱讀的 **每行 45～75 字元** 上限，強迫眼球大幅擺動。

## 案例剖析：工程師後端思維 vs. 使用者心智模型

* **第一版緊急上線為何讓民眾找不到？（以系統實作驅動 UI 的反模式）：**
  - **遷就後端認證模組（康威定律）：** 因為買口罩需要實名登入，工程師直接把功能掛在已經有登入機制的 **2 號「健康存摺」** 內，完全違背民眾對「存摺＝查就醫紀錄」的認知。
  - **誤導性的示能線索 (False Signifier)：** **1 號「口罩查詢」** 畫著戴口罩的圖示，吸引無數民眾誤點進入死胡同；頂部紅字跑馬燈看起來像純文字廣告，看不出可以點擊。
  - **視覺規格不一致：** 圓形、長方形存摺、立體書本混雜，缺乏統一網格與階層。
* **改版後如何解決問題？（以使用者目標驅動的九宮格重構）：**
  - **核心任務直接浮出表面：** 將 **「eMask 口罩預購」**、**「History 購買紀錄」** 與 **「Mask Map 口罩地圖」** 三大防疫任務直接獨立拉到最上排第一層。
  - **標準化視覺與雙語標籤：** 統一採用圓形圖示與整齊九宮格，並加上中英雙語標示，讓使用者一秒找到目標。

## 為什麼做好 UX 那麼難？

> **根本原因：** UX 之所以失敗，往往不是因為技術不夠好，而是因為工程思維的盲點與缺乏設計的開發習慣。

<div class="split73">
<div class="left">

- **缺乏系統思考 (Lack of Systems Thinking)**
  - 只有模組思考；功能疊床架屋、來一個做一個 (Patchwork Construction)
- **缺乏使用者思考 (Lack of User Thinking)**
  - 沉溺於後端架構與資料結構，忽略使用者的核心目標
- **缺乏同理心思考 (Lack of Empathic Thinking)**
- **缺乏使用者研究與需求分析 (Lack of User Research)**
- **沒有設計就施工 (Lack of Prior Design)**
  - 跳過互動規劃與原型設計，直接寫程式硬幹
- **缺乏測試、反饋與迭代修正 (Lack of Testing & Iteration)**
  - 未經完整易用性測試與使用者回饋便直接上線

## UI (使用者介面) vs. UX (使用者體驗)

* **使用者介面 (UI / User Interface)：**
  - 人類與軟體互動時，所看見、聽見與觸摸的具體感官接觸點。
  - *元素涵蓋：* 按鈕外觀、字型排版、色彩配置、邊距間距、CSS 格線、圖示、過渡微動畫。
  - *核心關切：* 「這個畫面在視覺上看起來如何？渲染與動效順不順暢？」
* **使用者體驗 (UX / User Experience)：**
  - 人類與品牌、服務或系統在完整旅程中產生的整體心理與情感認知感受。
  - *元素涵蓋：* 任務達成效率、流程阻力、認知負擔、滿意度、容錯修復能力與信賴感。
  - *核心關切：* 「使用者是否能直覺、高效且愉悅地達成他們的目標？」
* **經典生動比喻：**
  - UI 是精緻的馬鞍、韁繩與馬鐙；UX 則是騎在馬背上奔馳的整體駕馭感受！

## 設計思考五大階段詳細拆解

- **1. Empathize (同理 / 探索)：**
  - 進行質化訪談、現地情境觀察（Contextual Inquiry）與使用者行為追蹤。
  - 挖掘未被說出口的深層挫折與真實心理痛點。
- **2. Define (定義問題)：**
  - 將質化研究收斂為具象的人物誌（Personas）、同理心地圖與精確的 "How Might We (我們該如何...)" 問題陳述。
- **3. Ideate (構思解法)：**
  - 開展多元創意思考，暫緩評判；快速繪製低保真紙上草圖（Paper Wireframes）。
- **4. Prototype (打造原型)：**
  - 製作可供點擊測試的實體構件（Figma 可互動點擊原型、可運行的 HTML/CSS 假資料畫面）。
- **5. Test (驗證測試)：**
  - 將原型交由真實目標使用者操作，觀察卡關點，量化任務達成率並快速迭代修正。

### 概念核對問答 1 (CCQ 1)：預設用途 (Affordance) vs. 意符 (Signifier)
<!-- id: ase-ch06-ccq1 -->

<div class="ccq-columns">
  <div class="ccq-text">

某醫院重新設計自助報到機，為追求「極簡風 UI」，將 `「確認報到」` 設計成無邊框、無陰影的純灰字標籤。雖觸控螢幕**可以**感應點擊，卻有 **75% 的年長病患卡住**不知按哪裡。依 **Don Norman** 理論，此設計最核心的缺失為何？

- **A.** **缺乏預設用途 (Affordance)**；觸控螢幕硬體底層缺乏感應手指輕觸文字區塊的物理偵測能力。
- **B.** **缺乏意符 (Signifier)**；系統雖支援點擊，但欠缺邊框、立體陰影或對比色等可感知的視覺線索。
- **C.** **使用者教育訓練不足**；醫院應在自助報到機螢幕旁張貼字體放大的紙本操作步驟說明海報以引導病患。
- **D.** **後端系統模型延遲**；掛號資料庫的交易查詢架構過於繁瑣，必須導入快取機制以加速畫面渲染回應。

## NS01: 系統狀態可見度 (Visibility of System Status)

* **啟發原則定義：**
  > 「系統應在**合理的時間內**，透過**適當的回饋 (Feedback)**，始終**讓使用者明確掌握**當前正在發生什麼事。」
* **核心互動設計模式：**
  - **即時觸控回饋：** 按鈕點擊時的下沉態、微動效波紋（Ripple Effect），立即向使用者確認「輸入已被系統接收」。
  - **進度透明化：** 顯示具備確切百分比的進度條（%）、結帳步驟指示器（1. 購物車 &rarr; 2. 配送資訊 &rarr; 3. 付款）。
  - **背景任務即時狀態：** 旋轉進度環搭配具備動態文字的說明（*「正在上傳第 3 張相片，共 5 張...」*）。
  - **連線狀態提示：** 離線斷網即時警告橫幅、雲端同步狀態勾選指示。

## NS02: 符合真實世界 (Match System & Real World)

* **啟發原則定義：**
  > 「系統應**使用使用者的語言**，採用**使用者熟悉的詞彙、語句和概念**，而不是系統內部的術語。遵循**真實世界的通用慣例**。」
* **自然空間映射 (Natural Mapping)：**
  - 操作控制器在空間上的配置，應精確對應於被控制物體的物理空間幾何。
  - *經典反面教材：* 四口瓦斯爐排列為 2x2 方陣，但四個開關旋鈕卻排成一整條直線，強迫大腦進行繁複的空間座標換算，經常開錯爐火。
  - *優良設計：* 將四個旋鈕同樣排列為 2x2 矩陣，操作直覺秒懂且零出錯。
* **生活實體隱喻 (Familiar Metaphors)：**
  - 資源回收桶代表刪除、資料夾代表目錄階層、購物車代表待結帳商品。

## NS03: 使用者控制與自由度 (User Control & Freedom)

* **啟發原則定義：**
  > 「使用者常因**誤操作**而誤入非預期的功能狀態，此時需要一個清晰標示的『**緊急出口 (Emergency Exit)**』，讓他們能**迅速脫離該狀態**，而不需經歷冗長的對話流程。」
* **必備的工程實踐模式：**
  - **全域復原 / 重做 (Universal Undo / Redo)：** 編輯器、畫布工具及破壞性狀態變更均應全面支援 `Ctrl+Z` / `Cmd+Z`。
  - **清晰的取消出口：** 彈跳視窗（Modals）、檔案上傳與批次處理中，必須提供高對比、易於點擊的「取消 (Cancel)」按鈕。
  - **非破壞性導覽：** 允許使用者隨時退出多步驟結帳或註冊精靈，且不應擅自抹煞已填寫的表單暫存資料。
  - **資源回收暫存區 (Soft Deletes)：** 刪除操作先移至垃圾桶，保留 30 天復原期後才永久清除。

## NS04: 一致性與標準性 (Consistency & Standards)

* **啟發原則定義：**
  > 「使用者**不應懷疑不同的詞彙、狀態或操作是否代表相同的事物**。應遵循**平台與產業通用的既定慣例**。」
* **網際網路體驗的「雅各布定律 (Jakob's Law)」：**
  - 你的使用者有 99% 的數位生命都在**別人的網站與 App 上度過**。
  - 他們預期你的軟體運作方式，與他們熟知的其他產品完全一致（例如：左上角 Logo 回首頁、右上角購物車、放大鏡代表搜尋）。
* **一致性的兩大工程維度：**
  - **內部一致性 (Internal Consistency)：** 產品內部統一的設計系統（Design Tokens）、按鈕樣式、字級比例與名詞定義。
  - **外部一致性 (External Consistency)：** 遵循作業系統平台人機介面指南（iOS HIG 與 Android Material Design）。

  - **智慧預設值 (Intelligent Defaults)：** 預填最常見的合理參數，減少空表單帶給使用者的心理壓力。

## NS06: 辨識取代記憶 (Recognition Rather Than Recall)

* **啟發原則定義：**
  > 「透過**將物件、操作和選項清晰可視化**，使**使用者的記憶負擔降到最低**。使用者**不應被迫記憶**從對話流程某一部分到另一部分的資訊。」
* **認知心理學基石：**
  - **辨識 (Recognition / 大腦輕鬆)：** 看到熟悉的視覺線索時能立刻認出（如同選擇題）。
  - **回憶 (Recall / 大腦耗能)：** 在毫無線索提示下，全憑記憶提取資訊（如同純文字終端機指令或申論題）。
* **UI 工程實踐：**
  - 搜尋輸入框點擊時自動展開最近搜尋歷史關鍵字與熱門建議。
  - 檔案列表顯示縮圖預覽，而非只有冰冷抽象的二進位檔名。
  - 文字選取時自動在游標旁邊浮現情境式編輯工具列。

<!--
原則六：辨識取代記憶。

人類的工作記憶容量極度有限——同時只能處理大約 4 到 7 個資訊組塊。

「辨識」是非常省力的大腦運作：就像選擇題，你看到答案就能秒選。「回憶」則非常耗能：像申論題，大腦要在虛無中搜索資訊。

💡 難字與專業術語解說：
- recognition rather than recall: 辨識取代回憶（將選項視覺化呈現讓大腦直接認出，而非強迫大腦憑空背誦）
- working memory load: 工作記憶負荷（大腦短期暫存與處理資訊的心智負擔）
- blank-slate terminal: 空白終端機介面（毫無視覺提示、全靠背誦指令語法的介面）
- contextual action toolbar: 情境式操作工具列（選取物件時直接在旁邊浮現可用功能的選單）

## NS07: 彈性與使用效率 (Flexibility & Efficiency of Use)

* **啟發原則定義：**
  > 「**加速器 (Accelerators)**（新手使用者看不見）通常能**大幅加快資深專家的操作速度**，讓系統能**同時兼顧並滿足毫無經驗的生手與熟練的高手**。」
* **雙軌互動設計哲學 (Dual-Track Interaction)：**
  - **生手路徑 (Novice Path)：** 引導式圖形選單、功能導覽精靈、大按鈕與詳盡的文字解說。
  - **高手加速器 (Expert Accelerators)：** 全域快捷鍵 (`Cmd+K` / `Ctrl+K` 命令面板)、多指觸控手勢、可重用的巨集指令與批次處理。
* **漸進式熟練轉化：**
  - 在圖形選單中將快捷鍵組合標註於文字旁（如 `Cmd+S`），讓新手在日常點擊中自然習得快捷鍵，無痛晉升為進階用戶。

<!--

生手需要按部就班的精靈引導與大圖示；但如果一位每天處理 500 張發票的會計師每次都要用滑鼠點五層選單，他會精神崩潰。

💡 難字與專業術語解說：
- flexibility & efficiency of use: 彈性與使用效率（同時兼顧新手易學性與專家高效操作的雙軌設計）

- progressive mastery: 漸進式熟練（在選單旁標註快捷鍵提示，幫助新手在日常操作中自然學會快捷鍵）

## NS08: 簡約美學設計 (Aesthetic & Minimalist Design)

* **啟發原則定義：**
  > 「對話框與介面**不應包含無關或極少需要的冗餘資訊**。對話框中**每一單位多餘的資訊**，都在**與真正相關的資訊競爭使用者的有限注意力**，並**削弱其能見度**。」
* **極大化訊噪比 (Signal-to-Noise Ratio, SNR)：**
  - **訊號 (Signal)：** 與使用者當前任務決策直接息息相關的核心關鍵資訊。
  - **雜訊 (Noise)：** 喧賓奪主的裝飾線條、多餘徽章、冗長官樣廢話與閃爍橫幅。
* **工程技巧：漸進式揭露 (Progressive Disclosure)：**
  - 首頁與預設畫面僅展示最核心、80% 使用者必備的主要功能。
  - 將進階、低頻率的專業參數優雅收納於「進階設定 (Advanced)」摺疊面板或次級分頁中。

<!--

使用者螢幕上的注意力是極其寶貴的有限頻寬。每一個花俏的裝飾邊框、每一句廢話，都在瓜分使用者的認知資源。

## NS09: 協助使用者辨識、診斷與修復錯誤

* **啟發原則定義：**
  > 「錯誤訊息應採用**清晰平易的純文字**表達（**絕不出現晦澀代碼**），**精確指出問題的具體成因**，並**建設性地主動提出修復建議方案**。」
* **災難級錯誤訊息範例：**
  - ❌ *"Error 0x80004005: Unexpected runtime exception in thread main."* （讓使用者困惑恐慌，毫無幫助）。
* **卓越錯誤訊息的三大黃金法則：**
  - ✅ **平易白話：** *"我們無法為您的信用卡完成扣款。"*
  - ✅ **精確具體原因：** *"您輸入的有效期限 (05/23) 已經過期。"*
  - ✅ **建設性修復出口：** *"請更新您的信用卡到期日，或選擇其他付款方式 [更新付款資訊]。"*

<!--
原則九：協助使用者辨識與修復錯誤。

當使用者遇到錯誤時，他已經處於脆弱和受挫的情緒狀態中。千萬不要對著使用者吐出十六進位的記憶體代碼或是 Raw SQL Exception！

一條合格的錯誤訊息必須具備三要素：第一，用一般人看得懂的白話說明發生什麼事；第二，精確指出具體原因；第三，附上一個一鍵修復的按鈕或指引。

像現代網站會把冷冰冰的 404 Not Found 轉化為溫暖的搜尋導航頁，這就是極佳的修復實踐。

💡 難字與專業術語解說：
- recognize, diagnose, and recover: 辨識、診斷與修復錯誤（使用者發現出錯、理解原因並成功修正的三階段）
- plain language: 平易白話的自然語言（不含程式碼與系統縮寫的日常用語）
- runtime exception & stack trace: 執行期例外與呼叫堆疊追蹤（程式崩潰時的內部除錯資訊）
- constructive recovery: 具建設性的修復引導（明確告訴使用者「現在該怎麼做才能解決問題」）
-->

## NS10: 說明文件與求助支援 (Help & Documentation)

* **啟發原則定義：**

  - **情境式微提示 (Contextual Tooltips)：** 在複雜欄位旁提供小問號圖示 `?`，滑鼠懸停時即時浮現具體格式說明。

## 什麼是 Web UI/UX 設計模式？ (What is a UI Pattern?)

> **設計模式的本質：** 針對在特定情境下反覆出現的人機互動問題，所提煉出經過驗證的通用架構解決方案。

## Tidwell 介面設計模式的四大架構維度 (The 4 Dimensions)

> **全景架構：** 從底層的人類行為動機，層層向上構築至資訊架構、尋路導航與海量資料呈現。

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 維度 1 & 2：行為認知與資訊架構
- **1. 核心使用者行為模式 (Core Behaviors)**：

## Section 1：核心使用者行為與認知心理模式 (Core Behaviors)

> **核心設計哲學：** 介面必須主動包容人類的認知侷限與行為慣性，而非強迫使用者適應生硬的機器邏輯。

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 1. 試錯探索與即時反饋機制
- **安全探索 (Safe Exploration, TW1.1)**：
  - 消除使用者的點擊恐懼！永遠提供零風險的嘗試機會與明確的復原途徑（**Undo 復原**）。
- **即時滿足 (Instant Gratification, TW1.2)**：
  - 直通主要目標（如電商「再次購買」按鈕），跳過繁複漏斗流程。
- **中途變更 (Changes in Midstream, TW1.4)**：
  - 允許使用者在流程中途直接調整參數（如高鐵查詢即時切換更早/更晚車次），無須返回重填。
- **延遲抉擇 (Deferred Choice, TW1.5)**：
  - 降低首次體驗門檻，非核心資料允許「**稍後再說 (Skip for now)**」。

</div>
<div class="card" data-marpit-fragment>

### 2. 認知負荷與記憶輔助機制
- **增量式建構 (Incremental Construction, TW1.6)**：
  - 一邊撰寫、一邊提供即時動態預覽（如 Overleaf/Markdown Live Preview），減輕工作記憶負荷。
- **習慣化 (Habituation, TW1.7)**：
  - 遵循標準介面慣例（如左側標準導覽列），培養使用者的無意識肌肉記憶。
- **空間記憶 (Spatial Memory, TW1.9)**：
  - 核心功能位置恆定（如右上角設定齒輪），嚴禁動態隨機漂移！
- **前瞻記憶 (Prospective Memory, TW1.10)**：
  - 透過未讀徽章、未完成標記等視覺提示，輔助使用者記住未來待辦任務。

</div>

## Section 2：資訊架構與內容佈局模式 (Organizing Content & Layout)

> **核心設計哲學：** 螢幕空間有限而資訊無窮，優秀的佈局必須以使用者的發現路徑為核心，建立清晰的視覺階層。

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 1. 內容發現三要素與空間框架
- **內容發現三要素 (The Discovery Trifecta, TW2.1)**：
  - **搜尋 (Search)**：針對目標明確的使用者，提供直接、意圖驅動的文字查詢。
  - **焦點舞台 (Feature / Center Stage, TW4.2)**：系統主動推薦的核心精選，第一眼抓住眼球。
  - **分類瀏覽 (Browse)**：針對探索型使用者，提供依類別展開的圖文瀏覽清單。
- **儀表板 (The Dashboard, TW2.5)**：
  - 高密度匯總關鍵維運指標，提供一覽無遺的全局掌握力。
- **替代檢視 (Alternative Views, TW2.9)**：
  - 賦予使用者自主權，以偏好的形式消費同一份資料（如：地圖模式 vs. 清單模式）。

</div>
<div class="card" data-marpit-fragment>

### 2. 時間組織與複雜度控制
- **漸進式揭露 (Progressive Disclosure)**：
  - 預設保持介面極簡乾淨；唯有當使用者觸發特定編輯情境時，才揭露進階工具箱。
- **步驟精靈 (The Wizard, TW2.7)**：
  - 將龐大、令人生畏的繁雜流程，拆解為線性、可預測的步驟導航（Step 1 → 2 → 3）。
- **模組分頁 (Module Tabs, TW4.5)**：
  - 適用於**同層級、互斥**的資料切換（如：按主題 / 按月份 / 按頁面）。
- **手風琴摺疊 (Accordion, TW4.6)**：
  - 適用於**原地向下深入展開層級細節**（如 FAQ 常見問答），不跳離當前頁面。

</div>

## Section 3：尋路機制與導航設計模式 (Wayfinding & Navigation)

> **核心設計哲學：** 優秀的導航系統解答人類在數位空間的三大終極問題：**「我在哪裡？還剩多少？如何離開？」**

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 1. 入口識別與模態逃生黃金法則
- **明確進入點 (Clear Entry Points, TW3.1)**：
  - 清晰的第一道起跑線（如首頁顯著的「登入」或行動號召大按鈕），消除觀望猶豫。
- **身分管理工具 (Sign-in Tools, TW3.9)**：
  - 個人檔案、組織切換與登出選單，固定於右上角習慣化位置（Habitual Placement）。
- **模態視窗的黃金法則 (The Golden Rule of Modals)**：
  - 當以**強制回應面板 (Modal Panels / Forced Response, TW3.4)** 鎖定使用者專注力時：
  - **必須無條件設計逃生出口 (Escape Hatches, TW3.6)！**
  - **右上角的「✕ 關閉按鈕」與「確定送出」按鈕同等重要！** 嚴禁讓使用者陷入無路可退的死胡同。

</div>
<div class="card" data-marpit-fragment>

### 2. 三層次空間與進度感知定位體系
- **頂層流程進度 (Progress Indicators, TW3.10)**：
  - 針對線性、多步驟的任務流程，以編號節點（1 → 2 → 3 → 4）清楚標示「還剩多少步」。
- **中層階層定位 (Breadcrumbs, TW3.11)**：
  - 針對深層樹狀結構的資訊架構（如：`學年度 > 學院 > 系所 > 課程`），提供可點擊回溯的麵包屑軌跡。
- **底層長頁面定位 (Annotated Scrollbar, TW3.12)**：
  - 針對超長單頁海量資料（如通訊錄、日誌），在捲軸邊緣標註字母索引或視覺錨點，支援極速滑動跳轉。

</div>

## Section 4：資料呈現與集合展示模式 (Data Display & Lists)

> **核心設計哲學：** 依據硬體螢幕尺寸與使用者任務目標，在空間利用率與視覺掃描效率之間取得最佳平衡。

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 1. 跨裝置響應式清單架構
- **桌面寬螢幕：雙欄分割檢視 (Two-Panel Split View, TW7.1)**：
  - 左側維持長駐清單，右側同步呈現詳細內容（如 Slack、Outlook）。
  - **核心價值**：徹底消除在清單頁與細節頁之間的來回往返跳轉。
- **行動窄螢幕：單視窗深入鑽取 (One-Window Drilldown, TW7.2)**：
  - 窄螢幕下清單被詳細內容完全覆蓋替換（如 iOS Mail）。
  - **核心要求**：左上角必須強制配置醒目的返回鍵（Back button）。

</div>
<div class="card" data-marpit-fragment>

### 2. 空間壓縮與視覺掃描模式
- **縮圖網格 (Thumbnail Grid, TW7.5)**：
  - 「小而多」的高密度排列（如相簿網格），最適化人眼的高速視覺比對與掃描。
- **輪播切換 (Carousel, TW7.6)**：
  - 將多張大型圖片或卡片壓縮在單一水平視窗內，必須具備明確的方向性操作線索（左右箭頭與導航圓點）。
- **分頁控制 (Pagination, TW7.7)**：
  - 將海量資料切分為可控批次，避免單頁記憶體爆量與無限捲動疲勞。

</div>

## Tidwell 設計模式核心準則：從模式邁向直覺體驗

> **工程師必備心態：** 掌握模式不是為了生搬硬套，而是為了在系統架構中為人類認知弱點築起安全防護網。

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 1. 三大核心設計承諾 (The 3 Mandates)
- **建立親近感 (Build Familiarity)**：
  - 善用習慣化 (Habituation) 與通用慣例，讓使用者首次進入系統便能無師自通。
- **降低認知負荷 (Reduce Cognitive Load)**：
  - 以漸進式揭露、分部精靈與空間記憶，讓畫面在任何瞬間都只呈現關鍵資訊。
- **賦權使用者 (Empower the User)**：
  - 永遠提供逃生出口 (Escape Hatch)、撤銷復原 (Undo) 與多維檢視，讓使用者擁有絕對掌控權。

## 設計師專屬的結構化提示詞框架：RTCF

為了從 AI 模型獲取精確、具備專業水準的 UX 產出，務必杜絕模糊指令（❌ *「幫我設計一個登入頁」*），採用嚴謹的 **RTCF 提示詞工程框架**：

* **R — Role (角色定位)：**
  - 明確定義 AI 的專家身分（例如：*「你是一位專精於 WCAG 2.1 AA 無障礙標準的資深 UX 研究員」*）。
* **T — Task (具體任務)：**
  - 清楚界定要達成的具體目標（例如：*「請對這張手機結帳線框圖進行易用性啟發式評估」*）。
* **C — Constraints (邊界約束)：**
  - 注入領域規則與規格限制（例如：*「嚴格依照尼爾森原則 NS01、NS03 與 NS05 進行評估；針對 375px 寬度手機螢幕」*）。
* **F — Format (輸出格式)：**
  - 指定結構化表格（例如：*「請輸出為四欄 Markdown 表格：[原則編號, 觀察問題, 嚴重程度 (0-4), 具體重構建議]」*）。

# **6.5 為 AI 打造卓越體驗：UX for AI (UX4AI)**

<!--
我們現在進入 6.5 節：UX for AI（UX4AI）。

## AI 原生產品獨特的 UX 挑戰

* **1. 非確定性與不可預測性 (Non-Determinism)：**
  - 傳統軟體：輸入 `2 + 2` 永遠精確回傳 `4`。
  - AI 系統：即便輸入完全相同的提示詞，每次生成的措辭、語氣或程式碼結構皆可能完全不同。
* **2. 「模型幻覺 (Hallucination)」的兩難：**
  - 生成式模型具備用極度自信的語氣，憑空捏造出虛構事實、不存在的函式庫或假文獻的傾向。
* **3. 推論延遲與「思考黑盒子」：**
  - 具備深度推論能力的模型（如 o1、Gemini Thinking）在輸出第一個字前，需要 5 到 30 秒的計算時間。
* **4. 信任度的校準 (Calibration of Trust)：**
  - **過度盲信 (Over-trust)：** 使用者不加審查便直接部署 AI 程式碼，引發正式環境重大當機。
  - **過度懷疑 (Under-trust)：** 使用者因 AI 犯了一次小錯便徹底棄用，喪失所有生產力紅利。

<!--

## AI + NS02 & NS03: 地面錨定、控制與人類自主權

* **AI + NS02 (符合真實世界 / 身份透明)：**
  - **坦白機器人身份：** 明確宣告自身為 AI 輔助系統，絕不使用欺騙性的偽人類語氣偽裝真人。
  - **對話脈絡錨定：** 遵循自然語言輪替習慣，與使用者建立共享上下文。
* **AI + NS03 (使用者控制與自由度 / 人類自主權)：**
  - **即時停止生成按鈕 (Stop Generation)：** 當 AI 回覆偏離軌道或開始無限跳針時，提供一鍵即時中斷機制。
  - **提示詞編輯與分支對話 (Prompt Branching)：** 允許使用者隨時回頭編輯上一句話，分支出全新對話樹。
  - **輸出操控拉桿：** 提供溫度（隨機性）、回答長度與語氣風格的即時調整控制項。

## AI + NS05: 防錯機制與代理人防護圍欄 (Guardrails)

* **自主代理人 (Agentic AI) 帶來的極限風險：**
  - 具備系統權限的自主代理人能自行執行終端機指令、修改本機專案程式碼與存取遠端資料庫。
  - 一旦產生幻覺，可能誤刪整個專案目錄、清空資料表或洩漏 API 密鑰。
* **人機協同 (HITL) 關鍵防護圍欄：**
  - **執行前強制確認 (Pre-Execution Confirmation)：** 涉及終端機指令或檔案修改的高風險動作，必須強制彈窗等候人類工程師點擊「確認執行」。
  - **Diff 差異視覺化預覽：** 以類似 Git 的綠紅顏色清楚標示 AI 企圖新增與刪除的程式碼行數。
  - **沙盒安全隔離執行 (Sandboxed Execution)：** 未經驗證的代碼先在隔離容器內試跑，確認安全無虞後才套用至本機。

<!--
在自主代理人時代，防錯原則（NS05）關乎系統的生死存亡。

因此必須設置嚴密的人機協同防護圍欄：高風險操作必須強制暫停，展示 Git Diff 差異預覽，等待人類工程師點擊確認才准放行。

💡 難字與專業術語解說：
- agentic guardrail: 代理型 AI 安全護欄（限制自主 AI 代理執行高風險操作、確保人類保有最終控制權的防呆機制）
- state-mutating action: 狀態變更操作（會修改外部資料庫、檔案系統或發送真實外部通訊的不可逆動作）
- diff preview: 差異比對預覽（以紅綠顏色標示刪除與新增內容，讓使用者在套用前清楚審視 AI 修改細節的視圖）
- sandboxed execution: 沙箱隔離執行（在受限的虛擬環境中先測試執行 AI 生成的程式碼，防止破壞主系統）

## 執行正式專家啟發式評估 (Heuristic Evaluation)

* **什麼是啟發式評估？**
  - 由獨立評估者對照既定的易用性原則（如尼爾森十大原則），對介面進行逐頁檢查的折扣式易用性檢驗方法。
* **尼爾森 5 級易用性缺陷嚴重度量表 (Severity Rating Scale)：**
  - **0 級 = 不是問題 (Not a problem)：** 評估者個人的純主觀偏好，不影響任何使用者操作。
  - **1 級 = 僅表面外觀瑕疵 (Cosmetic problem)：** 微小的視覺排版瑕疵，僅在有多餘時間時才修復。
  - **2 級 = 輕微易用性問題 (Minor usability problem)：** 造成輕微不便，但使用者能自行摸索解決；修復優先級較低。
  - **3 級 = 重大易用性問題 (Major usability problem)：** 造成嚴重延遲或混淆，高優先級；產品發布前必須修復。
  - **4 級 = 易用性災難 (Usability catastrophe)：** 徹底阻斷任務進行，使用者無法完成目標；**修復前產品絕對禁止上線發布！**

## 專家啟發式評估 vs. 真人使用者測試

| 評估維度 | 專家啟發式評估 (Heuristic Evaluation) | 真人使用者測試 (Empirical User Testing) |
| :--- | :--- | :--- |
| **評估人員** | 3 到 5 位 UX 專家 / 資深軟體工程師 | 5 位真實代表性目標終端使用者 |
| **適用時機** | 專案早期 (線框圖 Wireframes、早期原型) | 專案中後期 (具備互動功能之原型、測試環境) |
| **時間與成本** | 極為極速 (1–2 天內完成)；成本低廉 | 較耗時 (1–2 週)；需招募受測者與實驗室環境 |
| **核心優勢** | 能極速掃除明顯原則違規與極端邊界問題 | 揭露真實人類行為中的意想不到摩擦與驚喜 |
| **本質局限** | 專家有時難以預測深層領域特殊習慣 | 使用者能告訴你哪裡卡住，但不一定知道怎麼修 |

      el.style.opacity = '1';

      if (timer) clearTimeout(timer);
      timer = setTimeout(clearInput, 2800);
    }

    function clearInput() {
      inputBuffer = '';
      if (timer) {
        clearTimeout(timer);
        timer = null;
      }
      if (hud) {
        hud.style.opacity = '0';
        setTimeout(() => {
          if (inputBuffer === '' && hud) hud.style.display = 'none';
        }, 150);
      }
    }

    function jumpToSlide(num) {
      const total = getTotalSlides();
      const target = Math.max(1, Math.min(num, total));
      const targetHash = '#' + target;
      
      // Visual flash confirmation
      const el = getOrCreateHud();
      const confirmedMsg = isEn ? ('✓ Slide ' + target) : ('✓ 第 ' + target + ' 頁');
      el.innerHTML = '<span style="color: #34d399; font-weight: 700; font-size: 15px;">' + confirmedMsg + '</span>';
      el.style.display = 'flex';
      el.style.opacity = '1';
      setTimeout(clearInput, 500);

      if (window.location.hash === targetHash) {
        window.dispatchEvent(new HashChangeEvent('hashchange'));
      } else {
        window.location.hash = targetHash;
      }
    }

    window.addEventListener('keydown', function(e) {
      // Don't intercept when focusing editable form elements
      const active = document.activeElement;
      if (active && (active.tagName === 'INPUT' || active.tagName === 'TEXTAREA' || active.tagName === 'SELECT' || active.isContentEditable)) {
        return;
      }

      // Ignore if modifier keys are pressed
      if (e.ctrlKey || e.altKey || e.metaKey) {
        return;
      }

      // Resolve digit from key or code (supports '2', 'Digit2', 'Numpad2')
      let digit = null;
      if (e.key >= '0' && e.key <= '9') {
        digit = e.key;
      } else if (/^(?:Digit|Numpad)([0-9])$/.test(e.key)) {
        digit = e.key.replace(/^(?:Digit|Numpad)/, '');
      } else if (/^(?:Digit|Numpad)([0-9])$/.test(e.code || '')) {
        digit = (e.code || '').replace(/^(?:Digit|Numpad)/, '');
      }

      if (digit !== null) {
        inputBuffer += digit;
        if (inputBuffer.length > 4) inputBuffer = inputBuffer.slice(-4);
        showHud();
        return;
      }

      // Backspace
      if ((e.key === 'Backspace' || e.code === 'Backspace') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        inputBuffer = inputBuffer.slice(0, -1);
        if (inputBuffer.length === 0) {
          clearInput();
        } else {
          showHud();
        }
        return;
      }

      // Escape
      if ((e.key === 'Escape' || e.code === 'Escape') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        clearInput();
        return;
      }

      // Enter key confirms numeric jump
      if ((e.key === 'Enter' || e.code === 'Enter' || e.code === 'NumpadEnter') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        const targetPage = parseInt(inputBuffer, 10);
        if (!isNaN(targetPage)) {
          jumpToSlide(targetPage);
        } else {
          clearInput();
        }
      }
    }, true);
  }


  // =========================================================================
  // 3. Split73 / Split64 Image In-Place Hover Zoom
  // =========================================================================
  function initSplitImageHoverZoom() {
    function updateInPlaceScale(img) {
      const isSplit73 = !!img.closest('div.split73');
      const baseScale = isSplit73 ? 1.52 : 1.38;
      const h = img.offsetHeight || 360;
      const maxAllowedScale = Math.max(1.22, Math.min(baseScale, 640 / h));
      img.style.setProperty('--split-zoom-scale', maxAllowedScale.toFixed(2));
    }

    const targets = document.querySelectorAll('div.split73 img:not(.emoji), div.split64 img:not(.emoji)');
    targets.forEach(img => {
      if (img.dataset.splitZoomBound) return;
      img.dataset.splitZoomBound = 'true';
      img.addEventListener('mouseenter', function() {
        updateInPlaceScale(img);
      });
    });

    const origBadges = document.querySelectorAll('.orig-ui-hover[data-orig-src]');
    origBadges.forEach(badge => {
      if (badge.dataset.origZoomBound) return;
      badge.dataset.origZoomBound = 'true';
      badge.addEventListener('mouseenter', function() {
        const split = badge.closest('div.split64, div.split73');
        if (!split) return;
        const rightImg = split.querySelector('div.right img:not(.emoji)');
        if (!rightImg) return;
        if (!rightImg.dataset.annotatedSrc) {
          rightImg.dataset.annotatedSrc = rightImg.getAttribute('src');
        }
        rightImg.setAttribute('src', badge.dataset.origSrc);
        updateInPlaceScale(rightImg);
        rightImg.classList.add('is-inplace-zoomed');
      });
      badge.addEventListener('mouseleave', function() {
        const split = badge.closest('div.split64, div.split73');
        if (!split) return;
        const rightImg = split.querySelector('div.right img:not(.emoji)');
        if (!rightImg) return;
        rightImg.classList.remove('is-inplace-zoomed');
        if (rightImg.dataset.annotatedSrc) {
          rightImg.setAttribute('src', rightImg.dataset.annotatedSrc);
        }
      });
    });
  }

  // Initialize all features
  function init() {
    initHeaderDropdown();
    initNumberQuickJump();
    initSplitImageHoverZoom();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', init);
  } else {
    init();
  }
  setTimeout(init, 400);
})();
