## 本章核心思考問題 (Focus Questions)

* **1. 計畫 vs. 調適的根本權衡：**
  - 在何種情況下，我們應該優先採用嚴格的「計畫驅動 (Plan-Driven)」流程？又在何種情境下，「敏捷調適 (Agile Adaptive)」是唯一生路？
* **2. 交付速度的真正內涵：**
  - 「快速上線」與「系統品質」真的是不可調和的矛盾嗎？軟體團隊如何在不欠下毀滅性「技術債」的前提下維持極速交付？
* **3. 極限技術紀律的威力：**
  - 為什麼純粹的管理框架（如 Scrum）若缺乏卓越的工程實踐（如 TDD 與重構），往往會淪為低效甚至災難性的「疲軟 Scrum」？
* **4. AI 時代的流程重塑：**
  - 當生成式 AI 與自主代理能以秒級速度生成數千行程式碼時，人類工程師的價值與流程管控如何轉型為「安全帶工程學 (Harness Engineering)」？

## 軟體開發流程與流程模型 (Process & Process Models)

* **何謂「軟體流程 (Software Process)」？**
  - 為了**開發、演進並維護**一套軟體系統，所執行的一系列具備結構化的**活動 (Activities)、方法 (Methods)、實踐 (Practices) 與轉換 (Transformations)**。
* **何謂「流程模型 (Process Model)」？**
  - 對軟體流程的高度抽象化表現（簡化藍圖）。
  - 它定義了：**應該產出哪些工件 (Artifacts)？由誰負責 (Roles)？遵循何種先後順序 (Phases)？以及何時進行驗證？**
* **流程模型的核心價值：**
  - **降低複雜度與混亂：** 為團隊協同提供共同語言與可預期的節奏。
  - **品質保證機制：** 確保測試與代碼審查並非「事後補救」，而是流程中不可或缺的守門員。
  - **可重複性與持續改進：** 唯有具備流程，團隊才能度量效能並進行科學化調優。

<!--
請大家看這兩個核心定義。

總結這張投影片，請記住這個核心觀念：流程模型是軟體工程提供可預測性、可重複性與品質保證的架構骨幹。

## 通用流程活動：軟體生命週期四大支柱

不論採用何種流程模型（瀑布、Scrum 還是 AI 驅動），所有軟體工程流程都**必然包含四大核心活動**：

* **1. 軟體規格說明 (Software Specification · 需求工程)：**
  - 明確界定軟體「必須做什麼 (What)」以及其運行的約束條件與品質標準。
* **2. 軟體設計與實作 (Software Design & Implementation)：**
  - 確立系統架構組織，並將其轉換為可運行的可執行程式碼與資料庫結構。
* **3. 軟體驗證與確認 (Software Validation & Verification)：**
  - 驗證軟體是否符合其規格說明，並確認軟體是否真正滿足客戶的真實商業期望。
* **4. 軟體演化 (Software Evolution · 系統維護)：**
  - 依據市場變更、使用者回饋與技術棧演進，持續修改並升級既有軟體。

> **核心洞見：** 活動本身不依賴特定時序。**各流程模型的根本差異，在於這四大活動發生的「時機」與「頻率」！**

<!--
請大家特別注意這四大通用活動：規格說明、設計與實作、驗證確認、系統演化。

這四大活動是軟體工程的物理定律，任何專案都逃不開。

瀑布模型主張將這四件事嚴格按順序切分，每個階段耗時數月；而敏捷模型則主張將這四件事濃縮在兩週的衝刺中，甚至在一天之內反覆循環數十次！

模型的差異不在於「做不做這四件事」，而在於「何時做、做多快、以何種頻率回饋」。

總結這張投影片，請記住這個核心觀念：四大核心活動是軟體工程不變的物理骨架，所有流程模型的本質差異僅在於活動編排的時機與頻率。
-->

### 計畫驅動範式 (Plan-Driven)
* **哲學：** 變更成本高昂，必須「前期防範於未然 (Upfront Planning)」。
* **代表模型：**
  - **瀑布模型 (Waterfall):** 嚴格線性序列，重視階段里程碑與正式簽核。
  - **V-模型 (V-Model):** 強化測試左移與雙向追溯性（航太、醫療、車載標準）。

### 調適/敏捷範式 (Adaptive / Agile)
* **哲學：** 變更不可避免，必須「透過快速回饋持續調適 (Empirical Feedback)」。
* **代表模型：**
  - **增量與疊代 (Incremental & Iterative):** 漸進精煉與垂直功能切片。
  - **Scrum & 看板 (Kanban):** 時間盒衝刺律動 vs. 連續流動拉動系統。
  - **極限編程 (XP):** 卓越代碼技術紀律（TDD、結對編程、重構）。
  - **DevOps & AI 規格驅動:** CI/CD 自動化管道與 AI 代理工程安全帶。

## 計畫驅動範式 — 瀑布模型與 V-模型 (Plan-Driven Paradigms)

* **計畫驅動 (Plan-Driven) 的核心哲學：**
  - 開發流程的所有活動都依循**預先詳盡制定的計畫**進行。
  - 主張在撰寫任何實作程式碼之前，**完整凍結並定義所有需求與系統架構**。
* **里程碑式的進度管理 (Milestone-Driven)：**
  - 每個階段的結束都必須產出受正式版本控制的**文檔工件 (Formal Documents)**。
  - 必須經過利害關係人與品質團隊的正式評審與簽核 (Sign-off) 方能進入下一階段。
* **適用範疇的決定性特徵：**
  - 系統需求**明確、穩定且具備強大法規限制**（如 FDA 醫療器材認證、DO-178C 航空電子）。
  - 系統架構變更成本極高，且外部合約嚴格鎖定交付規格。

<!--
請理解計畫驅動的核心邏輯：它假設人類能夠在專案開始前，將所有需求預先想得一清二楚。

在這種模型中，專案推進依賴正式的文檔簽核。需求規格書簽字了，才能做系統設計；架構文檔審查通過了，才能寫代碼。

總結這張投影片，請記住這個核心觀念：計畫驅動以預先分析對抗後期變更，是法規合規與安全關鍵領域的重要基石。

## 瀑布模型：五大線性序列階段

<div class="content-columns">
<div class="content-text">

* **歷史淵源：**
  - 由 **Winston W. Royce (1970)** 在《*Managing the Development of Large Software Systems*》中首次提出。
  - *歷史反諷：* 原文是用來指出這種單向線性流程充滿極高風險且容易招致失敗，主張必須加入疊代回饋；但業界卻誤將其簡化為單向推進的聖經！
* **五大嚴格序列推進階段：**
  1. **需求分析與定義 (Requirements Definition)：** 完整凍結使用者需求與功能規格。
  2. **系統與軟體設計 (System & Software Design)：** 建立硬體、軟體與資料架構。
  3. **實作與單元測試 (Implementation & Unit Testing)：** 將設計轉換為程式碼並驗證單一模組。
  4. **整合與系統測試 (Integration & System Testing)：** 組裝全模組驗證系統功能。
  5. **維運與維護 (Operation & Maintenance)：** 線上佈署、缺陷修復與長期維護。

第三階段是實作與單元測試：工程師撰寫原始碼，並針對個別模組進行單元測試驗證。

第四階段是整合與系統測試：將所有模組整合組裝，驗證整套系統是否符合當初的需求規格。

第五階段是維運與維護：系統正式上線佈署，並進行長期的缺陷修復與功能維護。

瀑布模型的核心規則在於「嚴格的階段閘門」：前一階段未經正式簽核前，絕不允許進入下一階段。

總結這張投影片，請記住這個核心觀念：瀑布模型將開發切分為嚴格的序列階段，並依賴正式里程碑簽核來推進。

### 最佳適用情境 (When to Use)
* **需求高度穩定且清晰：** 幾乎不可能在開發期間發生變更的成熟領域。

* **「巨石延遲交付」陷阱：** 客戶直到最後一刻才看到軟體，早期毫無實體可用回饋。
* **對變更極度脆弱：** 開發後期變更需求代價高昂，極易引發災難性延期。
* **「大爆炸式」整合地獄：** 模組各自為政開發數月，在最後測試階段爆發無數隱蔽接口衝突。

## 實務常見問題：瀑布模型真的死透了嗎？

* **Q1：現在業界還有人在用純瀑布模型嗎？**
  - **有，但僅限特定極端領域：** 鐵路號誌連鎖系統、核能電廠控制、人體植入式醫療晶片。在這些「不能承受一次當機」的場景中，瀑布模型搭配形式化方法 (Formal Methods) 仍是工業標準。
* **Q2：為什麼一般商務軟體全面揚棄純瀑布？**
  - 因為真實世界的「需求永遠在變動」！使用者往往「看到可以動的軟體之前，根本不知道自己真正要什麼」。瀑布模型假設需求能完美預測，違背了人類認知的基本規律。
* **Q3：瀑布模型留給現代軟體工程最重要的遺產是什麼？**
  - **結構化分析與架構思維：** 即使是現代最敏捷的團隊，在動工前依然需要清晰的架構概念與介面邊界思考，絕非盲目「隨性邊寫邊猜 (Vibe Coding)」。

## V-模型：前瞻性驗證與確認 (Proactive V&V)

* **V-模型的誕生目的：**
  - 改善傳統瀑布模型「只重設計、測試延後到最後」的致命弱點。
  - 將開發階段與對應的**測試驗證階段建立一一對應的對稱架構**。
* **V-模型的兩大靈魂維度：**
  - **左翼（分解與向下細化）：** 需求定義 → 系統設計 → 架構設計 → 模組實作。
  - **右翼（整合與向上組裝）：** 單元測試 → 整合測試 → 系統測試 → 驗收測試。
* **核心工程思維：**
  - **測試計畫左移：** 寫需求規格的當下，就同步設計驗收測試用例！
  - **雙向追溯性 (Traceability)：** 每一個測試用例都能追溯回特定需求條款；每一項需求都有對應的測試驗證機制。

<!--

## V-模型的架構：追溯性與測試層級

```
[使用者需求 User Requirements]  <-------- 驗收測試 (Acceptance Testing) --------> [客戶驗收驗證]
       |                                                                               ^
[系統規格 System Requirements]  <-------- 系統測試 (System Testing) ------------> [端到端系統整合]
       |                                                                               ^
[架構設計 Architecture Design]  <-------- 整合測試 (Integration Testing) -------> [模組子系統組裝]
       |                                                                               ^
[模組詳細設計 Detailed Design]   <-------- 單元測試 (Unit Testing) --------------> [個別函式模組]
       \                                                                               /
        --------------------------> [程式碼建構 Coding] --------------------------------
```

* **水平對應關聯：** 每個左側階段產出具體的「設計規格」以及對應右側的「測試計畫與用例」。
* **嚴格的品質把關閘門：** 低階單元測試未通過前，絕不允許進入高階整合測試，避免缺陷骨牌式擴散。

<!--
請看螢幕上這張水平對齊圖。

系統規格對應全系統的端到端系統測試：驗證效能、安全與邊界吞吐量。

架構設計對應整合測試：驗證各微服務與模組之間的 API 介面是否正確連通。

最底層的模組詳細設計，則由工程師撰寫單元測試守護。

這種分層清晰的對應關係，讓團隊能精準定位問題：當整合測試失敗時，我們知道是介面架構有誤，而不是去無頭蒼蠅般修改業務邏輯。

總結這張投影片，請記住這個核心觀念：V-模型將測試分級與設計階層嚴格綁定，建立了從單元到驗收的立體防禦體系。

## V-模型的優勢、限制與適用領域

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 核心優勢與適用領域 (Strengths)
* **極致嚴密的品質保證：** 大幅降低漏網之魚的逃逸缺陷率 (Defect Escape Rate)。
* **法規合規與審計驗證：** 航太 (DO-178C)、汽車電子 (ISO 26262)、醫療器材 (IEC 62304) 的法定標竿。

### 本質限制與代價 (Limitations)
* **依然具備線性僵化本質：** 本質上仍是計畫驅動，一旦前期需求發生根本性變動，回溯重做的代價極其驚人。

## 變革的機制 — 增量與疊代開發 (Incremental & Iterative Development)

傳統瀑布模型的最大痛點是「全部押在最後的大爆炸交付 (Big Bang Delivery)」。為了解決這個困境，軟體工程引入了兩大核心演進策略：

* **增量策略 (Incremental Strategy · 數量上的累加)：**
  - **理念：** 「將系統拆解為若干個功能切片，每次交付其中一部分完整的可運行功能。」
  - **關鍵特徵：** 每個增量都包含端到端的垂直功能（例如：先做購物車，再做金流，再做評論）。
* **疊代策略 (Iterative Strategy · 品質與精準度上的演化)：**
  - **理念：** 「先交付一個粗糙的全局系統，隨後在一次次的循環中逐步精煉品質與細節。」
  - **關鍵特徵：** 每次循環都涵蓋全系統，但每一次都比前一次更精確、更強固（雕刻家手法）。

<!--

總結這張投影片，請記住這個核心觀念：增量策略分批交付功能模組，疊代策略逐層深化系統品質。

## 增量交付：垂直功能切片與價值分期

* **增量開發的核心架構原則：**
  - **垂直切片 (Vertical Slicing)，而非水平分層 (Horizontal Slicing)：**
    - **[反模式] 錯誤的水平切片：** 增量 1 做完所有資料庫綱要；增量 2 做完所有 API；增量 3 做前端畫面。*(使用者到最後一天前都看不到任何東西！)*
    - **[最佳實踐] 正確的垂直切片：** 增量 1 包含單一功能的 UI + API + DB（如：「使用者能註冊登入」）；這是一個完整可獨立驗證的價值切片！
* **增量交付帶來的巨大優勢：**
  - **早期商業回報 (Early ROI)：** 核心功能提早數個月投入市場營運，創造營收。
  - **降低專案總體崩盤風險：** 即使後續預算腰斬，已交付的增量依然具備獨立運行價值。
  - **最重要的優先級保護：** 最關鍵、最高風險的功能必然被安排在增量 1，及早暴露瓶頸。

<!--

真正的增量交付要求「垂直切穿」：UI 介面、商業邏輯、資料存取，全部打通！哪怕這個增量只能讓使用者做一件事——「註冊帳號」，它也是一個可以在真實環境運行的完整切片。

總結這張投影片，請記住這個核心觀念：真正的增量交付必須採取垂直切片，確保每個交付物都具備端到端的獨立驗證價值。

## 疊代開發與雕刻家隱喻 (The Sculptor Analogy)

* **雕刻家的隱喻 (The Sculptor Analogy · Jeff Patton)：**
  - 想像一位雕刻大師要雕塑一尊大衛像：
    - 他**絕不是**先雕刻出完工度 100% 的大拇指，再雕刻手腕，再雕刻手臂！
    - 他首先鑿出大衛的大致人形輪廓（低精細度但具備全局視野）；接著修飾身軀比例；隨後精雕肌肉紋理；最後拋光面部神情。
* **疊代開發在軟體中的具體實踐：**
  - **第 1 次疊代（粗胚原型）：** 文字終端介面或粗糙 Mock 畫面，驗證核心演算法與資料庫關聯邏輯是否正確。
  - **第 2 次疊代（可用版本）：** 補齊基礎 UI 與主要正常流程 (Happy Path)，進行初步可用性測試。
  - **第 3 次疊代（生產就緒）：** 強化極端異常防護、效能調優、無障礙支援與安全性加固。

<!--
請牢記這個生動的隱喻：雕刻家手法。

軟體開發也是如此。我們應該先讓系統以最粗糙的形式「端到端跑通」，驗證資料流與核心演算法；接著逐步改善架構、提升效能、加固安全性。

總結這張投影片，請記住這個核心觀念：疊代精煉拒絕局部的過早優化，堅持先求全局走通、再求精益求精。

## 結合模型 (增量 + 疊代) 與最小可行產品 (MVP)

> 在真實世界的敏捷工程中，我們極少單獨使用純增量或純疊代。我們將兩者**深度結合**，打造**最小可行產品 (Minimum Viable Product · MVP)**。

* **何謂最小可行產品 (MVP)？**
  - Eric Ries《*精實創業 (The Lean Startup)*》定義：*「能讓團隊以最小心力，換取對客戶最大化『經過驗證的學習 (Validated Learning)』之產品版本。」*
* **增量與疊代的強大加乘綜效：**
  - **版本間進行疊代深化：** 每次發布都覆蓋端到端價值，從粗胚逐步走向精緻。
  - **功能間進行增量擴充：** 當核心功能獲得市場驗證後，再橫向追加相鄰模組（註冊登入 → 購物結帳 → 推薦系統）。
* **「從滑板到汽車」的經典隱喻 (Henrik Kniberg)：**
  - *不是：* 零件孤島組裝（輪胎 → 底盤 → 車殼 → 汽車）。
  - *而是：* 交通工具能力漸進（滑板 → 滑板車 → 腳踏車 → 摩托車 → 汽車）。
  - **在每一步驟中，客戶都能真正代步出行！**

## 增量能單獨套用嗎？外送平台實戰案例

許多初學者常困惑：「如果我只做增量、不做疊代，行得通嗎？」讓我們用外送平台 (UberEats / Foodpanda) 來剖析：

* **純增量模式（無疊代精煉）：**
  - **第 1 個月：** 交付完工度 100% 的使用者帳號密碼註冊系統（包含兩步驟驗證、頭像上傳、社群綁定）。
  - **結果：** 使用者可以完美註冊帳號，但**無法看菜單、無法訂餐、無法付錢！** 商業價值為 0。
* **結合模式 (MVP 增量 + 疊代)：**
  - **第 1 個月 MVP：**
    - 帳號系統採最簡版（只要輸入手機號碼發簡訊驗證碼）。
    - 菜單系統採純靜態圖片清單。
    - 金流系統直接採貨到付款現金結帳。
  - **結果：** 系統雖然粗糙，但**上線第一天就能開始接單外送、創造現金流！** 隨後再依營運數據逐步疊代進化。

## 思維轉變 — 敏捷哲學 (The Mindset Shift)

> 敏捷**絕不是**一套繁文縟節的官僚規範、一個 Jira 追蹤看板，或是一堆開不完的站立會議。敏捷是一種統攝全局的**文化思維與價值體系**：它將**人、可運行的軟體、客戶協同與變革適應力**，置於僵化計畫之上。

* **歷史背景：1990 年代的軟體危機再現：**
  - 重型計畫驅動流程導致大量專案災難性崩潰（Standish Group 著名的混沌報告：逾 70% 專案延期、超支甚至取消）。
  - 商業世界進入網際網路時代，需求每週都在變更，六個月的規格凍結期注定讓產品「上線即落後」。
* **雪鳥會議的歷史歷史創舉 (2001 年 2 月)：**
  - 17 位軟體先驅（包含 Kent Beck, Ward Cunningham, Martin Fowler, Jeff Sutherland, Ken Schwaber 等人）於美國猶他州雪鳥召開會議。
  - 正式誕生了著名的**《敏捷軟體開發宣言 (Agile Manifesto)》**。

## 敏捷宣言：四大核心價值 (The 4 Core Values)

2001 年《敏捷宣言》確立了四對關鍵的價值取向：

1. **個人與互動 (Individuals and interactions)**  
 → 重於 **流程與工具 (processes and tools)**
2. **可運行的軟體 (Working software)**  
 → 重於 **詳盡的文檔 (comprehensive documentation)**
3. **客戶協同合作 (Customer collaboration)**  
 → 重於 **合約協商 (contract negotiation)**
4. **回應變更 (Responding to change)**  
 → 重於 **遵循計畫 (following a plan)**

> *「也就是說，儘管右項各具其價值，但我們更重視左項的價值。」*

<!--

敏捷團隊依然需要工具，但人的溝通效率高於工具；
敏捷團隊依然需要文檔，但代碼能正常運行才是最高真理；

敏捷團隊依然需要計畫，但當現實與計畫衝突時，擁抱變更才是正道。

總結這張投影片，請記住這個核心觀念：敏捷宣言不是否定流程與文檔，而是在價值衝突時堅定選擇以人、代碼與適應力為先。

### 原則 1 – 6：客戶價值與團隊協同
* **1. 早期且持續交付：** 最高優先是透過提早且持續交付有價值的軟體來滿足客戶。

* **5. 激勵並信任團隊：** 圍繞具備積極動力的個人建構專案，給予環境與支援並給予充分信任。

* **7. 可運行軟體是進度的主要度量：** 衡量專案進度的唯一真實標準是可運行的軟體。

## 敏捷專案管理 — Scrum 與看板 (Agile Project Management)

> 敏捷專案管理框架的核心目的，在於組織團隊協同、確立交付節奏與視覺化追蹤進度。它們規範了**「工作如何被協調」**，但刻意對「程式碼如何被具體實作」保持沉默。

* **兩大主流框架的宏觀對照：**
  - **Scrum 框架（時間盒律動模式）：**
    - 採用固定時長（通常為 1 至 4 週）的**衝刺 (Sprint)**。
    - 衝刺期間**凍結範疇**，團隊專注於交付承諾的「潛在可發布增量」。
  - **看板框架（連續流動拉動模式）：**
    - **不設定固定衝刺週期**，工作以連續流動 (Continuous Flow) 的方式推進。
    - 透過嚴格限制**「在製品數量 (WIP Limit)」**，將瓶頸無所遁形地暴露出來。

<!--

Scrum 靠「時間盒」推進：兩週一輪，衝刺開始時承諾範疇，衝刺結束時驗收成果。

總結這張投影片，請記住這個核心觀念：Scrum 以固定時間盒創造節奏，看板以連續拉動流與 WIP 限制優化吞吐量。

## Scrum 框架：核心角色、工件與完成定義

* **三大神聖角色 (The 3 Roles)：**
  - **產品負責人 (Product Owner · PO)：** 決定「做什麼 (What)」，最大化產品商業價值，全權維護產品待辦清單的優先級。
  - **Scrum 專家 (Scrum Master · SM)：** 流程守護者與僕人式領導者，掃除團隊推進障礙，保護團隊不受外部干擾。
  - **開發團隊 (Developers)：** 決定「怎麼做 (How)」，跨職能且自我組織，共同為增量品質負責。
* **三大核心工件 (The 3 Artifacts)：**
  - **產品待辦清單 (Product Backlog)：** 依商業價值排序的全局功能需求清單。
  - **衝刺待辦清單 (Sprint Backlog)：** 本次衝刺承諾完成的任務子集與實作計畫。
  - **產品增量 (Increment)：** 衝刺結束時產出且**符合「完成定義 (DoD)」**的可用軟體。

<!--
Scrum 的結構非常嚴謹，由三三四構成：三種角色、三個工件、四大儀式。

三種角色各司其職：PO 管商業價值，SM 管流程順暢與排除障礙，開發團隊管技術實作。

請特別注意「完成定義 (Definition of Done，簡稱 DoD)」：它不是「我寫完代碼了」，而是包含單元測試全過、代碼審查通過、自動化 CI 構建成功、整合環境驗證完畢。唯有滿足 DoD，才能被稱為真正的產品增量。

總結這張投影片，請記住這個核心觀念：Scrum 透過角色權責制衡與嚴格的完成定義，確保每次衝刺產出的都是具備生產品質的可用軟體。

## Scrum 四大儀式與衝刺律動節奏

* **1. 衝刺規劃會議 (Sprint Planning · 衝刺第 1 天)：**
  - PO 說明價值目標；開發團隊評估工作量，共同承諾本次衝刺待辦清單。
* **2. 每日站立會議 (Daily Scrum · 每天 15 分鐘)：**
  - 開發團隊聚焦當日目標，回答三問題：*昨天做了什麼？今天打算做什麼？遇到什麼阻礙？*
* **3. 衝刺審查會議 (Sprint Review · 衝刺最後一天)：**
  - **對外成果展示：** 邀請利害關係人與客戶實際操作可運行的軟體增量，蒐集真實回饋。
* **4. 衝刺回顧會議 (Sprint Retrospective · 衝刺最末尾)：**
  - **對內流程自我檢討：** 團隊內部坦誠檢視協同障礙，制定下一衝刺的**具體流程改進行動**。

<!--

總結這張投影片，請記住這個核心觀念：四大儀式是團隊的校準節奏，其中回顧會議是推動團隊持續進化與自我調適的靈魂。

## 看板框架：持續流動與拉動系統 (Pull Systems)

* **起源與哲學（源自豐田精益生產體系 Toyota Production System）：**
  - 強調**「價值流動 (Flow)」**與**「消滅浪費 (Muda)」**。
  - 將不可見的軟體工程知識工作，轉化為物理看板上清晰可見的卡片流動。
* **看板的四大核心實踐：**
  1. **工作流程視覺化 (Visualize the Workflow)：** 清晰劃分分析、開發、審查、測試與部署各個階段。
  2. **限制在製品數量 (Limit Work in Progress · WIP)：** 強制規定每個階段同時進行的工作卡片上限。
  3. **度量與管理流動 (Manage Flow)：** 追蹤週期時間 (Cycle Time) 與交付前置時間 (Lead Time)。
  4. **顯式化流程規則 (Make Policies Explicit)：** 明確界定卡片何時才能被拉入下一個欄位。

<!--

軟體開發最可怕的是「隱蔽的多工」：每位工程師手頭上同時開工三四個功能，結果沒有一個能在兩週內真正完成！

總結這張投影片，請記住這個核心觀念：看板的核心哲學在於工作視覺化與嚴格限制在製品，以平穩連續的流動消滅流程浪費。

## Scrum vs. 看板：架構維度全景對比

| 比較維度 | Scrum (時間盒衝刺模式) | 看板 Kanban (連續拉動流動模式) |
| :--- | :--- | :--- |
| **節奏機制 (Cadence)** | 固定時長衝刺（1–4 週時間盒） | 連續流動，隨時隨需交付發布 |
| **發布時機** | 衝刺結束時產出產品增量 | 任何功能只要通過測試即可隨時發布 |
| **變更規範** | 衝刺期間嚴格**凍結範疇** | 只要不超出 WIP 限制，隨時可調整待辦順序 |
| **在製品限制** | 透過衝刺待辦清單間接限制工作量 | 每個欄位強制設定明確的 **WIP 數量上限** |
| **團隊角色** | 嚴格定義三大角色 (PO, SM, Dev) | 不預設特定角色，尊重既有組織結構 |
| **度量指標** | 衝刺速率 (Velocity)、燃盡圖 | 前置時間 (Lead Time)、週期時間、累積流圖 |
| **最佳適用情境** | 產品功能研發、新創探索專案 | 運維維護 (Ops)、缺陷修復、客服支援管線 |

<!--

再看適用情境：
如果要集中兵力開發新產品核心模組，Scrum 的衝刺節奏極具凝聚力；

總結這張投影片，請記住這個核心觀念：Scrum 適合目標明確的週期性產品研發，看板適合高度動態響應的連續性維運支援。

> "Shipping first time code is like going into debt.  
> A little debt accelerates development so long as it is paid back promptly with a rewrite."  
> 「首次交付代碼就像借債。只要能及時重寫償還，適度的負債確實能加速開發。」

## 速度背後的隱形成本 — 技術債 (Technical Debt)

<div class="content-columns">
<div class="content-text">

> 在缺乏工程紀律的情況下快速交付程式碼，就如同向未來的自己**借取金融貸款**。它或許能加速今天的發布，但其累積的複利利息，終將讓未來的研發速率走向徹底破產。

* **隱喻的起源：**
  - 由敏捷宣言共同起草人、Wiki 發明者 **Ward Cunningham (1992)** 首次提出。
* **敏捷交付的核心悖論：**

  - **複利利息：** 你今天借了時間，但未來每一天都必須以脆弱代碼、回歸錯誤與研發速度崩跌來償還高額利息！

## 「疲軟 Scrum (Flaccid Scrum)」現象與軟體架構侵蝕

> 「缺乏極限編程 (XP) 技術紀律的 Scrum，就如同給跑車裝上除草機引擎：你擁有華麗的管理儀表板與站立會議，但軟體系統一遇高負載便分崩離析。」  
> — *Martin Fowler*

* **「疲軟 Scrum」的誘人幻覺：**
  - 團隊全面導入了 Scrum 的**管理儀式**（衝刺規劃、每日站立會議、燃盡圖、回顧會議）。
  - 卻徹底忽視了底層的**卓越工程實踐**（TDD、結對編程、自動化 CI/CD、持續重構）。
* **忽視技術紀律的慘痛後果：**
  - **研發速度雪崩：** 6 到 12 個月後，任何微小變更都會引發連鎖回歸錯誤，開發速度急劇歸零。
  - **英雄救火陷阱：** 整個龐大系統僅剩一兩位資深工程師敢碰那團義大利麵代碼。
  - **恐懼重構文化：** 沒有人敢修改既有代碼，深怕觸動隱蔽的強耦合地雷。

## 技術債的實證數據與真實災難事件 (Empirical Evidence & Real-World Disasters)

> 技術債絕非抽象的修辭隱喻：在全球範圍內，它吞噬了工程師 **42% 的工作時間**，更曾引發**數十億美元級別的企業運維崩潰**。

### 全球實證研究數據 (Empirical Data)
* **Stripe 開發者係數實證研究 (The Developer Coefficient)：**
  - 全球軟體工程師平均每週耗費 **42% 的工作時間** 在應付技術債、低劣代碼與維護修補！
  - 每年造成全球高達 **850 億美元** 的 GDP 生產力損失。
* **CISQ 軟體品質低劣成本報告 (2022)：**
  - 全美因既有技術債與軟體缺陷造成的經濟損失高達 **2.41 兆美元**。

### 重大案例：西南航空大崩潰 (2022)
* **系統骨牌式雪崩：**
  - 2022 年聖誕假期暴風雪引發航班調度混亂。
  - 西南航空累積數十年未償技術債的機組排班舊系統 (**SkySolver**) 在連鎖重新排班下徹底崩潰。
* **毀滅性的經營代價：**
  - **16,700 班航班取消**，數百萬旅客滯留機場。
  - 損失與罰款**逾 8 億美元**，企業商譽重挫。
  - *根本原因：* 長期忽視核心系統現代化與技術債重構。

> "Any fool can write code that a computer can understand.  
> Good programmers write code that humans can understand."  
> 「任何傻瓜都能寫出電腦能理解的代碼。  
> 優秀的工程師才能寫出人類能理解的代碼。」

總結這張投影片，請記住這個核心觀念：極限編程是抵禦技術債與維護敏捷生命力的終極工程實踐體系。

## 卓越技術紀律 — 極限編程 (Extreme Programming · XP)

<div class="content-columns">
<div class="content-text">

> 由 **Kent Beck 於 1996 年創立**，極限編程是一種專注於**程式碼紀律**、**技術卓越**與**持續重構**的敏捷流程模型——它是徹底克制與消除「技術債」的終極解藥。

* **為什麼稱為「極限 (Extreme)」？**
* Kent Beck 提出一個大膽的工程哲學：*如果一項工程實踐已被證明對軟體品質有好處，我們就應該把它推向極限，隨時隨地實踐它！*
  - *測試很好？* → 先寫測試才准寫生產代碼 (**TDD**)。
  - *代碼審查很好？* → 兩人協同隨時隨地審查 (**結對編程**)。
  - *重構很好？* → 每分每秒持續重構以維持 (**簡單設計**)。
  - *整合很好？* → 每天持續整合數十次 (**CI/CD**)。
  - *發布很好？* → 持續交付微小增量 (**小型發布**)。

## XP 實踐：測試驅動開發 (Test-Driven Development · TDD)

* **「測試先行 (Test-First)」的心智逆轉：**
  - **嚴格鐵律：** 在寫任何一行生產程式碼之前，必須先撰寫一個**必定失敗的自動化單元測試**！
  - 迫使工程師站在**呼叫者與使用者**的視角思考 API 介面與邊界合約，徹底根除過度設計。
* **紅-綠-重構循環 (The Red-Green-Refactor Cycle)：**
  1. **RED (紅燈階段)：** 撰寫一個微小的單元測試，執行並確認它必定**失敗 (編譯失敗或斷言失敗)**。*（強制思考函式介面與規格邊界）*
  2. **GREEN (綠燈階段)：** 以最快速、最直覺甚至「骯髒硬編碼」的方式撰寫最少量的程式碼，讓測試儘速**變綠燈通過**。*（追求快速驗證）*
  3. **REFACTOR (重構階段)：** 在全套測試綠燈的保護網下，**重組程式架構、消除重複、提升可讀性**，同時確保所有測試始終維持綠燈！
* **終極效益：** 產出**具備 100% 回歸防護網的整潔程式碼**，任何時刻修改代碼都有十足信心！

<!--
TDD 是軟體工程史上最強大的心智轉變。

TDD 完全顛覆了這個習慣：你連一行生產代碼都還沒寫，就必須先寫測試！

因為沒有實作代碼，測試當然會失敗（紅燈）；接著你寫最簡單的代碼讓它通過（綠燈）；然後在測試全過的保護傘下大膽重構代碼。

總結這張投影片，請記住這個核心觀念：TDD 透過紅綠重構循環將測試化為設計工具，賦予開發者無懼重構的信心。

## 持續重構與簡單設計 (Simple Design)

* **何謂「重構 (Refactoring)」？**
  - Martin Fowler 經典定義：*「在不改變軟體外部可觀察行為的前提下，改善其內部結構，使其更容易理解且修改成本更低。」*
  - 在 XP 中，重構不是一年一度的特定階段，**而是工程師每小時的自然反射動作！**
* **Kent Beck 的「簡單設計四原則 (4 Rules of Simple Design)」：**
  1. **通過所有測試 (Passes all tests):** 品質的第一底線是行為正確無誤。
  2. **表達設計意圖 (Expresses intent):** 代碼自帶文檔，命名精準清晰。
  3. **消除重複 (No duplication):** 嚴格落實 DRY 原則 (Don't Repeat Yourself)。
  4. **最小化元素 (Smallest number of elements):** 消滅過度設計的抽象類別與死代碼。

<!--
什麼是重構？請特別注意定義中的這句話：「在不改變外部行為的前提下」。

如果你在重構的同時順便加新功能，那不叫重構，那叫自找麻煩。

重構的前提是「全套綠燈的單元測試」。只有當你確信修改內部結構不會破壞既有功能時，重構才安全。

搭配 Kent Beck 的簡單設計四原則：通過測試、表達意圖、沒有重複、元素最少。這四條原則是抵擋過度設計的最佳指南針。

## 結對編程與集體代碼所有權 (Pair Programming)

* **結對編程的雙人協同機制：**
  - 兩位工程師共享同一個工作站：**駕駛員 (Driver)** 專注撰寫代碼與測試；**領航員 (Navigator)** 專注審視架構盲點、邊界條件與長期設計。
* **集體代碼所有權 (Collective Ownership)：**
  - 嚴禁單一開發者「佔地為王」私有化模組；團隊中任何成員都有權限在任何時間重構任何代碼。
* **消除知識孤島與「巴士係數 (Bus Factor)」風險：**
  - 徹底消除孤島資訊：即便關鍵工程師被巴士撞倒（或中了彩券離職），團隊依然能無縫運作，不會因為單一人員缺席而癱瘓。
* **即時連續的代碼審查 (Continuous Review)：**
  - 在代碼被提交至版本控制系統*之前*，就即時攔截邏輯漏洞、語法拼寫錯誤與架構缺陷。

## 系統架構與協同文化 — DevOps

> 一種結合文化哲學、組織架構與技術實踐的變革運動，旨在打破**開發 (Dev)** 與**維運 (Ops)** 之間的傳統壁壘，透過自動化流水線、基礎設施即程式碼 (IaC) 與生產環境遙測數據，徹底貫通軟體交付全生命週期。

* **打破「混亂之牆 (Wall of Confusion)」的利益對立：**
  - **開發團隊的激勵誘因：** 渴望持續擁抱變更、極速推出新功能與頻繁發行。
  - **維運團隊的激勵誘因：** 追求系統 100% 穩定、零當機，對任何變更充滿戒心。
* **DevOps 的核心融合思維：**
  - **左移思維 (Shift-Left)：** 將系統維運、資訊安全與部署品質前移成為開發者的共同責任。
  - **「誰建造，誰維運」(You build it, you run it)：** Amazon 技術長 Werner Vogels 提出的經典原則，消滅「將代碼拋過高牆」的推諉惡習。

## 持續整合 (Continuous Integration · CI)：打破 Dev 與 Ops 的高牆

> CI 透過以高頻率的主幹合併與全自動化品質把關閘門，取代傳統低效的人工作業，徹底瓦解了「混亂之牆」。

* **持續整合的核心工作流：**
  1. **高頻率提交代碼 (High-Frequency Commit)：** 開發者每天多次將程式碼合併至主幹分支 (Trunk/Main)。
  2. **自動化建置 (Automated Build)：** 每次 Push 觸發容器自動編譯與依賴項安裝。
  3. **自動化測試守護網 (Automated Testing)：** 自動執行全套單元測試、整合測試與靜態代碼分析 (Linter / SonarQube)。
  4. **快速失敗回饋 (Fail Fast & Fix Immediately)：** 若構建或測試失敗，流水線立即警報，團隊**最高優先立即修復**！
* **終結「整合地獄 (Integration Hell)」：**
  - 不再累積數月的龐大衝突代碼，將整合問題縮小在幾小時的微小代碼變更內解決。

總結這張投影片，請記住這個核心觀念：持續整合以高頻微小的自動化驗證消滅整合地獄，確保主幹代碼永遠維持健康可用。

## 為什麼 DevOps 需要持續交付 (CD)？

> 躺在程式碼倉庫裡的代碼**毫無任何商業價值**。持續交付 (CD) 拆除了最後一道維運屏障，讓發布軟體成為一項日常、低風險且可預測的商業決策。

* **持續交付 (Continuous Delivery) vs. 持續部署 (Continuous Deployment)：**
  - **持續交付 (Continuous Delivery)：**
    - 程式碼通過全套自動化測試與環境驗證後，**隨時具備可部署至生產環境的狀態**。
    - 是否真正發行至線上，保留由業務主管**「人工點擊按鈕審批 (Manual Approval)」**決定。
  - **持續部署 (Continuous Deployment)：**
    - **完全無人工干預的純全自動化流水線**！
    - 任何一行代碼只要通過全套自動化測試閘門，即刻由自動化腳本直接推播發布至真實生產環境！

<!--

持續交付 (Continuous Delivery)：代碼隨時準備好發布，最後一步需要人按一下按鈕。這適合需要商業時機考量的產品，例如配合行銷活動宣布。

持續部署 (Continuous Deployment)：徹底的全自動化！工程師 git push，測試全過，十分鐘後程式碼就已經在線上面向數百萬使用者運行了。GitHub、Netflix、Amazon 每天進行數千次持續部署！

總結這張投影片，請記住這個核心觀念：持續交付強調隨時具備發布能力，持續部署則實現了從代碼提交到生產環境的完全無人全自動化。

## 基礎設施即程式碼 (IaC) 與生產環境可觀測性

> 在 DevOps 中，**基礎設施本身就是軟體**：透過宣告式、受版本控制的代碼管理雲端拓撲，能徹底消滅環境漂移，實現可靠的持續交付。

<div class="two-columns">
<div class="card" data-marpit-fragment>

### 基礎設施即程式碼 (IaC)
* **當作牲口，而非寵物 (Cattle, Not Pets)：**
  - 將伺服器視為可隨時銷毀重建的不可變資產，而非精心照料的寵物。
* **宣告式環境保證：**
  - Terraform、Docker 與 Kubernetes 確保 Dev、Staging 與 Production 環境具備 100% 相同配置。
* **徹底消滅「獨角獸伺服器 (Snowflake Servers)」：**
  - 徹底終結「在我電腦上明明可以跑！」的推諉藉口。
  - 任何基礎設施變更均必須經由 Pull Request 審查與版本控制留痕。

### 生產環境可觀測性與即時回饋
* **可觀測性三大支柱 (The 3 Pillars)：**
  - **度量指標 (Metrics)：** 聚合數值遙測（CPU 使用率、API 延遲）。
  - **日誌記錄 (Logs)：** 帶有時間戳記的離散事件詳細紀錄。
  - **分散式追蹤 (Traces)：** 微服務間端到端使用者請求調用路徑。
* **閉合 DevOps 回饋迴路：**
  - 生產環境即時遙測數據能精準將線上崩潰與效能瓶頸回流至開發衝刺待辦清單中。

## AI 賦能 SDLC：軟體流程模型的典範轉移

> 在 AI 時代，軟體工程的核心不再是敲打語法代碼，而是**協調與編排整個軟體生命週期**。AI 將代碼建構的邊際成本降至接近於零，推動人類工程師的價值全力轉移至**上游 (Upstream)** 的規格定義與**下游 (Downstream)** 的嚴密驗證。

* **從「以人為本」邁向「代理人自主 (Agentic)」流程：**
  - **傳統流程模型 (瀑布 / 敏捷 / DevOps)：** 核心在於協調*人類開發者*——透過規格文件、每日站立會議、衝刺看板與同儕審查。
  - **AI 賦能流程模型：** 在持續的協同工程迴路中，協調整合**人類總建築師**、**自主 AI 代理人集群**以及**確定性自動化驗證工具**。
* **開發活動重心的戲劇性位移：**
  - **程式碼建構實作 (Coding)：** 耗時從 70% 驟降至 15%（由 AI 代理人承擔繁重的樣板代碼生成）。
  - **規格說明 (Specification)：** 耗時大幅攀升至 40%（成為定義邊界與驗收標準的核心瓶頸）。
  - **驗證確認 (Validation)：** 耗時攀升至 45%（自動化測試與架構審查成為唯一可信的護城河）。

## 實體化 AI 流程：工程安全裝備 (The Engineering Harness)

> 在敏捷中，流程紀律依賴人類儀式（站立會議、回顧、結對編程）來維持。但**自主 AI 代理人無法參加會議，也不會感到內疚**。因此，流程紀律必須被**「實體化 (Operationalized)」**為代碼化的防禦防護網——即**工程安全帶 (Engineering Harness)**。

* **何謂工程安全裝備 (Harness)？**
  - 包裹在 AI 模型外部的**確定性運作環境、沙盒、輸入導軌 (Input Rails) 與驗證管線 (Verification Pipelines)**。
* **為什麼單靠 Prompt Engineering 必然失敗？**
  - 提示詞本質是**隨機性 (Probabilistic)** 的，無法保證 100% 遵守邊界規範。
  - 唯有透過**確定性 (Deterministic)** 的編譯器、靜態分析器、單元測試與安全沙盒，才能強制確保 AI 代碼具備工業級生產可靠度。

## AI 代理人工程安全裝備 (Harness) 的三大支柱

現代 AI 規格驅動流程模型建構於三大核心安全裝備支柱之上：

* **1. 上游導軌：上下文與規格約束 (Context & Spec Rails)：**
  - **結構化輸入：** 透過系統化的專案架構文檔、API 介面合約 (OpenAPI/GraphQL Schema) 與不可突破的編程規範文件，強制收斂 AI 的推論空間。
  - **拒絕無邊界長提示：** 嚴禁丟出模糊的一句話需求，必須給予清晰的 Given-When-Then 驗收標準。
* **2. 隔離執行：沙盒化執行環境 (Execution Sandbox)：**
  - AI 代理人編寫的代碼與自動化工具呼叫，**一律在隔離的 Docker 容器或 WebAssembly 沙盒中運行**。
  - 限制檔案系統與內部網路存取權限，嚴防供應鏈投毒與惡意代碼注入。
* **3. 下游護欄：確定性驗證守門員 (Verification Gatekeepers)：**
  - **自動化反饋流水線：** 代碼生成後，自動觸發編譯器 (TSC/Cargo)、靜態分析 (ESLint) 與測試套件 (Jest/Pytest)。
  - **自動修復閉環：** 若測試失敗，日誌直接回饋給 AI 代理人要求自我修復，**人類工程師只審查最終全部綠燈的乾淨變更**。

## 代理人回饋迴路實務 (The 3-Step Agentic Loop in Practice)

在現代軟體工程開發環境（如 Google Antigravity / Cursor / Claude Code）中，規格驅動流程以三步自動化閉環持續運轉：

```
[人類架構師 Human Architect] 
       │ (1. 撰寫清晰規格說明 Specification)
       ▼
[AI 代理人編程 Agent Construction] ◄────────────────┐
       │ (2. 嘗試實作代碼與修改檔案)                     │
       ▼                                            │ (修復回饋 Loop)
[確定性驗證 Deterministic Verification]               │
       │ (執行 Linter / 單元測試 / 靜態安全掃描)          │
       ├─── [測試失敗 Fail] ──> 自動擷取錯誤日誌 ────┘
       ▼
  [測試全部通過 All Green] ──> 提交人類同儕審查 (PR Review) ──> 發布部署
```

* **人類角色的根本轉變：** 人類工程師不再花費數小時手打 CRUD 樣板程式，而是專注於**第 1 步的「規格精度」**與**最終 PR 合併前的「架構與資安把關」**。

## AI 規格驅動開發的四大黃金法則

在 AI 輔助開發的現代軟體工程中，每位工程師必須嚴格奉行四項核心鐵律：

* **1. 規格即單一真理來源 (Specifications as Single Source of Truth)：**
  - 絕不在沒有明確規格、型別定義或驗收標準的情況下要求 AI 撰寫代碼。
* **2. 確定性驗證先於代碼生成 (Deterministic Tests Precede Code)：**
  - **TDD 在 AI 時代更加關鍵！** 先由人類或嚴密規格定義出測試用例（紅燈），再命 AI 產出實作使其變綠燈。
* **3. 絕不合併無法捍衛的代碼 (Never Merge Code You Cannot Defend)：**
  - 嚴格杜絕「雖然不懂但它跑得動」的盲目合併心態。每位工程師都必須能為進入 main 分支的每一行代碼負起完全的架構與安全責任。
* **4. 維持嚴格的代理人沙盒邊界 (Maintain Strict Sandbox Boundaries)：**
  - 限制 AI 工具調用與檔案存取權限，落實最小權限原則 (Principle of Least Privilege)。

> **軟體工程師的全新角色定位：** 你不再只是代碼打字員，而是**系統總建築師 (Systems Architect)、規格撰寫者 (Specification Author) 與驗證治理官 (Verification Governor)**。

## 第二章核心觀念重點測驗 (填空檢核)

檢驗你對軟體開發流程九大模組核心觀念的掌握程度：

1. 軟體工程的四大通用核心活動分別為**軟體規格說明**、**軟體設計與實作**、**軟體驗證與確認**以及**軟體演化**。
2. 瀑布模型將開發切分為嚴格序列階段，其最致命的風險在於將可運行的軟體交付與客戶回饋延後到了整個週期的**最末端 (Big Bang)**。
3. V-模型的核心價值在於**測試左移 (Shift-Left Testing)** 與需求測試間的**雙向追溯性 (Traceability)**。
4. 敏捷的核心哲學是「回應**變更**重於遵循計畫」；進度的唯一真實度量標準是**可運行的軟體 (Working Software)**。
5. 看板框架透過對欄位強制設定**在製品數量上限 (WIP Limits)**，暴露流程瓶頸並落實拉動系統。
6. Ward Cunningham 提出的**技術債 (Technical Debt)** 隱喻指出，為了趕進度抄捷徑就如同向未來借款，未來修改代碼時所付出的額外痛苦時間即為**利息**。
7. 在極限編程 (XP) 中，測試驅動開發 (TDD) 的三部曲循環為 **RED (紅燈失敗)** → **GREEN (綠燈通過)** → **REFACTOR (重構優化)**。
8. DevOps 打破了開發與維運之間的混亂之牆，透過 **CI (持續整合)** 與 **CD (持續交付/部署)** 實現快速且可靠的發布。
9. 在 AI 規格驅動開發中，包裹在機率性大語言模型外圍的確定性編譯器與測試防護體系稱為**工程安全裝備 (Engineering Harness)**。

      });
      
      const dropdown = document.createElement('div');
      dropdown.className = 'nav-dropdown';
      
      dropdown.addEventListener('click', function(e) {
        e.stopPropagation();
      });
      
      const dropHeader = document.createElement('div');
      dropHeader.className = 'nav-dropdown-header';
      dropHeader.innerHTML = '<span>' + txtOutline + '</span>';
      dropdown.appendChild(dropHeader);
      
      const grid = document.createElement('div');
      grid.className = 'nav-dropdown-grid';
      
      sections.forEach(s => {
        const item = document.createElement('a');
        const isActive = (s.title === currentTitle);
        item.className = 'nav-dropdown-item' + (isActive ? ' active' : '');
        item.href = '#' + s.id;
        item.innerHTML = '<span class="badge">#' + s.id.padStart(2, '0') + '</span><span class="item-text" title="' + s.title + '">' + s.title + '</span>';
        
        item.addEventListener('click', function(e) {
          e.preventDefault();
          wrapper.classList.remove('is-open');
          dropdown.style.display = 'none';
          const targetHash = '#' + s.id;
          if (window.location.hash === targetHash) {
            window.dispatchEvent(new HashChangeEvent('hashchange'));
          } else {
            window.location.hash = targetHash;
          }
          setTimeout(() => { dropdown.style.display = ''; }, 350);
        });
        
        grid.appendChild(item);
      });
      
      dropdown.appendChild(grid);
      wrapper.appendChild(titleSpan);
      wrapper.appendChild(dropdown);
      return wrapper;
    }

    // Close any pinned dropdown when clicking anywhere outside
    document.addEventListener('click', function(e) {
      if (!e.target.closest('.header-nav-wrapper')) {
        document.querySelectorAll('.header-nav-wrapper.is-open').forEach(w => w.classList.remove('is-open'));
      }
    });

    // 2. Enhance each header element across all slides
    slideSections.forEach(sec => {
      const header = sec.querySelector('header');
      if (!header || header.dataset.navEnhanced) return;
      header.dataset.navEnhanced = 'true';
      
      const links = header.querySelectorAll('a');
      let prevLink = null;
      let nextLink = null;
      
      links.forEach(a => {
        const txt = a.textContent.trim();
        if (txt === '◄' || txt === '◀') prevLink = a;
        if (txt === '►' || txt === '▶') nextLink = a;
      });
      
      let title = header.textContent.trim();
      title = title.replace(/^[◄◀]\s*/, '').replace(/\s*[►▶]$/, '').trim();
      if (!title) return;
      
      header.innerHTML = '';
      if (prevLink) {
        prevLink.className = 'header-nav-arrow';
        prevLink.title = txtPrev;
        header.appendChild(prevLink);
        header.appendChild(document.createTextNode(' '));
      }
      
      const wrapper = createDropdownWrapper(title);
      header.appendChild(wrapper);
      
      if (nextLink) {
        header.appendChild(document.createTextNode(' '));
        nextLink.className = 'header-nav-arrow';
        nextLink.title = txtNext;
        header.appendChild(nextLink);
      }
    });
  }

  // =========================================================================
  // 2. Number Quick Jump (<kbd>Num</kbd> + <kbd>Enter</kbd>)
  // =========================================================================
  function initNumberQuickJump() {
    let inputBuffer = '';
    let timer = null;
    let hud = null;

    // Detect language: check titles or body text
    const slideSections = document.querySelectorAll('section[id]');
    let hasZh = false;
    slideSections.forEach(s => {
      if (/[\u4e00-\u9fa5]/.test(s.textContent || '')) hasZh = true;
    });
    const isEn = !hasZh;

    function getOrCreateHud() {
      if (!hud) {
        hud = document.createElement('div');
        hud.id = 'slide-quick-jump-hud';
        hud.style.cssText = [
          'position: fixed',
          'bottom: 36px',
          'left: 50%',
          'transform: translateX(-50%)',
          'background: rgba(15, 23, 42, 0.94)',
          'color: #ffffff',
          'padding: 8px 18px',
          'border-radius: 28px',
          'font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, system-ui, sans-serif',
          'font-size: 14px',
          'font-weight: 500',
          'box-shadow: 0 16px 36px rgba(0, 0, 0, 0.35), 0 0 0 1px rgba(255, 255, 255, 0.15)',
          'backdrop-filter: blur(16px)',
          '-webkit-backdrop-filter: blur(16px)',
          'z-index: 999999',
          'display: none',
          'align-items: center',
          'gap: 8px',
          'pointer-events: none',
          'opacity: 0',
          'transition: opacity 0.15s ease, transform 0.15s ease'
        ].join(';');
        const targetParent = document.fullscreenElement || document.body;
        targetParent.appendChild(hud);
      }
      const parent = document.fullscreenElement || document.body;
      if (hud.parentElement !== parent) {
        parent.appendChild(hud);
      }
      return hud;
    }

    function getTotalSlides() {
      const secs = document.querySelectorAll('section[id]');
      return secs.length || 1;
    }

    function showHud() {
      const el = getOrCreateHud();
      const total = getTotalSlides();
      const label = isEn ? 'Go to slide:' : '跳至頁碼:';
      const enterHint = isEn ? 'Enter ↵' : 'Enter 確認 ↵';
      el.innerHTML = '<span>🧭 ' + label + '</span> ' +
        '<strong style="color: #38bdf8; font-size: 20px; font-weight: 700; font-family: ui-monospace, SFMono-Regular, Menlo, monospace; letter-spacing: 1px;">' + inputBuffer + '</strong> ' +
        '<span style="opacity: 0.6; font-size: 13px;">/ ' + total + '</span> ' +
        '<span style="background: rgba(255,255,255,0.18); padding: 2px 7px; border-radius: 6px; font-size: 11px; margin-left: 2px; font-weight: 600;">' + enterHint + '</span>';
      el.style.display = 'flex';
      el.style.opacity = '1';

      if (timer) clearTimeout(timer);
      timer = setTimeout(clearInput, 2800);
    }

    function clearInput() {
      inputBuffer = '';
      if (timer) {
        clearTimeout(timer);
        timer = null;
      }
      if (hud) {
        hud.style.opacity = '0';
        setTimeout(() => {
          if (inputBuffer === '' && hud) hud.style.display = 'none';
        }, 150);
      }
    }

    function jumpToSlide(num) {
      const total = getTotalSlides();
      const target = Math.max(1, Math.min(num, total));
      const targetHash = '#' + target;
      
      // Visual flash confirmation
      const el = getOrCreateHud();
      const confirmedMsg = isEn ? ('✓ Slide ' + target) : ('✓ 第 ' + target + ' 頁');
      el.innerHTML = '<span style="color: #34d399; font-weight: 700; font-size: 15px;">' + confirmedMsg + '</span>';
      el.style.display = 'flex';
      el.style.opacity = '1';
      setTimeout(clearInput, 500);

      if (window.location.hash === targetHash) {
        window.dispatchEvent(new HashChangeEvent('hashchange'));
      } else {
        window.location.hash = targetHash;
      }
    }

    window.addEventListener('keydown', function(e) {
      // Don't intercept when focusing editable form elements
      const active = document.activeElement;
      if (active && (active.tagName === 'INPUT' || active.tagName === 'TEXTAREA' || active.tagName === 'SELECT' || active.isContentEditable)) {
        return;
      }

      // Ignore if modifier keys are pressed
      if (e.ctrlKey || e.altKey || e.metaKey) {
        return;
      }

      // Resolve digit from key or code (supports '2', 'Digit2', 'Numpad2')
      let digit = null;
      if (e.key >= '0' && e.key <= '9') {
        digit = e.key;
      } else if (/^(?:Digit|Numpad)([0-9])$/.test(e.key)) {
        digit = e.key.replace(/^(?:Digit|Numpad)/, '');
      } else if (/^(?:Digit|Numpad)([0-9])$/.test(e.code || '')) {
        digit = (e.code || '').replace(/^(?:Digit|Numpad)/, '');
      }

      if (digit !== null) {
        inputBuffer += digit;
        if (inputBuffer.length > 4) inputBuffer = inputBuffer.slice(-4);
        showHud();
        return;
      }

      // Backspace
      if ((e.key === 'Backspace' || e.code === 'Backspace') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        inputBuffer = inputBuffer.slice(0, -1);
        if (inputBuffer.length === 0) {
          clearInput();
        } else {
          showHud();
        }
        return;
      }

      // Escape
      if ((e.key === 'Escape' || e.code === 'Escape') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        clearInput();
        return;
      }

      // Enter key confirms numeric jump
      if ((e.key === 'Enter' || e.code === 'Enter' || e.code === 'NumpadEnter') && inputBuffer.length > 0) {
        e.preventDefault();
        e.stopPropagation();
        const targetPage = parseInt(inputBuffer, 10);
        if (!isNaN(targetPage)) {
          jumpToSlide(targetPage);
        } else {
          clearInput();
        }
      }
    }, true);
  }

  // Initialize both features
  function init() {
    initHeaderDropdown();
    initNumberQuickJump();
  }

  if (document.readyState === 'loading') {
    document.addEventListener('DOMContentLoaded', init);
  } else {
    init();
  }
  setTimeout(init, 400);
})();
