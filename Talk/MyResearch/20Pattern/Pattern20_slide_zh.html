論文定位與研究貢獻： - 書目資訊：薛念林（Nien-Lin Hsueh），〈Design Pattern Analysis with Software Evolution Data〉，發表於 Journal of Information Science and Engineering（JISE）第 36 卷第 1 期，第 53–73 頁，2020 年 1 月（DOI: 10.6688/JISE.202001_36(1).0004；收稿日 2018/07/19、接受日 2018/09/17；科技部計畫補助 MOST 106-2221-E-035-MY2）。 - 核心研究問題：Gang-of-Four（GoF）設計模式常被導入以提升軟體可維護性與可擴充性，但既有評估方法多僅針對單一版本的靜態結構快照進行分析，未能檢驗已部署模式在後續軟體演化歷程中是否真正發揮預期效益。 - 方法與實證範疇：本研究形式化定義模式應用情境（PAC）、預期模式使用方式（EPU）與使用程度指標（DoU），實作網頁版 Pattern Utilization Analyzer（PUA）工具，並針對 15 個 Java 開源專案、共 296 次版本演化，實證評估 9 組（涵蓋 11 種）品質改善型 GoF 設計模式。

過度設計與演化回收率之實證反差： - 架構投資與維護成本的權衡：導入設計模式需額外增加抽象介面、類別層級與間接呼叫成本，其目的是為未來的需求變更預留彈性。然而當預期的擴充從未發生，或模式被過度套用、誤用時，這些結構複雜度反而成為額外維護負擔，甚至影響系統效能。 - 296 次演化的跨專案實證發現：追蹤 SourceForge 上 15 個真實 Java 開源系統的長期版本歷程後發現，各類已部署設計模式的平均使用度皆低於 0.20，更有大量實例呈現 DoU = 0（初始部署後全程未被擴充或重複使用）。 - 核心分析命題：此現象引導本研究以嚴謹統計檢定釐清——偏低的使用度究竟源於「設計模式本身的類型差異」（RQ1），抑或取決於「專案領域特性與團隊架構設計紀律」（RQ2）。

論文結構與論證脈絡： - 第一至二章（導論與背景文獻）：闡明為何評估維護性必須立基於跨版本演化數據而非單一快照，以四項準則統整 12 篇設計模式評估文獻（Table 1），並說明選用 Tsantalis 等人圖形相似度演算法而非 DP-Miner 的技術依據。 - 第三章（使用度評估方法）：介紹設計模式四大角色分類、拆解 FR 與 NFR 意圖，並以數學公式形式化定義 PAC、EPU、使用度判定謂詞與 DoU 指標（公式 1–6、Fig. 3–6）。 - 第四章（系統設計與實證結果）：說明三模組 PUA 網頁系統架構（Fig. 7）、以 JHotDraw 六個 Observer 實例演示分析流程（Fig. 8），並呈現 15 個 SourceForge 開源專案資料集（Table 2）與完整 15 × 9 DoU 矩陣（Table 3）。 - 第五至六章（統計分析、效度威脅與結論）：以單因子 ANOVA 與 Scheffé 事後檢定回答 RQ1 與 RQ2（Table 4–6、Fig. 9–10），依 Yin 之個案研究框架檢視四大效度威脅，並歸納對開發者、分析師與專案經理的實務價值及雲端化展望。

軟體演化視角評估設計模式之必要性： - 靜態快照模型的盲點：傳統品質評估多採靜態物件導向指標或品質模型，僅針對軟體生命週期中的單一版本進行檢視。然而多數設計模式的核心目標在於降低未來需求變更時的維護負荷，單一時間點快照只能驗證「模式是否存在」，無法判定「模式是否在後續演化中被有效利用」。 - 兩種演化軌跡對照（論文 Fig. 1–2）：若開發者於 v1 部署 Strategy 模式 dp1 以利未來擴充演算法，但從 v1 到 v10 從未新增或移除任何具體策略類別（Fig. 1），則該模式屬於低度利用；相對地，若 v1→v2 移除舊策略、v2→vn 新增新策略（Fig. 2），則表示該模式成功讓系統透過「擴充」而非「修改既有程式碼」來吸納變更。 - 演化變更熱點（Hot Spot for Change）：預期使用方式即代表設計模式預期承接變更的熱點，唯有跨所有連續版本比對結構演變，才能客觀衡量其維護投資是否回收。

四大研究目標與統計假說架構： - 四項研究目標：（1）運用軟體演化數據形式化提出設計模式使用度評估方法；（2）開發自動化分析工具 PUA 支援大規模驗證；（3）應用於 15 個公開保存版本歷程的 SourceForge 開源系統（藉助開源版本庫透明度）；（4）透過統計檢定探討模式使用度與模式類型或專案間之關聯。 - RQ1（模式類型因子）：以單因子 ANOVA（α = 0.05）檢定虛無假設 H0: μ1 = μ2 = ... = μ9（9 組品質改善型設計模式之平均 DoU 相等），檢驗是否特定設計模式天生就比其他模式更容易在演化中獲得使用。 - RQ2（開源專案因子）：以單因子 ANOVA（α = 0.05）檢定虛無假設 H0: μ1 = μ2 = ... = μ15（15 個開源專案之平均 DoU 相等），檢驗應用領域屬性（如 MVC 圖形框架相對於小型工具軟體）與開發團隊紀律是否造成顯著的使用度差異。

設計模式評估文獻與偵測技術對照（Table 1）： - Table 1 之四大分類準則：依研究動機（Motivation）、方法（Method）、是否分析程式碼（Code Analysis）與研究標的（Subjects：設計模式、軟體系統、論文或人類受試者）整理 12 篇代表文獻： - 靜態指標與良構性：Huston（2001）發現不同 OO 指標對設計模式可能產生相互矛盾的評估結果；Hsueh 等人（2008）提出量化方法驗證模式是否良構，但未分析演化程式碼。 - 人工受控實驗：Prechelt 等人（2001, 2002）比較使用模式與較簡設計之維護效益及文件化助益；Ng 等人（2007, 2012）證實善用已部署模式的維護者交付的程式碼缺陷率顯著較低，並指出程式理解與人為因素的關鍵性。 - 系統性回顧與專家調查：Zhang 與 Budgen（2012, 2013）指出僅 3 種模式獲資深專家普遍肯定，約四分之一模式評價偏低。 - 演化、污垢與缺陷分析：Aversano 等人（2007）追蹤模式修改頻率與共變類別；Vokáč（2004）探討模式與缺陷數之關聯；Izurieta 與 Bieman（2013）研究三個開源專案中的模式污垢（grime）與腐化；Hsueh 等人（2011）曾針對單一專案 Jaxe 進行時機與效益初探。 - 偵測演算法選型依據：Tsantalis 等人（2006）將系統與模式靜態結構表徵為圖形與矩陣，透過頂點相似度評分可偵測經修改之模式變異體，並在文件完整的 JHotDraw 上達到 100% 精確率與 100% 召回率；相較之下，Dong 等人的 DP-Miner（2007）雖採加權矩陣提升靜態行為分析準度，但不支援模式變異體與動態分析。

雙軌設計模式使用度評估架構（Fig. 3）： - 路徑 A — 理論規格建立（Fig. 3 左側）：由於並非所有 GoF 模式皆為了解決維護性問題，方法首先進行模式角色分類並篩選出品質改善型模式；接著將模式意圖拆解為功能性意圖（FR-intent）與非功能性意圖（NFR-intent），據此推導出形式化的預期模式使用方式（EPU）。 - 路徑 B — 實證演化挖掘（Fig. 3 右側）：自版本控制庫收集目標專案的連續發行版本原始碼，逐版本執行圖形相似度模式偵測，並萃取每個模式實例的結構角色對應——即模式應用情境（PAC）。 - 理論與實證之橋接：將相鄰版本的 PAC 結構差異與路徑 A 定義的 EPU 進行符合度比對，即可客觀判定各模式實例在每次版本演進中是否真正滿足其原始設計目的。

設計模式四大角色分類與 FR/NFR 意圖拆解（Fig. 4）： - 四大角色分類框架（Hsueh et al., 2009）： 1. 活動促進者（Activity-Facilitator）：以經驗法則協助系統設計中的重複性非演算法活動，如系統分解、物件配置、存取控制、控制流與元件組合。 2. 品質改善者（Quality-Improver，本研究核心）：因應主觀、相對且具交互影響的非功能性需求（NFR），在滿足基本功能前提下提供更佳的可維護性、重用性與擴充性。 3. 衝突解決者（Conflict-Resolver）：透過資源特化、引入代理者或仲裁者，協調資源競爭、需求分歧與設計階段常見的副作用衝突。 4. 問題解決者（Problem-Solver）：處理邊界條件與系統可靠性例外，例如 Observer 模式透過註冊與通知機制解決主體與觀察者之間的狀態不一致問題。 - FR 結構與 NFR 結構對照（Fig. 4，以 Strategy 為例）：FR-intent 描述模式「做什麼」，對應較簡潔的 FR-structure（Context 直接呼叫演算法）；NFR-intent 描述如何提升品質屬性，對應擴充後的 NFR-structure（引入抽象 Strategy 介面，使日後可在不更動 Context 的情況下新增或移除 ConcreteStrategy）。正因使用度旨在驗證 NFR 意圖是否於演化中兌現，故僅鎖定品質改善者進行評估。

PAC、EPU 與使用度判定謂詞之數學形式化（公式 1–5、Fig. 5）： - 模式應用情境（公式 1）：PAC(dp, D) = {<element, r>} 記錄軟體版本 D 中參與設計模式 dp 的設計元素（類別）與其扮演的角色 r。以資料壓縮系統套用 Strategy 為例（公式 2）：PAC(Strategy, D) = {<DataCompression, R_C>, <CompressionTool, R_S>, <RAR, R_CS>, <ZIP, R_CS>}，其中 R_C、R_S、R_CS 分別代表 Context、Strategy 與 ConcreteStrategy 角色。 - 預期模式使用方式（公式 3）：EPU(dp) = {<role, operator>}（其中 operator ∈ {+, −}）形式化定義該模式於演化中預期對關鍵角色執行的結構操作。Strategy 之預期使用為新增或移除具體策略類別而不改動其他元件，故 EPU(Strategy) = {<R_CS, +>, <R_CS, −>}（公式 4）。 - 使用度判定謂詞（公式 5）：utilized(dp, D_{j+1}) ⇔ ∃ D_j 使得 Δ(PAC(dp, D_j), PAC(dp, D_{j+1})) 符合 EPU(dp)，其中 D_j 與 D_{j+1} 為部署同一模式實例 dp 之相鄰版本。如 Fig. 5 所示，於 D_{j+1} 在 CompressionTool 介面下新增 7-zip 壓縮類別，其結構差異恰好對應 <R_CS, +>，因而形式化判定為有效使用。

模式使用程度（DoU）定義與生命週期正規化（公式 6、Fig. 6）： - 指標公式（公式 6）：DoU =（實際被使用次數）／（模式存活演化次數），數值介於 0 與 1 之間。分子計算滿足 EPU 判定謂詞之相鄰版本轉換次數；分母為該模式實例連續存活之版本數減 1，藉此公平處理「中途才導入」或「中途遭移除」的實例。 - Fig. 6 逐一演算（8 個版本 V1–V8、5 個模式實例）： - dp1（存活 V1–V8，7 次演化）：於 V3→V4、V4→V5 有效使用 2 次，DoU = 2/7。 - dp2（存活 V1–V8，7 次演化）：於 V3→V4、V4→V5、V6→V7 有效使用 3 次，DoU = 3/7。 - dp3（於 V3 導入、存活 V3–V8，5 次演化）：於 V4→V5 有效使用 1 次，DoU = 1/5。 - dp4（於 V3 導入、於 V5 移除，僅歷經 2 次演化）：於 V3→V4 有效使用 1 次，DoU = 1/2（分母僅計入實際存活期）。 - dp5（於 V3 導入、存活 V3–V8，5 次演化）：全程未發生符合 EPU 之擴充，DoU = 0/5。 - 論文詮釋提醒：較高的 DoU 代表該模式對系統演化貢獻較頻繁，但判定某低 DoU 模式是否確實「無用」而應移除，仍須仰賴開發者結合業務脈絡進行專業審查。

PUA 自動化分析系統架構與模式分組細節（Fig. 7）： - 三大模組網頁架構：Pattern Utilization Analyzer（PUA）整合三個核心模組：（1）版本控制模組，負責管理自 SourceForge 匯入之多版本原始碼與各版本偵測結果；（2）PAC 模組，解析 Pattern4 輸出並儲存各版本之模式應用情境；（3）EPU/PAE 模組，自動比對相鄰版本 PAC 差異是否符合 EPU，並計算實例與專案層級之 DoU。 - Pattern4 偵測範圍（9 組涵蓋 11 種 GoF 模式）：透過 Tsantalis（2011）之圖形相似度評分工具逐版本偵測建立型（Factory Method [FM]、Prototype [P]）、結構型（Adapter-Command [AC]、Composite [C]、Decorator [D]）與行為型（Observer [O]、State-Strategy [SS]、Template Method [TM]、Visitor [V]）。 - 合併分組原因：由於 Adapter 與 Command、State 與 Strategy 在靜態類別圖與關聯矩陣上具備同構結構，靜態圖形比對工具無法僅憑結構區分兩者，故依 Pattern4 規格合併為 AC 與 SS 兩組進行統計分析。

JHotDraw 專案 Observer 實例層級剖析（Fig. 8）： - 標竿案例地位：JHotDraw 源自 Erich Gamma 所設計之二維結構化繪圖框架，以高度規範地運用經典設計模式聞名，是檢驗模式偵測與演化分析方法的指標系統。 - 五個連續版本追蹤（5.2 → 5.3 → 5.4b1 → 5.4b2 → 6.0b1）：PUA 追蹤到 6 個獨立的 Observer 實例（dp1–dp6）： - 於 v5.2 部署（歷經 4 次相鄰演化）：dp1 於 5.3→5.4b1 被使用 1 次（DoU = 1/4）；dp2 全程未被使用（0/4）；dp3 在 4 次轉換中有 3 次被有效擴充（DoU = 3/4 = 75%）；dp4 被使用 1 次（1/4）。 - 於 v5.3 新引入（歷經 3 次相鄰演化）：dp5 被使用 1 次（1/3）；dp6 全程未使用（0/3）。 - 跨專案對照意涵：即便在完整 8 次 JHotDraw 演化（5.2–7.6）中，Observer 以 DoU = 0.350 居全實驗 15 個專案之冠，Fig. 8 仍顯示同一系統內不同實例的使用率存在 0% 至 75% 的顯著異質性。

15 個開源專案實驗基準與領域覆蓋（Table 2）： - 抽樣策略設計：為兼顧與既有文獻之可比性並避免挑選偏差，資料集結合 3 個軟體工程文獻經典標竿專案（JHotDraw、JUnit、FreeMind）以及自 SourceForge 隨機挑選之 12 個 Java 開源專案（HtmlUnit、Jaxe、JConvert、JEdit、Jena、JGnash、JMemorize、LatexDraw、PDFsam、Pixelitor、TuxGuitar、Weka）。 - 跨領域系統多樣性：涵蓋二維與向量／影像繪圖（JHotDraw、LatexDraw、Pixelitor）、心智圖（FreeMind）、自動化測試與無介面瀏覽器（JUnit、HtmlUnit）、XML 與程式編輯器（Jaxe、JEdit）、語意網 RDF/OWL 工具箱（Jena）、機器學習演算法庫（Weka）、個人財務（JGnash）、閃卡學習（JMemorize）、PDF 分割合併（PDFsam）、單位換算（JConvert）及多軌吉他譜編輯（TuxGuitar）。 - 時間與演化規模：開發歷程最長橫跨 12 年（2000–2012），單一專案演化次數介於 8 次（JHotDraw 5.2–7.6）至 38 次（Jaxe 1.0–3.5），總計分析 296 次版本演進。

跨專案 DoU 實證矩陣深度解讀（Table 3）： - 矩陣編碼與有效觀測值：Table 3 共計 96 個已部署之「專案 × 模式」有效儲存格（對應 ANOVA 總自由度 df = 95）。空白表示該專案未部署該模式，0 表示已部署但在追蹤期間從未被有效使用。 - 普遍偏低的使用現況：所有 9 組設計模式的平均 DoU 皆低於 0.20，顯示多數已部署模式並未頻繁發揮預期擴充功能。其中 Visitor（V）僅見於 Jena 與 JHotDraw 且兩者皆為 0；Prototype（P）最高亦僅 0.060（Jena）。 - 高度領域契合之亮點案例： - FreeMind 整體表現最為優異，Decorator（0.333）、Observer（0.333）、State-Strategy（0.301）與 Template Method（0.263）均名列前茅。 - JHotDraw 的 Observer 達全場最高 0.350，State-Strategy（0.176）與 Decorator（0.162）亦具水準。 - Weka 的 State-Strategy 高達 0.315（對應機器學習演算法持續擴充）；LatexDraw 的 Composite 達 0.261（對應階層式繪圖元件）；TuxGuitar 的 Factory Method 達 0.200；HtmlUnit 的 Decorator 達 0.196。 - 相對地，Jaxe、JEdit、PDFsam、Pixelitor、JUnit、JMemorize 與 JGnash 普遍偏低或掛零。

RQ1 單因子 ANOVA 統計檢定與行為詮釋（Table 4、Fig. 9）： - 假說設定（顯著水準 α = 0.05）：虛無假設 H0: μ1 = μ2 = ... = μ9（9 組設計模式之平均 DoU 無差異），對立假設 H1 為至少有一組平均數不同。 - 變異數分析數據（Table 4）：組間變異 SS = 0.090（df = 8, MS = 0.011），組內變異 SS = 0.626（df = 87, MS = 0.007），總變異 SS = 0.716（df = 95），統計量 F = 1.569、p = 0.146（> 0.05）。因此無法拒絕 H0，代表已部署模式的使用度並不取決於設計模式類型。 - 開發者行為面成因：Fig. 9 盒鬚圖顯示所有模式類型之平均 DoU 皆低於 0.20，無任何模式具備天生的使用度優勢。結合 Ng 等人（2012）與 Vokáč（2004）研究，論文提出兩點解釋：（1）模式部署深受人類開發習慣與程式理解門檻影響；（2）工程師傾向挑選自己熟悉的模式，並因結構複雜度而規避如 Visitor 等較複雜模式，使部署選擇與實際演化需求脫節。

RQ2 單因子 ANOVA 與 Scheffé 事後多重比較（Table 5–6、Fig. 10）： - 假說設定（顯著水準 α = 0.05）：虛無假設 H0: μ1 = μ2 = ... = μ15（15 個開源專案之平均 DoU 相等），對立假設 H1 為專案間平均 DoU 存在差異。 - 變異數分析數據（Table 5）：組間變異 SS = 0.356（df = 14, MS = 0.025），組內變異 SS = 0.361（df = 81, MS = 0.004），總變異 SS = 0.716（df = 95），F = 5.704、p < 0.001，強烈拒絕 H0。專案因子獨自解釋近半數總變異量（η² = 0.356 / 0.716 ≈ 49.7%）。 - Scheffé 事後多重比較（Table 6）：採適用於不等組樣本數且較保守的 Scheffé 法檢定發現，FreeMind 顯著優於 8 個專案：Jaxe（Δ = 0.256, p = 0.001）、Jena（Δ = 0.207, p = 0.006）、jGnash（Δ = 0.243, p < 0.001）、jMemorize（Δ = 0.242, p < 0.001）、JUnit（Δ = 0.230, p = 0.002）、PDFsam（Δ = 0.250, p = 0.028）、Pixelitor（Δ = 0.246, p = 0.001）與 TuxGuitar（Δ = 0.191, p = 0.040）。 - 領域架構機制：在 JHotDraw（Observer = 0.350）與 FreeMind（Observer 與 Decorator 皆為 0.333）這類 MVC 互動式圖形介面系統中，通知監聽與視覺裝飾機制直接承接圖形變更後的視圖更新演化（Aversano et al., 2007），反映良好的領域契合與持續維護紀律。

依循 Yin 個案研究框架之四大效度威脅檢核（第 5.4 節）： - 建構效度（模式偵測準確度）：DoU 計算高度仰賴 Tsantalis 等人靜態圖形相似度工具（Pattern4）之精確率與召回率。緩解依據為該工具於文件完整的 JHotDraw 達 100% 精確率與 100% 召回率（Tsantalis et al., 2006），且於 Aversano 等人（2009）跨系統獨立審核中整體精確率亦超過 85%，有效限制偽陽性對統計結果的干擾。 - 內部效度（混淆因子控制）：為釐清影響 DoU 之真正因子，研究以單因子 ANOVA（α = 0.05）搭配 Scheffé 事後檢定，嚴謹分離出不顯著之模式類型因子（p = 0.146）與極顯著之專案因子（p < 0.001）。 - 外部效度（推論泛化範圍）：雖然 15 個 SourceForge Java 系統涵蓋多元領域與規模，但外推至大型企業封閉原始碼或非 Java 生態系仍需更多實證樣本；此外，模式範圍刻意限定於 23 種 GoF 模式中具明確演化 NFR 意圖之 9 組（11 種）品質改善型模式（Hsueh et al., 2009）。 - 信度（可重現性）：全部 15 個開源專案原始碼（SourceForge）與 Pattern4 工具皆為公開資源；論文第 4.2 節詳列四步驟 PUA 執行程序，Table 3 亦完整公開原始 DoU 數據矩陣，支援獨立統計重現。

實證總結、維護決策價值與未來技術藍圖： - 核心實證結論：橫跨 15 個 Java 開源專案與 296 次軟體演化，已部署 GoF 設計模式的平均使用度普遍低於 0.20，許多實例在初始部署後從未再被重複利用。統計檢定證實模式使用度不因模式類型而異（p = 0.146），而是顯著取決於軟體專案領域與設計紀律（p < 0.001）。 - 論文第 6 節提出之三項工程實務價值： 1. 開發人員：於專案演進期間即時掌握已部署設計模式的實際活用狀態。 2. 維護分析師：依據低 DoU 診斷結果規劃重構行動，包含重構至具高使用度之模式，或移除長期未啟用之冗餘抽象。 3. 專案經理：當需求變更始終未命中原設擴充點時，可藉此回溯功能規劃與架構預測之落差。 - 未來研究方向：將 PUA 重構為雲端服務以提升跨版本圖形比對之運算效能；擴充偵測器與 EPU 規則以支援更多 GoF 與架構設計模式；並運用升級後平台對更大規模之現代開源與企業系統進行長期實證。
