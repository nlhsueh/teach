論文基本資訊與研究定位： - 篇名：Automatic testing environment for multi-core embedded software—ATEMES（多核心嵌入式軟體自動化測試環境） - 發表期刊：The Journal of Systems and Software (JSS), Vol. 85, pp. 43–60, 2012（Elsevier，DOI: 10.1016/j.jss.2011.08.030）。 - 作者群：孔崇旭（通訊作者，台中教大）、石志雄（東海）、熊博安（中正）、賴泓叡（台中教大）、張志宏（修平）、朱正忠（東海）、薛念林（逢甲）、楊朝棟（東海）。 - 核心立意：針對多核心嵌入式軟體測試之六大痛點，建構主機—目標端純軟體自動化測試環境 ATEMES，於 ARM11 MPCore 四核心實機上驗證複合型別 C/C++ 測試自動生成、多回合 GCOV 覆蓋率、即時多核心 CPU 監控、Intel TBB 管線 Token 最佳化與中斷回應效能評估。

論文結構導覽： - 第 1 節（緒論，pp. 43–44）：歸納多核心嵌入式測試六大挑戰，提出 ATEMES 之主機—目標端交叉測試架構。 - 第 2 節（相關研究，pp. 44–45）：評析 JaBUTi/ME、Justitia 與 Cho & Choi 等嵌入式測試工具之自動化不足。 - 第 3 節（自動化測試機制，pp. 45–49）：詳述遞迴複合型別資料生成（Fig. 1）、CppUnit 案例與驅動生成（Figs. 2–4）、多回合累積覆蓋率（Figs. 5–7）及 TBB 5-Token 滑動視窗分析（Figs. 8–11）。 - 第 4 節（系統工具設計，pp. 49–54）：說明四大模組（PRPM、HSATM、TSATM、POPM）、五層架構（Fig. 13）與 12 步驟多回合測試流程（Fig. 29）。 - 第 5 節（六大實驗，pp. 54–58）：於 ARM11 MPCore（4 CPUs）執行覆蓋率、單元測試、多核心 CPU 監控、TBB 平行基準、可用性問卷與中斷回應時間測試。 - 第 6 節（結論，pp. 58–59）：呈現 Table 7 綜合功能比較表、系統限制與未來方向。

六大問題拆解與對應解方（第 1 節，pp. 43–44）： - 論文明確界定多核心嵌入式測試之六大挑戰，並將 ATEMES 核心機制一一對應： - 挑戰 (1) ➔ 遞迴複合型別資料生成 + CppUnit 測試案例／驅動自動合成。 - 挑戰 (2)(3) ➔ 主機—目標端交叉測試卸載 + Intel TBB 多回合 Token 自動基準最佳化。 - 挑戰 (1)(4) ➔ 多回合 GCOV 覆蓋率自動累積與主機端即時視覺化。 - 挑戰 (3)(5) ➔ 自動插樁 C++ Mutex 保護共享統計資料 + ARM Linux 系統呼叫監控各核心使用率 + 中斷間隔回應測試。 - 挑戰 (6) ➔ 針對 30 位受測者執行 44 題六構面可用性與信度實證評估。

競品定位分析（第 2 節與 Table 7，pp. 44–45, 59）： - Table 7 將 ATEMES 與三位代表性學者之純軟體測試／平行分析工具（Erik Putrycz、Alexei Alexandrov、William Thies）進行 12 項能力比對。 - ATEMES 具備五項他者皆無之獨特能力：（1）自動多回合測試、（2）自動測試驅動生成、（3）複合 C/C++ 資料結構自動測試、（4）執行期即時結果呈現、（5）多核心中斷效能與覆蓋率整合測試。

系統架構與模組職責（第 4 節，Figs. 12–29，pp. 49–54）： - ATEMES 將繁重解析與圖形介面留於 x86 Ubuntu 工作站，僅於 ARM11 MPCore 目標板部署輕量執行器： 1. PRPM（前處理模組）：含 Code Manager、CodeParser、UnitTestCaseGenerator 與 InstrumentCodeEditor（自動插樁 Mutex 鎖定、TBB 計時器與核心使用率探針）。 2. HSATM（主機端自動測試模組）：含 TestDriverGenerator（產生 CppUnit XML 驅動）與 AutomaticTestHost（自動交叉編譯與上傳）。 3. TSATM（目標端自動測試模組）：於 ARM11 驅動 TargetSideTestController 與 Profiler Manager（收集 CPU 效能與 .gcda/.gcov 覆蓋日誌）。 4. POPM（後處理模組）：解析日誌、以 JFreeChart 即時繪圖並動態回饋給 PRPM/HSATM 啟動下一回合。 - 五層軟體堆疊（Fig. 13）：硬體層（x86 / ARM11）➔ Linux OS ➔ 函式庫層（CppUnit、GCOV、JFreeChart）➔ ATEMES 應用層（C/C++ 與 Java）➔ 主機 GUI 層（Java）。

自動化生成與覆蓋率演算法（第 3.1 與 3.2 節，Figs. 1–7，pp. 45–48）： - 全自動 vs. 半自動單元測試：全自動模式完全無須人工介入，專責捕捉目標程式之執行期例外與 Segmentation Fault；半自動模式則允許測試工程師輸入預期結果（Oracle），由自動生成的 CPPUNIT_ASSERT 判斷功能正確性。 - 以 Fig. 3 的 binsearch()（參數包含結構陣列與兩個整數）為例，演算法能自動展開結構內部欄位並生成對應讀檔迴圈，大幅節省撰寫 C/C++ 測試樣板的時間。 - 多回合聯集累積機制讓每回合僅須於目標板執行少量測資，再由主機端彙整總覆蓋率，有效避開嵌入式記憶體限制。

Intel TBB 平行管線與中斷測試演算法（第 3.3 與 5.7 節，Figs. 8–11，pp. 48–49）： - Intel TBB 管線（Pipeline）的 Token 數直接決定並行度：過小導致多核心閒置，過大則徒增緩衝區與排程負擔。 - ATEMES 自動插樁計時器與 C++ Mutex（避免多執行緒統計資料競爭），跨多回合掃描 Token 數並計算 5-Token 滑動平均延遲（例如 1–5 為 17.6 ms、2–6 為 12.4 ms、3–7 降至 11.8 ms、4–8 回升至 12.4 ms），自動推薦最低延遲區間（3–7）。 - 在中斷效能測試中，ATEMES 則自動掃描核心數、中斷間隔與中斷次數（每間隔連續觸發 20 次中斷），協助系統架構師以實測數據評估硬體規格。

實驗 1 與 2 數據深入解析（第 5.1 與 5.2 節，Tables 1–3，Figs. 30–31，pp. 54–55）： - 實驗一（Tables 1–2）：針對 13 支資料結構程式（多含結構陣列參數）於 ARM11 上進行 20 回合隨機測試，每回合總耗時穩定介於 889–1,006 ms。merge、adjust、getRollDiceSum 首回合即達 100% 列與分支覆蓋；seqsearch、merge_pass、merge_sort、quicksort 第 2 回合收斂至 100%；insertion_sort 第 5 回合、rollDiceGame 第 9 回合、heapsort 第 10 回合達標。僅 binsearch（分支 90%）與 fractionCalculator（列 92%、分支 65%）未能觸及深層條件分支，成為後續導入適應性隨機測試（ART）的直接依據。 - 實驗二（Table 3，Fig. 31）：六支程式共 30 筆案例清楚區分為通過（20 筆，67%）、斷言失敗（5 筆，16.5%）與執行期例外／區段錯誤（5 筆，16.5%）。

實驗 3 多核心遙測分析（第 5.3 節，Table 4，Fig. 32，pp. 55–56）： - Fig. 32(a)–(d) 記錄矩陣乘法執行過程中四個連續時間點的 ARM11 四核心負載分布。 - Table 4 數據顯示顯著的核心負載差異：Core 4 平均最高（31.06%，峰值 75%）、Core 3 次之（29.93%，峰值 76%）、Core 1 極度平穩（25.06%，區間 22–28%），而 Core 2 平均最低（18.98%，峰值 62%）。這讓開發者能直觀檢驗作業系統排程與執行緒切分是否充分發揮四核心效能。

實驗 4 TBB 平行基準剖析（第 5.4 節，Table 5，Fig. 33，p. 56）： - 本實驗全自動完成 100 組 Token × 4 種核心組態 = 400 次實機效能測試，完全無須人工修改原始碼或手動重新編譯。 - Fig. 33 驗證兩項關鍵現象：（1）核心數越多，整體影像處理延遲越低；（2）Token 數存在明確效能拐點——低於 5 導致核心閒置，高於 12 則無顯著加速卻增加緩衝區壓力。Table 5 給出精準推薦範圍（1 核心 5–9、2 核心 6–10、3 核心 7–11、4 核心 8–12）。

實驗 5 可用性與信度分析（第 5.5 節，Table 6，Fig. 34，p. 57）： - 為回應研究挑戰 (6)，30 位研究生在 2 小時內以資料結構、矩陣乘法與影像處理三類範例程式全面試用 ATEMES。 - 內部一致性檢定：全 44 題 Cronbach's α = 0.928（標準化 α = 0.927），總平均達 4.533 / 5.0（變異數 0.012），六個構面均分皆突破 4.5 分。 - 作者亦客觀討論效度考量：研究生過去較少接觸多核心嵌入式自動化測試工具，因此免手寫程式的自動化特性帶來極高接受度；同時忠實記錄四項待改進回饋（GUI 美觀、穩定度、網頁儲存與操作說明文件）。

實驗 6 中斷回應時間評估（第 5.7 節，Figs. 35–40，pp. 58–59）： - 嵌入式產品量產時常面臨硬體成本與即時中斷服務水準（SLA）的雙重壓力。 - 測試工程師僅須在 ATEMES 中指定中斷處理函式名稱，系統即自動生成包含核心數、中斷間隔與中斷次數（20 次）的測試驅動並跨端執行（Figs. 37–40）。 - 實驗定量指出：1 核心須中斷間隔 >= 4 秒、2 核心可縮短至 >= 2 秒，而 3 或 4 核心則可確保 512×384 六階段視訊管線在高頻中斷下依然流暢無阻。

綜合討論與研究限制（第 5.6 與 6 節，pp. 57–59）： - 作者於結論中務實指出兩項核心技術限制：（1）單元測試之預期輸出驗證仍須人工介入（經典 Test Oracle 問題），（2）覆蓋率僅限於列覆蓋與分支覆蓋。 - 實驗一中 fractionCalculator 的分支覆蓋停滯亦說明純隨機輸入在複雜條件判斷上的天花板，直接指向未來導入適應性隨機測試（ART）之必要性。 - 整體而言，ATEMES 以純軟體架構整合五大測試功能，大幅超越既有單點嵌入式工具。

結論與未來研究藍圖（第 6 節，p. 59）： - ATEMES 透過主機—目標端四模組閉迴路架構，同時化解了嵌入式資源受限、C/C++ 複合型別測試繁瑣與多核心平行參數調校三大難題。 - 論文明確提出三大後續研發方向： 1. 發展更精準之自動測資與案例生成演算法（如 Adaptive Random Testing）。 2. 結合網頁技術打造完整回歸測試與結果雲端歸檔系統。 3. 深化多核心嵌入式軟體專屬測試項目，包含多執行緒競爭條件（Race Condition）自動化測試與平行管線效能分析。
